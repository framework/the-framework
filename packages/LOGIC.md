The deliverables The Framework ships, one directory each. The product is the `framework` package; every other package is either a library the product is built from — the driver [2] seam, a branch used as a file store, and the four skills [3] — or a skill the product does not depend on (the browser, Discord), a command skill, the runner, the scheduler, or a companion: the Chrome extension of the Claude web bridge, and the marketing website.

## Glossary

[1] agent: the unit of work: one task worked by a coding agent in its own checkout, on its own branch, started through the project's start hook and shown in the dashboard from the files its tool keeps.
[2] driver: a coding agent wrapped as a black box: start it in a directory, prompt it for one turn, stream what it does, resume it later.
[3] skill: one of the four capabilities an agent is taught — `branches`, `tickets`, `queue`, `logs` — each a package with the instructions the agent reads (its `SKILL.md`), a command on the agent's PATH, and an API the product calls.
[4] the `agent-data` branch: the branch of a project's repository used as a file store for everything agents share: tickets, the agent queue, the runs.
[5] the Claude web bridge: the daemon's bridge endpoints plus the Chrome extension: carries the question a cloud session is parked on into the dashboard, and types the pick back into the session.

## Business logic — TL;DR

- **The product** (`framework/`) - the `framework` npm package: the `the-framework` CLI, the daemon, and the dashboard it serves. It runs no coding agent and names no tool: it starts an agent [1] through the project's own start hook and shows every agent by reading the files its tool keeps. It ships no prompt text. Depends on the driver and its Claude Code adapter, the branch store and the four skills below; not on the command skills, not on the runner or the scheduler.
- **The driver seam** (`agent-driver/`) - the `agent-driver` npm package: one contract for driving a coding agent as a black box, with a fake driver [2] implementation and the pieces every adapter shares. It keeps an agent's card and diary, reads the agent's inbox when a turn ends, and reports the question a turn ended on. Depends on nothing else here.
- **The Claude Code adapter** (`agent-driver-claude/`) - the `@agent-driver/claude` npm package: Claude Code as a driver on this machine and on a GitHub Actions runner, the reader of the account's quota, Claude Code's switches for the person's own setup, and whether `claude` can start. Depends on `agent-driver`.
- **The Codex adapter** (`agent-driver-codex/`) - the `@agent-driver/codex` npm package: Codex as a driver on this machine, Codex's switches for the person's own setup, and whether `codex` can start. Depends on `agent-driver`.
- **A branch used as a file store** (`agent-data/`) - the `@gemstack/agent-data` npm package: the `agent-data` branch [4] every skill keeps its files on, checked out under `.branches/`, written through one sync → commit → push cycle, plus the git runner and the git-exclude rule that machinery is built on. A library, not a skill: read by code, never by an agent. Every skill depends on it; it depends on nothing.
- **The `branches` skill** (`skill-branches/`) - the `@gemstack/skill-branches` npm package: one checkout per agent under `.branches/`, named as its branch, reclaimed once its work is on the remote; the `branches` command and the skill [3] every agent reads. Depends on `agent-data`.
- **The `tickets` skill** (`skill-tickets/`) - the `@gemstack/skill-tickets` npm package: the project's tickets with their plans and claims on the `agent-data` branch, the `tickets` command that reads, writes, claims and closes them, and the skill text. Depends on `agent-data`.
- **The `queue` skill** (`skill-queue/`) - the `@gemstack/skill-queue` npm package: the agent queue on the `agent-data` branch, the `queue` command that reads it, adds an entry at a priority and takes one off, and the skill text. Depends on `agent-data`.
- **The `logs` skill** (`skill-logs/`) - the `@gemstack/skill-logs` npm package: the record of every run agents made on a project, on the `agent-data` branch, and the read-only `logs` command; the tool that runs an agent writes it through this package, and the product reads it. Depends on `agent-data`.
- **The `browser` skill** (`skill-browser/`) - the `@gemstack/skill-browser` npm package: a headless Chrome the agent [1] drives from the shell with the `browser` command (open, read, click, type, press, screenshot, eval, close), kept by one background process per project, and the skill text. When the agent's environment names its diary, opening a page appends a `screen` line there, so the dashboard shows the browser live in the agent's transcript, where the agent used it, for the person watching to use too. Keeps nothing on the `agent-data` branch; depends on nothing here, and nothing depends on it.
- **The `discord` skill** (`skill-discord/`) - the `@gemstack/skill-discord` npm package: the `discord` command (send, setup, status) that posts one message to a Discord channel through its webhook, set once per machine and user outside every project (`DISCORD_WEBHOOK` in the environment winning over it), as a message of at most 2,000 characters, formatted by Discord's markdown, that pings nobody, and the skill text. A person's `ended:` line for the runner names it, so a run that needs them posts to the channel. Keeps nothing on the `agent-data` branch; depends on nothing here, and nothing depends on it.
- **The `question` skill** (`skill-question/`) - the `@gemstack/skill-question` npm package: one `SKILL.md` and no code teaching an agent [1] to ask the person to decide by ending its reply with one `await-choices` block, the question with its options, and stopping, unless it has a tool of its own for asking. The agent picks it by itself, the launcher does not list it, and nothing depends on it.
- **The `work-queue` command** (`skill-work-queue/`) - the `@gemstack/skill-work-queue` npm package: a command skill, one `SKILL.md` and no code, the job of working one queued task off the agent queue; it composes the capability skills of a project without naming one. One package per command; a project tracks its skill file under `.claude/skills/<command>`, and the scheduler fires it by its slash command.
- **The routine commands** (`skill-update-tickets/`, `skill-plan-tickets/`, `skill-triage/`) - three more command skills of the same shape, one package each: bring the tickets up to date with the issue tracker and close the tickets of merged pull requests; queue a plan for the tickets that have none or an outdated one, ten a run at most; put the tickets whose plan says they are ready on the agent queue, the quick wins (`/triage quick`) and the consensual work (`/triage consensual`), two modes of one command that the schedule paces on two lines. Each is fired by the scheduler on the interval and the check the project's schedule gives it.
- **The launcher's commands** (`skill-plan/`, `skill-research/`, `skill-maintainability/`, `skill-readability/`, `skill-security-audit/`, `skill-ux/`, `skill-maintenance/`, `skill-market-research/`, `skill-suggest-new-tickets/`, `skill-suggest-new-features/`, `skill-suggest-tickets-to-work-on/`, `skill-post-merge-cleanup/`) - twelve more command skills of the same shape, one package each, fired by a person: write a ticket for the task typed after the slash command and, under it, a plan naming the ways to do the work and the one to take, then stop, so a person queues the ticket. Refactor a part of the code for maintainability, or for readability; audit a part for security; review a part's UI flows; each of these four opens a pull request a person merges. Queue a maintainability refactor and a security audit for each part that needs one. Write tickets from a market research, new tickets, or new features. Rate how obviously well a part solves each problem it solves, or rank the tickets to work on next: these two change nothing and end on a written result, the agent's last message. Write up merged pull requests: open a pull request bringing the knowledge files up to date with what they decided and taught; a schedule can fire it, hourly say.
- **The runner** (`agent-runner/`) - the `agent-runner` npm package: a tool, not a skill, with one command line (`run`, `check`, `init`): it runs one agent [1] from start to end in its own checkout through the branches package and agent-driver [2], the run recorded on the `agent-data` branch [4] through the logs package, continues a run that ended on a question, sweeps up the runs of this machine whose process died, and runs the person's `ended:` line from `.agent-runner/config.yml` when a run ends waiting or ends done with a new pull request. Its `run --detach` is what a project's start hook names in this monorepo, `run --detach --resume` what its resume hook names, and `check` what its check line names. Reads no schedule and keeps no state. Names no skill. Depends on `agent-driver`, both adapters, `agent-data`, `skill-branches` and `skill-logs`; the scheduler depends on it.
- **The scheduler** (`agent-scheduler/`) - the `agent-scheduler` npm package: a tool, not a skill, with one command line (`tick`, `init`, `start`, `stop`, `status`, `model`, `offset`, `switch`) and one small process per project; it reads the project's tracked `agent-schedule.md`, pulls the `agent-data` branch [4], counts the runs in flight there, and has the runner start one agent [1] per due command. Names no skill. Depends on `agent-runner`, `agent-driver`, `@agent-driver/claude`, `agent-data`, `skill-branches` and `skill-logs`; nothing depends on it.
- **The Claude web bridge's extension** (`chrome-extension/`) - a Chrome extension, not an npm package: the far end of the Claude web bridge [5], reading claude.ai in a signed-in browser. Talks to the product over HTTP only.
- **The website** (`the-framework.ai/`) - the marketing site at https://the-framework.ai. Presents the product; shares no code with it.

No skill depends on another skill; the product, the runner and the scheduler are the only things that depend on a skill.
