What the tests cover, against real git repositories with a bare `origin` and a second clone standing in for another machine, both with sharing turned on unless said otherwise:

- **Birth and checkout** - making the branch exist births it parentless (it shares no commit with `main`), checks it out at `.branches/<branch>`, hides the checkout from the project's own git status, and doing it again changes nothing and still reports success.
- **A second worktree** - a write from a second worktree of the clone goes through the clone's one checkout: it lands and is pushed, the checkout's path from that worktree is the clone's, and a read from that worktree sees the file.
- **Adoption** - a branch origin already has is adopted with its files, instead of a second history being born.
- **A write** - commits on the branch under the caller's message, pushes it to origin, and leaves `main` untouched; a change that writes nothing commits nothing and reports no change; in a repository with no remote the write lands locally and reports that nothing was pushed.
- **Stranded commits and conflicts** - a write syncs in what another machine pushed and carries out an earlier local-only commit together with its own; a stranded commit that conflicts with origin's version resolves toward origin, and the change is re-applied on top of origin's version.
- **A lost race** - a push rejected because another writer landed in between re-runs the change once against the fresher files: the change is on the branch exactly once, next to the other writer's file.
- **A lost race under another process's lock** - when the re-sync's rebase and its abort both meet the branch's ref lock held by another process, the change still lands on origin exactly once next to the other writer's file, the checkout ends on the branch at origin's tip, and the next write lands too.
- **A checkout found off its branch** - a checkout left detached with a commit made on it is put back on the branch by the next write, and that commit and the write both reach origin; a checkout switched to another branch by hand is checked out on the branch again by the setup, the other branch keeps its tip, and the branch does not take the other's file.
- **A lock held by another process** - git's index-lock refusal and its ref-lock refusal are recognized and a plain push failure is not; a change refused twice runs a third time and lands on origin exactly once, as one commit; a lock that never lifts is reported with git's reason and leaves the checkout at its last commit.
- **The pull** - converges the checkout on what another machine pushed and answers that the branch reaches origin; in a repository with no remote it succeeds and answers `no-remote`.
- **One write at a time** - three concurrent writes run one after another, never interleaving, and all three land in order.
- **Two processes take turns** - two separate processes on one clone write six files each through the same checkout at once; no write fails and all twelve files land on origin (with the lock turned off, a write fails with git's bare "Command failed: git commit").
- **The checkout's lock** - a lock held by a live process is waited for; one held by a process that is gone is taken over at once; one held past the wait fails the write, leaves the checkout as it was, and is never removed by the waiter.
- **Reads** - a file reads off the checkout, from an agent's own checkout of the same repository too, which resolves to the project as its repository; a missing file reads as absent; after another machine moved origin on, a plain read still shows the checkout while a fresh read shows origin; a clone that holds no local branch reads origin's copy and lists a directory off it, and a missing directory lists as empty.
- **The one-shot write** - from a clone, lands on origin under the caller's message and births the branch when origin has none; the clone holds no local branch afterwards; another machine's persistent checkout is left where it was until its own pull; a lost race re-runs the change once and both writers' files land; no throwaway worktree stays registered; a change that writes nothing makes no commit; in a repository without `origin` the write lands as a local commit that a one-shot reader then finds, and a remote by another name, even with sharing turned on, still reads as `no-remote`.
- **Sharing off** - a repository with an origin whose sharing was never turned on reads as off and as `kept`: a write through the checkout is a local commit reported as not pushed, the pull succeeds answering `kept`, a one-shot write from a second worktree of the clone lands locally and both kinds of read see it, and origin holds nothing of the branch; what another machine shared is not fetched; once sharing is turned on, the next pull answers `origin` and origin holds everything kept here beside what the other machine pushed; turned off again, a later write leaves origin's tip where it was.
- **A fresh clone that keeps its records** - a clone with sharing off and no local branch opens a one-shot reader on the copy of origin's it was cloned with and reads a file another machine had shared; what that machine pushes after the clone is not seen, since nothing is fetched.
- **The config untouched** - adopting origin's branch and resolving a conflict toward origin's copy leave the repository's config byte for byte as it was.
- **The branch taken off this machine** - after one shared write and one write made with sharing turned off, taking the branch off answers `.branches/<branch>`, `branch <branch>` and `.branches` as removed and nothing kept: the checkouts directory is gone, lock file included, the rule `/.branches` is out of the exclude file, only `main` is left of the local branches, origin's refs are as they were, and the project's git status is clean; forgetting the sharing answer says there was one, a second time says there was none, and sharing reads as off.
- **Nothing to take off** - in a repository with neither the checkout nor the branch, both lists are empty and not even `.branches/` is made; a plain folder with a file at `.branches/<branch>` is kept with the reason `not a checkout git knows`, its file untouched.
- **From a second worktree** - asked from a second worktree of the clone, nothing is removed: `branch <branch>` is kept with the reason `it belongs to the repository at <the clone's directory>`, and the clone still has the checkout's file and the branch.
- **The checkouts directory shared with an agent** - with an agent's checkout beside the branch's in `.branches/`, taking the branch off answers `.branches/<branch>` and `branch <branch>` only: the agent's checkout is still there, the rule `/.branches` is still in the exclude file, and the project's git status is clean.
