Hides a path from git without touching any tracked file: one ignore rule is appended to `info/exclude` in the repository's common git directory, the ignore file that is git's own rather than the project's, so no `.gitignore` changes and the user never sees a diff. The rule goes in the common git directory rather than in a worktree's own because git reads excludes only from there; one line, written once, covers every worktree of the repository, an agent's checkouts included. The same rule can be taken back out, for a tool that removes what the rule hid; since every checkout of the repository reads the one file, the checkouts of the repository can be listed too, so a tool can see that none still holds what the rule hides before it takes the rule out.

## Business logic — TL;DR

- **Written once** - a rule already present as a line of the file, ignoring surrounding whitespace, is left alone; otherwise it is appended on a line of its own (after a newline when the file does not end with one), and the `info` directory is created when it is missing.
- **Taken back out** - every line that is exactly the rule, ignoring surrounding whitespace, is removed, and every other line stays as it was, a person's own included; a line that only contains the rule is not the rule. A rule that is not there, and a repository with no exclude file, change nothing and create no file. The answer says whether a line went. The file is replaced in one step, written beside itself and then renamed, so a reader sees the old contents or the new, never half.
- **Every checkout of the repository** - the root of the main checkout and of each linked worktree, an agent's included, as git lists them.
- **Where the file is** - the common git directory is asked from git and resolved against the repository when git answers with a relative path; an empty answer means nothing is written, and nothing is taken out.
- **Failure is the caller's call** - outside a repository, or with a git directory that cannot be written, the write, the take-back and the listing of the checkouts each fail with git's or the file system's error and the caller decides whether that matters; the checkout code in `file-branch.ts` treats the write as best effort and keeps the checkout, and the tools' clean-ups (`agent-runner cleanup`, `branches cleanup`, and `own-directory.ts` for `agent-scheduler cleanup` and `orchestration cleanup`) treat the take-back and the listing as best effort and leave the rule.
