What the tests cover:

- **Reading the streamed output** - the session id is announced on the first line that carries it and again only when it changes; the model is announced off the `init` line only; assistant text and tool names surface as they stream; the result line's text is the turn's answer; a non-JSON line and a JSON `null` are ignored; without a result line the accumulated assistant text stands in.
- **The message being written** - each text piece yields the whole text so far; a new text block starts from empty; thinking and tool-argument pieces yield nothing.
- **Usage** - the price and the four token counts are read off the result line; a result line without usage yields none; tokens without a price yield usage with the price absent, never zero.
- **Rate limit telemetry** - a rate-limit line becomes a reading with its status and window verbatim and its reset time converted from seconds to milliseconds, without disturbing the turn; statuses and windows never seen before pass through; a line missing the status, the window or a numeric reset time yields nothing.
- **Running a process** - a process that streams a session id, a tool use and a result resolves the turn with the result's text and session id, reporting `start` first, the tool as an action and `result` last; a non-zero exit with no text fails the turn with the process's standard error output; a non-zero exit after streamed text fails the turn with that text, reports an `error` and no `result`.
- **The command line** - print mode with streamed, verbose JSON output and the pieces of each message; the `acceptEdits` permission mode by default; the framing appended as the system prompt; the model passed through.
- **The diary in the environment** - a driver session that keeps a log spawns the coding agent with the configured environment plus `AGENT_DIARY` naming `<id>.jsonl` in the log's directory; one without a log gets the configured environment unchanged.
- **MCP servers** - no configuration flag without servers; with servers, a configuration file holding exactly them, the same file across the driver session's turns, removed when the driver session ends.
- **Continuing the driver session** - a fresh turn appends the framing and does not resume; a turn asked to continue resumes the session id of the last turn and skips the framing; a driver session seeded with a session id resumes it on its first such turn; a turn asked to continue with no known session id runs fresh with the framing.
- **A conversation that is gone** - a refused resume is retried once as a fresh turn with the framing, the user is told through a notice, the dead session id is dropped and later turns chain off the new one; a resume that fails for any other reason is not retried.
- **The person's own setup** - given none, no switch; with every part off, `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` and `ENABLE_CLAUDEAI_MCP_SERVERS=false` in the spawned environment and `--setting-sources project,local` ahead of the configured extra arguments; each part turned on alone drops only its own switch; the caller's other environment entries are kept; the quota read gets the same environment switches.
- **Listing the models** - the listing starts Claude Code with `--setting-sources project,local` when `skills` is off (covered in `claude-code-models.test.ts`).
- **Can a session start here** - a logged-in `claude` is ready; `"loggedIn": false` is a problem naming `claude auth login`; a missing CLI names the Claude Code install page.
- **The model on a logged session's card** - a driver session started on `opus` with a log ends with `claude-opus-5-5`, the model Claude Code named, on its card, and no diary line for it.
- **What a tool call gave back** - a tool use carries its id, and a command of several lines or a long one also carries the command whole; a tool result yields an `output` for that id with its text, whether the text is given plain or as text blocks; a result marked as an error says the call failed, even with no text; a result with no text, one naming no call, and a user line that is no result yield nothing; a long output keeps its start and its end and says how much was cut.
- **What an edit or a write did to its file** - a write that created a file says its path, every line of its content as added, and that it was created; an edit says the lines its patch added and removed, over all its hunks; a write over a file that was already there is a change, not a created file; an edit that printed nothing still yields its `output`, for the file it changed; a call that failed says no file; an account that names no file at its top (a read's, a command's), one that holds no patch, and one that is plain words say no file; one account on a line of two results is given to neither.
