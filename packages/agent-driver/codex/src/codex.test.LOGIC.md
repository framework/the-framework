What the tests cover, against a fake Codex app server that answers the driver's requests with the messages of a real Codex turn:

- **Reading the app server's messages** - the thread id is announced first as a `session` progress event, then the model; each message streams as `partial` progress events carrying the message so far, a new message starting from nothing, then as whole text; the last message Codex sends is the turn's answer, not the first; each started work item is a tool use named by its kind with what it did (the command without its shell wrapper, the paths of a file change); a reasoning summary is a thought; the prompt echoed back is no tool use; banner lines, an empty line, a JSON `null`, a number and a notice the driver does not read are ignored.
- **Usage** - the turn's token readings are summed and the price is absent, never zero; a resumed conversation's repeat of its previous turn's reading is not counted; the cached tokens are split out of Codex's inclusive input total; reasoning tokens are not added to the output count a second time; a missing or malformed reading yields no usage; absent counts read as zero; a cached count above the input count cannot push the uncached input negative.
- **The exchange** - the command line is `codex app-server` alone; the driver initializes, starts a conversation in the driver session's directory under the `workspace-write` sandbox with the approval policy `never`, and starts the turn with the prompt as its one text input.
- **A writable git directory** - in a freshly initialized git repository, the repository's absolute `.git` path is passed to Codex as a writable path under `workspace-write`, and none under `read-only`, whose sandbox the conversation asks for.
- **Framing as developer instructions** - the driver session's framing, then the turn's extra framing, blank-line separated, are the conversation's developer instructions, and the prompt goes alone.
- **Continuing the conversation** - a turn asked to continue with no turn before it starts fresh, with the model and the framing; the next one resumes the thread id the first reported, with the model and no framing; a turn not asked to continue starts fresh again; a driver session started with an earlier session id resumes that one, under the sandbox the driver was configured with.
- **No quota reading** - the driver offers no quota reading rather than a made-up number.
- **A request of the app server's own** - an approval request is answered with a refusal, and the turn goes on to its answer.
- **A failed turn** - a turn Codex says failed fails, though the app server exits cleanly, with the sentence inside the API's refusal as the reason, reported as the last `error` progress event, as "codex failed: <reason>", and "codex failed" and the reason apart; a plain message is the reason as it is; an interrupted turn fails saying so; a resume Codex refuses fails with its message; an app server that exits before its turn ends fails the turn, with what it wrote on standard error for a crash, and "the turn did not finish" for a clean exit; a turn whose process fails before its end still leaves the thread id and the model on the log's card, for a later resume.
- **The person's own setup** - given none, no feature switch and the person's own Codex home; `memory` off and `connectors` off each give only their own feature switches; with `skills` off Codex is spawned with `CODEX_HOME` naming the driver's home, which then holds a link to the person's `auth.json`; a link pointing elsewhere is put back and what Codex saved in that home stays; a newer login file in the link's place is copied onto the person's file first, an older one is not; two sessions starting at once both start, with no link yet, with a link pointing elsewhere, and over a saved login, which reaches the person's file whole; a home that is the person's own is left alone; the default home is under the state directory, or under `HOME` from the given environment.
- **Can a session start here** - only `codex` is asked; an empty `~/.agents/skills` gives no warning, one holding a skill gives one naming the folder while `skills` is off, and none with `skills` on or no setup given; `memory` on with `skills` off is a warning, and not with `skills` on; "Not logged in" is read as no, also off standard error, and names `codex login`; a missing CLI names the Codex install page.
- **Listing the models** - of a catalog with a hidden model and three listed ones out of order, the three listed ones are kept in Codex's priority order with their display names; output that is not JSON is an error; the listing runs `codex debug models`, and a non-zero exit fails it naming the command and the exit code.
