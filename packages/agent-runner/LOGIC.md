The `agent-runner` package: a standalone tool, like `agent-driver`, that runs one coding agent [1] from start to end for one project: its own checkout [2], one prompt, the agent's own loop to the end, and a run record [3] on the project's `agent-data` branch [4], where every machine and the dashboard read it. It also continues a run that ended on a question, runs the follow-up [5] a run names once it ends done with a pull request, and holds the sweep [6] a scheduler runs on its tick to record the runs of this machine whose process died (the tool has no command of its own for it). A person runs it from a shell, a dashboard runs it through the project's start, resume and check hooks that its `init` writes, and the scheduler (`agent-scheduler`) spawns it for every command that is due. It reads no schedule and keeps no state file: the prompt it is given is all it runs, and what it knows of a run is on the branch, in the run's checkout and in the run's lock [7]. When a run ends waiting on a question, or ends done with a pull request it did not have, it runs the person's `ended:` line [11], if there is one: the tool names no service to tell, and a person reaches Discord, say, with `ended: npx discord send "$MESSAGE"`. `package.json` and the `tsconfig*.json` files configure the build and the test runner and carry no business logic; `dist/` and `dist-test/` are build output.

## Context

**User story**: the user presses Start in the dashboard with a prompt; the project's start hook runs `agent-runner run --detach "$PROMPT"`, the dashboard gets the run's id back at once and shows the agent working in its own checkout; the agent commits its work to its branch, which stays on this machine: it pushes the branch and opens a pull request itself only when the run was given a publish level [12], or when the prompt or the user asks, and otherwise the user publishes it from the run's page; the run's record says how it went, which branch holds the work, its pull request when it has one, and what it cost. When the agent stops to ask, the run reads `waiting`, and the user's answer continues the same run through the resume hook; Stop ends it. From a shell, `agent-runner run "/work-queue"` does the same in the foreground and answers when the agent has ended.

**Business logic story**: the scheduler decides when a command runs; this tool decides nothing about when, and runs what it is given. A run in flight is a run record on the `agent-data` branch with `status: running` and the tool's mark [8], so every machine that shares the repository sees it, and a scheduler counts it against a command's cap. A run is one process of the tool's own, `agent-runner run`, that makes a checkout through the `branches` package, prompts the coding agent once through its driver (`@agent-driver/claude` or `@agent-driver/codex`, on the `agent-driver` contract) with no system prompt (a command's skill file is the whole instruction, and the agent publishes its own work, when asked to, with the skills in its checkout, as far as the run's publish level [12] says, told in one sentence after the prompt; the tool publishes nothing), then writes the run record and reclaims [9] the checkout. The sweep is what whoever runs this tool on a clock calls, the scheduler's tick on every minute; this tool runs no clock of its own.

## Glossary

[1] coding agent: the CLI doing the actual work: Claude Code or Codex. A run is on Claude Code unless `run --driver codex` says Codex.
[2] checkout: an agent's own working copy of the project: a git worktree under the project's `.branches/` directory, named as its branch.
[3] run record: the `logs` skill's record of a run on the `agent-data` branch: a card (`<id>.json`: what was asked, the branch, the pull request, how it ended, what it cost) and a diary (`<id>.jsonl`: what the agent said). Written twice, over the same file: as a marker before the agent exists, and with how it went when the run ends.
[4] the `agent-data` branch: the branch of a project's repository used as a file store for everything agents share: tickets, the agent queue, the runs.
[5] follow-up: the prompt a run names with `run --then`: once the run ends done with a pull request, a fresh run on the same branch is given that prompt followed by a space and the first run's id; the launcher's "Post-merge cleanup" box names `/post-merge-cleanup`.
[6] sweep: the pass that records and reclaims the runs of this machine whose process died, and only this machine's; the scheduler runs it on every tick.
[7] the run's lock: `.agent-runner/runs/<id>.lock` at the repository root, holding the pid of the one process of the run at work on it; a pid that is not a live process holds nothing.
[8] the tool's mark: `caller.runner` on a card: the machine that started the run, the run's process on that machine while it runs, and, each when the run has one, the follow-up's prompt and the publish level [12]. A run's card carries no command: what the run was asked is its prompt, the card's intent.
[9] reclaim: removing a finished agent's checkout once its branch holds everything in it.
[10] run: one agent this tool starts: a process of the tool's own (`agent-runner run`), a checkout, one prompt to the coding agent, and a run record when it ends. Its id is its start time, `2026-09-16T14-01-00-000Z`.
[11] the `ended:` line: the value of the `ended` key in the project's `.agent-runner/config.yml`, a shell command of the person's, on this machine only (the tool hides its directory from git).
[12] publish level: how far a run's agent publishes its work when it finishes, given with `run --publish`: `branch` (push the branch and open no pull request), `pr` (push the branch and open its pull request) or `merge` (push the branch and open its pull request, set to merge on its own once its checks pass). A run given none publishes only what its prompt asks.

## Business logic — TL;DR

- **The executable** (`bin/`) - `agent-runner`, the one command line: `run` (also `--detach`, `--resume`, `--then`, `--publish`, `--parent`, `--base`, `--model`, `--driver`, and `--id` for a run spawned with its id, with `--mark` when it is to write its marker itself), `check`, `init`; JSON on stdout, one line for a person on stderr, exit 0, 1 or 2.
- **The rules and the processes** (`src/`) - run records as markers, the live record the dashboard reads, the run's lock, one run's [10] life and its resume, the person's `ended:` line [11], the telling of a run's parent, the sweep, the detached run and whether a run can start here, the dashboard's hooks written by `init`, and the command line; told in `src/LOGIC.md`.

## Business logic

### A run's life

#### Context

**User story**: see `## Context`.

#### Business logic

- A run starts one of three ways: `run <prompt>` in this process, which mints its id and writes its own marker; `run --detach <prompt>`, which mints the id and spawns the run's process to write its own marker, answering the id at once, before any git work (the dashboard's start hook: pushing the marker takes seconds, and the page waits on the id); or `run <prompt> --id <id>`, the run's process spawned by someone who wrote its marker already (a scheduler's tick), or, with `--mark`, by a detached start. The marker carries the tool's mark [8] with this machine and, when the run's process is the one writing it, its pid; a scheduler's marker has no pid, and the lock, handed to the run's process once it exists, is what says the run lives. The model is the one given with `--model`; none given, the coding agent [1] starts on its own default (a scheduler passes its own model).
- The run makes a checkout [2] through the `branches` package, starts a driver session that keeps the run's card and diary in the checkout as it works, the same two files as the record, prompts the coding agent once with the prompt and lets the agent's own loop run to the end; a line written to the session's inbox meanwhile becomes the agent's next turn, and a line that reached it as the run was ending is still sent by the same process, in the same session, before the run ends; the agent commits and names its branch itself, and pushes it and opens a pull request only when asked to. A run may be given a publish level [12] (`run --publish <branch|pr|merge>`): its agent is then told, in one sentence after its prompt, how far to publish when it finishes; with no level the prompt goes as written, and the agent publishes only what the prompt itself asks. The level is kept in the tool's mark [8], so a resumed run is told the sentence again. The run then reads the pull request back off the branch through the command the project's git host package declares (none when the project has none, or when the branch has no pull request), copies the card and the diary onto the branch over the marker, and reclaims [9] the checkout under the `branches` rule: a dirty tree keeps it; a clean one goes, its branch stays on this machine, and nothing is pushed. One run is stopped by a signal to its own process, SIGINT or SIGTERM, which is what a dashboard's Stop sends, the pid being on the run's live card: the agent's processes end, the run is recorded `stopped`, its checkout reclaimed.
- A run whose last turn asked a question ends `waiting` and keeps its checkout; `run --resume <id>` with the answer, or a text, continues the same run and record, after waiting for the run's lock, so a resume never works the run while another process of it still does; `run --detach --resume <id>` does it in its own process, answered at once (the dashboard's resume hook). A run may name a follow-up [5] (`run --then <prompt>`, what a dashboard's "Post-merge cleanup" box asks for): its agent is told to publish its work, pushing its branch and opening its pull request, without arming the merge, whatever its publish level [12]; once the run ends done with a pull request, a fresh run of its own, given no publish level, works the same branch with that prompt and the first run's id, and when it ends done this process merges the first run's pull request through the git host; otherwise the request stays open for a person.
- Once a run's record is written, before its checkout is reclaimed, the run's process runs the person's `ended:` line [11] from `.agent-runner/config.yml`, in the project's root, when the run ended `waiting`, or ended `done` with a pull request other than the one its branch already had when the process took it up (none for a fresh run, the first run's for a follow-up's run, the record's for a resume): with `MESSAGE` (one line for a person naming the project, the prompt, and the question or the pull request), `RUN_ID`, `STATUS`, `QUESTION` and `PR_URL` in its environment, waited for, and killed with everything it started when still running at 60 seconds; the run's lock is held meanwhile, so a resume of the same run waits for it. What the line does never changes the run; a failed or stopped end runs nothing, and neither does the sweep.
- A run's coding agent, Claude Code or Codex, starts with the person's own setup, as when started by hand: its memory (`memory`), the connectors, apps and plugins of the person's account (`connectors`), and the person's own instructions, skills and settings files (`skills`). Each of the three parts is left out on this machine with its own line under `personal:` in `.agent-runner/config.yml` (`memory: off`), so a run does the same job on every machine. Each coding agent's driver turns the parts off with its own switches; Codex has none for skills in `~/.agents/skills`, and the readiness check says so. The project's own instructions and skills load either way.
- A run can be started for another run, its parent (`run --parent <id>`, run by the parent's own agent: this tool starts nothing on its own), and from a branch other than origin's default (`run --base <ref>`), so it has what its parent has built so far; both are on its record. Every run that makes its own branch also writes on its record the commit that branch was made at: the run's own work is what came after that commit, which is how a reader still tells it apart once it is merged, or when the run started from another run's branch. When it ends, however it ends, its parent gets one line, which run, how it ended, where its work is and its last words, the way a person's message reaches a run: into the parent's inbox while it works, as a resume in a process of its own once it has ended. Nothing waits for a child.
- The sweep [6] records and reclaims what a run of this machine could not: a run whose lock a live process holds is left alone; otherwise a live card still `running` is recorded `failed`; one that ended but was never recorded is recorded as it ended, and kept when it is `waiting`; a marker of this machine with no checkout behind it is recorded `failed` with the spawn's stderr, else `stopped`; a run the sweep ended tells its parent. A running record from another machine is never touched: only that machine's sweep, or a person, changes it.
- `check` answers whether a run on a coding agent can start on this machine (its CLI installed and logged in; warnings for running as root and, on Codex only, for skills in `~/.agents/skills` while this machine leaves `skills` out, which Codex cannot keep out, and for `memory` on while `skills` is off, which brings nothing back), and `init` writes the tool's `start`, `resume` and `check` lines into the dashboard's `.the-framework/hooks.yml`, keeping a person's lines; the writer takes any tool's lines, and the scheduler's `init` writes its own through it.
