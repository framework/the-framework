The rules and the processes of `agent-runner`: run records [1] as markers, the live record [2] a run's session keeps for the dashboard, the run's lock [3] that keeps one process per run, one run's [4] life from checkout [5] to record and its resume, the person's `ended:` line [10] run when a run's end needs them, the follow-up [6], the sweep [7], the detached run, whether a run can start here, the person's own setup left out of a run's coding agent except the parts this machine turns on under `personal:`, the dashboard's hooks, and the command line. Every file here has a `LOGIC.md` of its own.

## Context

**User story**: the user presses Start in the dashboard, or types `agent-runner run "/work-queue"`, and one agent works the prompt in its own checkout [5], opens its pull request, and leaves a run record saying how it went; the user answers a run that asked, stops one that should not go on, and a scheduler starts the same runs on its own clock.

**Business logic story**: two processes meet these files. The run's process (`run.ts`, started as `agent-runner run` in the foreground, or spawned detached by `runner.ts`) takes the run's lock (`run-lock.ts`), which the spawning process took first and handed over, writes its marker (`records.ts`) unless it was written for it, makes the checkout, hands the session the live record's place (`live-card.ts`), prompts the coding agent once, reads the pull request back through the project's git host (`git-host.ts`), records the run over its marker, runs the person's `ended:` line [10] (`ended.ts`) when the run ended waiting or with a new pull request, and reclaims [8] the checkout, or keeps it when the agent asked, and only then lets the lock go; `run --resume` continues such a run once the lock is free. The process that spawns a detached run (`runner.ts`: `run --detach`, or a scheduler's tick through `spawnRun`) takes the lock before the run's process exists and hands it over once it does. The sweep (`sweep.ts`) is called from outside, by a scheduler's tick, leaves alone every run whose lock a live process holds, and finishes what a run's process could not. A person's shell and a dashboard's hooks reach all of it through the command line (`cli.ts`). The checkout and the record are the `branches` and `logs` packages' rules; the coding agent is its driver's, from `@agent-driver/claude` or `@agent-driver/codex` on the `agent-driver` contract.

## Glossary

[1] run record: the `logs` skill's record of a run on the `agent-data` branch: a card (`<id>.json`) and a diary (`<id>.jsonl`). Written twice, over the same file: as a marker before the agent exists, and with how it went when the run ends.
[2] live record: the card `<id>.json` and the diary `<id>.jsonl` under `.the-framework/` in a run's checkout, the same two files as the run record, written by `agent-driver`'s session as the agent works; the inbox `inbox.jsonl` beside them carries what reaches the agent from outside.
[3] the run's lock: `.agent-runner/runs/<id>.lock` at the repository root, holding the pid of the one process of the run at work on it; a pid that is not a live process holds nothing.
[4] run: one agent this tool starts: a process of the tool's own (`agent-runner run`), a checkout, one prompt to the coding agent, and a run record when it ends. Its id is its start time, `2026-09-16T14-01-00-000Z`.
[5] checkout: an agent's own working copy of the project: a git worktree under the project's `.branches/` directory, named as its branch.
[6] follow-up: the prompt a run names with `run --then`: once the run ends done with a pull request, a fresh run on the same branch is given that prompt followed by a space and the first run's id.
[7] sweep: the pass that records and reclaims the runs of this machine whose process died, and only this machine's; the scheduler runs it on every tick.
[8] reclaim: removing a finished agent's checkout once its work is on the remote.
[9] the tool's mark: `caller.runner` on a card: the machine that started the run, the run's process on that machine while it runs, and the follow-up's prompt when the run names one.
[10] the `ended:` line: the value of the `ended` key in the project's `.agent-runner/config.yml`, on this machine only, a shell command of the person's that this tool runs when a run ends waiting, or ends done with a new pull request.

## Business logic — TL;DR

- **This machine's settings** (`config.ts`, `config.test.ts`) - `.agent-runner/config.yml` read as a YAML map, a broken file one line on the log and no settings; `personal:` a map with one line per part of the person's own setup (`memory`, `connectors`, `skills`), a part on only for `on` or YAML true, anything else in the map one line on the log.
- **The names** (`names.ts`) - the tool's directory `.agent-runner`, its `runs/` and its `config.yml`, the dashboard's directory and its hooks file.
- **Run records as markers** (`records.ts`, `records.test.ts`) - a marker is a running card with the tool's mark [9]; withdrawn when a scheduler lost the cap; overwritten by the record at the end.
- **The live record** (`live-card.ts`) - where the session's card, diary and inbox live in the checkout; a card read as this tool's only with the mark; closing a dead run's record from outside.
- **The run's lock** (`run-lock.ts`, `run-lock.test.ts`) - one process per run: taken before the record is touched, waited for while a live process holds it, a dead holder's taken over, handed from a detached run's parent to the run's process, let go only by its holder; the probe of a live pid; where a spawned run's stderr lands.
- **The git host** (`git-host.ts`) - the project's git host reached by declaration, the package the project says provides the `git-host` kind: a branch's pull request read back through its command, or none; a pull request merged through it.
- **One run** (`run.ts`, `run.test.ts`) - the run's lock, marker, checkout, the session with its live record and inbox, the prompt once, the pull request, the record over the marker, the checkout reclaimed; a run with no checkout is recorded `failed`; a signal to the run's process stops it, recorded `stopped`, and a later one changes nothing; lines that reached the inbox as the run ended are sent by the same process before it lets the run go; a run whose last turn asked ends `waiting` and keeps its checkout; once the record is written, the `ended:` line [10] runs when the run ended `waiting` or `done` with a pull request its branch did not have (a follow-up's run never announcing the first run's); a resume waits for the run's lock, then continues the same run with the answer or a text; a run that names a follow-up tells its agent not to arm the merge, and once it ends done with a pull request a fresh run on its branch gets the follow-up's prompt and its id, and the first run's pull request is merged through the git host when that one ends done.
- **The `ended:` line** (`ended.ts`, `ended.test.ts`) - a run's end that needs a person (ended `waiting`, or `done` with a pull request its branch did not have when this process took it up, so a follow-up's run does not announce the first run's again) runs the `ended:` line [10] in the project's root, with the message, the run's id, the status, the question and the pull request's URL in its environment, waited for, and killed with everything it started when still running at 60 seconds, while the run's lock is held, so a resume started meanwhile waits for it; a missing line runs nothing, a broken file or a failing line is one line on the log, never an error, and the run's end never changes.
- **The sweep** (`sweep.ts`, `sweep.test.ts`) - a run whose lock a live process holds left alone; dead runs of this machine recorded and reclaimed; markers with nothing behind them ended; another machine's runs never touched.
- **The processes** (`runner.ts`, `runner.test.ts`) - whether a run can start on this machine (the coding agent's CLI, nothing else probed), the detached run with the run's lock taken before its spawn and handed to it, the detached start on demand (its follow-up, when given, on the marker and passed to the run), the detached continuation, a run and a resume in this process, either coding agent unrestricted with the run's id in its environment, and the model: the one given, else the coding agent's own default.
- **The dashboard's hooks** (`init.ts`, `init.test.ts`) - this tool's lines written into the dashboard's `.the-framework/hooks.yml` so its check, its Start and its answers to a run run through this tool; a person's lines and comments kept, a list given only the line it lacks, nothing written without the dashboard's directory; the same writer for another tool's lines.
- **The command line** (`cli.ts`, `cli.test.ts`) - the three commands, a person's run refused before anything is written when its coding agent cannot start, JSON on stdout, a line on stderr, exit 0, 1 or 2, and the project found from inside a checkout.
- **The entry point** (`index.ts`) - re-exports everything a program imports, the scheduler among them.
- **A test helper** (`test-repo.ts`) - a throwaway project with an origin and an `agent-data` branch, for the tests.
