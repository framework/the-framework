The `@openagt/agent-scheduler` package: a standalone tool, like `@openagt/agent-driver`, that starts coding agents [1] on a schedule for one project. The project's skills bring the schedule [2]: a skill says, in the front matter of its `SKILL.md`, which commands [3] it schedules, each with when it is due and how many may run at once. Each person switches a scheduled command on for their own machine [14], may set their own pace for it there [20] and their own number of agents at once [21], and picks how far its runs publish there [17]. The tool ticks [4] every minute, pulls the project's `agent-data` branch [5], sweeps [6] what earlier runs [7] left, and for every command whose skill is on the start point [23] and that is switched on on this machine, due, under the cap [8] in force and within the account's quota [9], has `agent-runner` start one agent in its own checkout [10], which records the run [11] on the branch, where every machine and the dashboard read it. The tool names no command of its own: a skill's front matter is where a command is named, and the skill is what runs, the rest of the command's name being the word the skill gets. A person who wants a scheduled command that no skill of the project brings saves a prompt of their own as an automation [24], of one of two kinds. Shared with the project, the tool writes it into the project as a skill file, theirs to commit, and from then on it is a skill like any other. Kept on this machine, the tool writes the same file into its own folder, hidden from git: it is the one scheduled command that is no skill's, a run of it has the automation's name as its prompt and is handed its text with it, and nobody else gets its command, though its text is in the record of each of its runs. The tool shows an automation of either kind, saves it again under its name and removes it, as long as its file reads as the tool writes one: a skill somebody wrote, and an automation whose file was changed by hand into something the tool does not write, are edited and removed by hand. The package also brings its own part of a dashboard, its module [18]: the Automations page, where a person switches each scheduled command on or off, sets when it runs and how many agents work on it at once, picks how far its runs publish, saves an automation [24] from the "New automation" form, shared with the project or only on this machine, and, on the row of such an automation, opens it in the same form to save it again under its name ("Edit prompt") or removes it ("Remove"), the Scheduler section of the Settings page, the Scheduler card of the Overview and the stop line on the usage bar, each reading through `agent-scheduler status` and saving through `offset`, `switch`, `pace`, `agents` and `publish`, the form trying a check through `try` and saving through `add`, or through `edit` when it was opened from a row with what `show` printed, and a removal going through `remove`. `package.json` (which exports the module as `./dashboard`) and the `tsconfig*.json` files configure the build and the test runner and carry no business logic; `dist/` and `dist-test/` are build output.

## Context

**User story**: the project has a `work-queue` skill whose front matter says `schedule:` with `when: npx queue`, and a `triage` skill whose `schedule` holds `word: quick` and `every: 6h`. The user runs `agent-scheduler start`, switches both commands on for their own machine, and picks `pr` as the publish pick [17] of `work-queue`; from then on, whenever the project's agent queue holds an entry, one agent works it in its own checkout and opens a pull request, never two at once, and at most every six hours one agent triages the tickets, and never past the share of the week's quota that has elapsed; the user reads why nothing started (`not due`, `cap reached (…)`, `quota: …`) in the state file or on a dashboard, changes the model or the spend cushion for their own machine, turns a scheduled command on or off for their own machine with its schedule switch [14] (every scheduled command starts switched off, so a skill that arrives in the project starts no agent by itself), sets how often at most a scheduled command starts on their own machine with its pace pick [20] (`agent-scheduler pace "triage quick" 2d 10:00` for every second day from 10:00 on; until they pick, the command runs at its skill's pace [19]), sets how many agents may work on a scheduled command at once with its agents pick [21] (`agent-scheduler agents work-queue 3`; until they pick, the skill's number holds), changes how far a scheduled command's runs publish on their own machine with its publish pick [17] (until they pick, a run commits its work and pushes nothing), and runs `agent-scheduler stop` to turn it off while the agents in flight run to the end. A user who writes a new skill with a `schedule` in their own checkout sees its command listed at the next tick; switched on and due, it starts no agent and says `not on origin/main: a run's checkout starts from origin/main, and the command's skill is not there` until the skill is on origin's default branch, because an agent's checkout is made from there and would not hold the skill. A user who wants an agent to answer each new comment on the project's issues, which no skill of the project does, writes no skill file by hand: on the Automations page they press "New automation", type a name, what the agent is told, "every 15 minutes" and a shell line that lists the comments posted since `$LAST_RUN`, press "Try it" to read what the line prints today, and save (or run `agent-scheduler try` and `agent-scheduler add` in a shell). The project then has the file `.claude/skills/answer-comments/SKILL.md`, which they commit and bring to origin's default branch; `/answer-comments` is listed like any skill's command, switched off, and once they switch it on it starts as any other does. A user who wants such an automation for themselves alone picks "Only on this machine" in the form (or adds `--private` to `agent-scheduler add`): nothing is written into the project, the automation is kept as a file under `.agent-scheduler/automations/`, it is listed on their machine only, switched off, and it can start as soon as they switch it on. A user who later wants other words in an automation they saved presses "Edit prompt" on its row, changes the prompt or when it runs in the same form, and saves (or runs `agent-scheduler show` and then `agent-scheduler edit` with the parts to change): its file is written anew where it is, a change of theirs to commit when it is a shared one, and the command keeps its name, so its past runs, its switch and their picks for it stay. A user who no longer wants one presses "Remove" on its row and confirms (or runs `agent-scheduler remove`): its file is deleted, nothing is committed for them, and the command is gone from the page at once, with what their machine held for it.

**Business logic story**: the daemon of OpenAgent used to watch the branch and start agents on its own rules, in its own memory. This tool replaces that with files and small processes: the schedule is in the project's skill files, each skill bringing its own scheduled commands, and in the files of the automations kept on this machine [24], beside the state; the tool's state [12] is an untracked JSON file under `.agent-scheduler/`, per user; a run in flight is a run record [11] on the `agent-data` branch with `status: running`, so two machines sharing the repository count the same runs against a cap; a run is one detached process of `agent-runner`, `agent-runner run`, the same tool a dashboard's Start runs through, that makes a checkout through the `branches` package, from the start point [23] and never from the files in the person's own checkout, prompts the coding agent [1] once through `agent-driver` with no system prompt (the command's skill file is the whole instruction, or the text of an automation kept on this machine, handed with the prompt, and the agent publishes its own work, as far as the run's publish level [16] says, with the skills in its checkout), then writes the run record and reclaims [13] the checkout; and the scheduler's process [15] is a loop of ticks that holds nothing a restart would lose. This tool decides when; `agent-runner` runs. The spend-boundary rule is copied from OpenAgent rather than imported, because this tool depends on `@openagt/agent-driver-claude`, which reads the quota, and not on OpenAgent, which draws the panel.

## Glossary

[1] coding agent: the CLI doing the actual work: Claude Code or Codex. A scheduled run is on Claude Code.
[2] the schedule: all the scheduled commands of a project. A skill of the project brings its own with the `schedule` key in the front matter of its `SKILL.md`, called the skill's `schedule`. The tool reads the skills in the project's two skill folders, `.claude/skills` and then `.agents/skills`. A skill with no `schedule` key brings none. A command whose skill is only under `.agents/skills` is listed and never started: every scheduled run is on Claude Code, which reads a project's skills from `.claude/skills`. The skills are read as they are on disk in the person's own checkout: a command whose skill is not on the start point [23] is listed and not started until it is. An automation kept on this machine [24] is one more scheduled command, read from its own file under `.agent-scheduler/automations`, after the skills; being no skill, it is held to neither of those two rules.
[3] command: a scheduled command, one command a skill schedules, named as a person types the command without its slash: the skill's folder name, then at most one word the skill takes as its argument (`triage quick`); the coding agent's harness expands the slash command `/<name>`, and a run's whole prompt is that slash command. An automation kept on this machine [24] is a scheduled command too, named as its file, with no word after the name: no skill schedules it, and a run of it has that name as its prompt, with no slash, and is handed its text with it. Its runs are counted on this machine alone.
[4] tick: one pass of the scheduler: pull the `agent-data` branch, sweep, then one decision per scheduled command, each decision one line in the state.
[5] the `agent-data` branch: the branch of a project's repository used as a file store for everything agents share: tickets, the agent queue, the runs.
[6] sweep: `agent-runner`'s pass, run on every tick, that records and reclaims the runs of this machine whose process died, and only this machine's.
[7] run: one agent this tool starts: a detached process of `agent-runner` (`agent-runner run`), a checkout, one prompt to the coding agent, and a run record when it ends. Its id is the time it was minted, `2026-09-16T14-01-00-000Z`; the start on its record is the moment the tick turned to its command, before its check ran.
[8] cap: how many runs of one scheduled command a machine lets be in flight at once: the machine starts another run of the command only while fewer than its number are in flight on any machine that shares the repository. Its number is the agents pick [21] made on it, a person's own number for the command there, else the number the command's skill gives, 1 when the skill gives none.
[9] quota: the account's subscription allowance, as the coding agent reports it: a session window and a quota week, each with a percentage used.
[10] checkout: an agent's own working copy of the project: a git worktree under the project's `.branches/` directory, named as its branch.
[11] run record: the `logs` skill's record of a run on the `agent-data` branch: a card (`<id>.json`: what was asked, the branch, the pull request, how it ended, what it cost) and a diary (`<id>.jsonl`: what the agent said). Written by `agent-runner` twice, over the same file: as a marker before the agent exists, and with how it went when the run ends.
[12] the state: `.agent-scheduler/state.json` at the repository root, per user, hidden from git through the repository's exclude file: on or off, keep-alive, the model, the spend cushion, this machine's schedule switches [14], pace picks [20], agents picks [21] and publish picks [17], the scheduler's pid, the last tick's decisions and the schedule it read.
[13] reclaim: removing a finished agent's checkout once its branch holds everything in it.
[14] schedule switch: a person's choice, on one machine, whether a scheduled command runs there; kept in the state, not in the skill. Every scheduled command is off on a machine until a person switches it on there. A switch that is on holds the time it was switched on.
[15] the scheduler's process: the tool's own process between `start` and `stop`, ticking every minute; the state holds its pid.
[16] publish level: how far a run of a command publishes its work: `commit` (commit the work and push nothing), `branch` (commit it, push the branch and open no pull request), `pr` (commit it, push the branch and open its pull request) or `merge` (commit it, push the branch and open its pull request, set to merge on its own once its checks pass). A scheduled run's level is this machine's publish pick [17] for its command. A run given no level publishes nothing.
[17] publish pick: a person's choice, on one machine, of how far a scheduled command's runs publish there: `nothing`, or one of the publish levels [16] (`commit`, `branch`, `pr`, `merge`); kept in the state, not in the skill. It is `commit` until the person picks.
[18] module: a package's own part of a dashboard: its browser part, named by the package's `exports["./dashboard"]`, which the dashboard loads for every project that depends on the package and which reads and saves through the package's own command.
[19] pace: how often at most a scheduled command starts, the one in force on a machine: this machine's pace pick [20] for the command, else the interval its skill gives; an interval (a count of minutes, hours, days, weeks of 7 days or months of 30 days), with a time of day when it has one. A command its check alone paces has no pace.
[20] pace pick: a person's choice, on one machine, of a pace for one scheduled command there: "whenever there is work", or an interval with an optional time of day; kept in the state, not in the skill. A command with no pace pick runs at its skill's pace.
[21] agents pick: a person's choice, on one machine, of that machine's number for one scheduled command: the machine starts another run of the command only while fewer than that number are in flight on any machine that shares the repository. A whole number from 1 to 99; kept in the state, not in the skill. A command with no agents pick has its skill's number.
[22] attached text: a text handed to a run's agent with the run's first prompt, apart from the prompt (`agent-runner run --attach`): the agent reads it after the prompt, and no later prompt of the run carries it. A run that a check started is handed what the check printed this way. A run of an automation kept on this machine [24] is handed the automation's text this way, before what its check printed.
[23] start point: the commit a scheduled run's checkout starts from: origin's default branch (`origin/main`), or, in a repository with no remote, the commit the person's own checkout is on (`HEAD`). Never the files in a person's own checkout: a skill written there and not committed, or committed and not yet on origin's default branch, is not on the start point.
[24] automation: a person's own prompt saved as a scheduled command [3], with the `schedule` the person picked, an interval, a check [25] or both. Written by `agent-scheduler add` or the "New automation" form of the Automations page, as one of two kinds, the person's choice. While its file reads as the tool writes one, the tool shows it, saves it again under its name and removes it (`agent-scheduler show`, `edit` and `remove`, or "Edit prompt" and "Remove" on the Automations page); an automation whose file was changed by hand into something the tool does not write is edited and removed by hand. A shared automation is a command skill of the project (a skill run as the slash command `/<name>`, never picked up by the coding agent on its own): the file `.claude/skills/<name>/SKILL.md`, whose text is the prompt and whose front matter carries that `schedule`; the person commits it, and from then on it is a skill like any other, and its command a scheduled command like any other. An automation kept on this machine is one file written the same way, `.agent-scheduler/automations/<name>.md`, in the tool's own folder, which is hidden from git: nothing is to commit and nobody else gets its command, though its text is in the record of each of its runs, which is shared where the project shares its records. It is no skill and no slash command: its command is listed, switched and started like any other scheduled command, a run of it has the automation's name as its prompt, with no slash, and is handed the file's text with it, its runs are counted on this machine alone (where a command's runs in flight or its last start are said to be counted on any machine, for it that is this machine's), and what is said of a command's skill (the interval and the check its skill gives, its skill's number of agents, what its skill says it does) is, for it, said of that file.
[25] check: the shell command line a skill's `schedule` gives a command [3] as `when`, run at the repository root on every tick [4]; its output says whether the command is due. It may read `$LAST_RUN`: the time of its command's last start, or the time the command was switched on on this machine when that is later.

## Business logic — TL;DR

- **The executable** (`bin/`) - `agent-scheduler`, the one command line: `tick`, `init`, `start`, `stop [--unless-keep-alive]`, `status`, `model`, `offset`, `switch`, `publish`, `pace`, `agents`, `add`, `show`, `edit`, `remove`, `try`, `cleanup`; JSON on stdout, one line for a person on stderr, exit 0, 1 or 2. Running, continuing and checking one run are `agent-runner`'s command line.
- **The rules and the processes** (`src/`) - the schedule as read from the project's skills and the due rule, the state, the pace [19] in force and from when a command is due by it, the cap [8] in force, the spend boundary, a command's runs counted across machines off the run records, the start point [23] of a run and whether a skill's file is on it, a person's own automation [24] saved by `add`, as a skill file of the project or kept on this machine, answered as its file says it by `show`, saved again under its name by `edit` and removed by `remove`, each of the three only while its file reads as the tool writes one, and a check [25] run once by `try`, the tick's decisions, the scheduler's process, the dashboard's `open` and `close` hooks written by `init`, what the tool left in a project removed by `cleanup` (the state file and the scheduler's log, then `.agent-scheduler/` once it is empty, then the rule hiding it from git; the automations kept on this machine stay, and the directory with them), and the command line; told in `src/LOGIC.md`.
- **The dashboard part** (`dashboard/`) - the package's module [18]: the Automations page (per project, each scheduled command with what its skill says it does, when it runs, what the scheduler last decided for it, its schedule switch [14], its pace pick [20], its agents pick [21] and its publish pick [17], per project a "New automation" form that tries a check [25] and saves an automation [24], shared with the project or kept on this machine, and, on the row of an automation whose file reads as the tool writes one, "Edit prompt", which opens the same form filled in from the file to save it again under its name, and "Remove", which asks first and then deletes it), the Settings page's Scheduler section (the spend cushion as a number), the Overview's Scheduler card (each project's scheduler and its last tick), and the usage bar's stop line (the spend cushion as a handle); told in `dashboard/LOGIC.md`.

## Business logic

### A scheduled run's life

#### Context

**User story**: see `## Context`.

#### Business logic

- A person turns the tool on with `start` and switches on, for their machine, the scheduled commands they want run there [14]; the state [12] says `on` and the scheduler's process [15] ticks [4] every minute. `stop` says `off` and ends that process after the tick in flight, which starts nothing more; the agents in flight are `agent-runner`'s processes and run to the end. A scheduler ending clears only its own pid from the state, so the next scheduler, started while it ends (a dashboard's close hook then its open hook), keeps its pid. Stopping one run is `agent-runner`'s: a signal to the run's own process. A dashboard that starts the scheduler when it opens runs `stop --unless-keep-alive` when it closes, which leaves a scheduler whose state says keep-alive running: keep-alive, set with `start --keep-alive`, is per user and read by that line only.
- A tick first pulls the `agent-data` branch [5] (a pull that fails ends the tick: a stale branch must start nothing), then runs `agent-runner`'s sweep [6], then, when the state is on, decides per command [3] of the schedule [2] in the cheapest order: the command's skill is in `.claude/skills`, where the coding agent of scheduled runs, Claude Code, reads it; the command is switched on on this machine [14]; it is due by its pace [19], this machine's pace pick [20] or else its skill's interval: the interval has passed since its last start on any machine, or, for a pace with a time of day, that time has come on a day at least the interval's days after the day of its last start; the check says due, a check reading, as `$LAST_RUN`, the time of its command's last start on any machine, or the time the command was switched on on this machine when that is later or the command never started, so a check that asks what is new since then goes quiet once a run was started for what it found; the cap [8] in force, this machine's agents pick [21] or else the skill's number, is not reached, counted from the run records [11] saying `running` on the branch, whatever the machine; the command's skill's file (`SKILL.md` in the skill's folder) is on the start point [23], asked only now that a run would otherwise start, origin's default branch fetched first, once per tick and waited for 5 seconds at most, as a run's own checkout fetches it (the schedule is read from the skill files in the person's own checkout, and a run's checkout is made from the start point, so a skill that is not on the start point is no command to the run's agent; a command that is switched off, not due, without work or at its cap is never asked about, so nothing is fetched for it); the coding agent's CLI is installed and logged in on this machine; the quota [9] has headroom, read only when everything else says start; and, last, the command is still switched on on this machine, its schedule switch [14] read again from the state as it is at that moment, since a person may have switched the command off, or removed it, while its check and the readings ran. An automation kept on this machine [24] is decided in the same order without the two questions about a skill: it is in no skills folder and on no commit, and needs to be in neither. A command that passes gets a run record written as a marker through `agent-runner`, `status: running`, with, as the run's start, the moment the tick turned to the command, before its check ran (the run keeps that start on its record, so the next check asks from before this one ran and misses nothing that came in meanwhile), with the prompt `/<command>`, or the name alone of an automation kept on this machine, the state's model and `agent-runner`'s mark (`caller.runner`: this machine, and the publish level [16] in force when there is one: this machine's publish pick [17] for the command, `commit` where nobody picked, and no level for a pick of `nothing`); the tool counts again, withdraws the marker if another machine's landed first past the cap in force on this machine, and otherwise has `agent-runner` spawn the run [7] as a detached process, on the state's model and at the publish level in force, handing it, when a check started it, what the check printed, as its attached text [22]; a run of an automation kept on this machine is handed its text that way, before what a check printed. A record names no command: a run counts for the skill's command its prompt names with a slash, else for the one its first word is, so a run a person started from a dashboard or a shell with `/work-queue` holds the `work-queue` cap and interval too; a prompt with no slash counts for an automation kept on this machine only when it is that automation's name and nothing else, and only on the machine that started the run; any other prompt counts for no command. What says a run's process lives is not the marker but the run's lock, `agent-runner`'s, which the spawn takes before the run's process exists and hands to it.
- From there the run is `agent-runner`'s: it makes the checkout [10] from the start point [23], prompts the coding agent [1] once with `/<command>`, or with the name of an automation kept on this machine [24], whose text it hands the agent with the prompt, lets the agent's own loop run to the end (the agent commits and names its branch itself, and publishes as far as the publish level [16] in force says, which `agent-runner` tells it in one sentence after the prompt; a run with no level in force, this machine's publish pick [17] for its command being `nothing`, publishes nothing; a run that a check started is handed its attached text [22] with the prompt, after it: words saying that the command's check printed what follows and that it says why the run started, not what the work is, then what the check printed, at most its first 8000 characters), records the run over the marker and reclaims [13] the checkout; a run whose last turn asked a question ends `waiting` and keeps its checkout for a person's answer.
- On every tick `agent-runner`'s sweep records and reclaims what a run of this machine could not: a run whose lock a live process holds is left alone; otherwise a live card still `running` is recorded `failed`; one that ended but was never recorded is recorded as it ended, and kept when it is `waiting`; a marker of this machine with no checkout behind it is recorded `failed` with the spawn's stderr, else `stopped`. A running record from another machine is never touched: only that machine's sweep, or a person, changes it, and a machine that never comes back leaves its command capped on purpose.
- Every decision of the tick is one line in the state (`started <id>`, `not due`, `not due (last start 2h ago, every 6h)`, `not due (next start from 2026-10-10 10:00, every 2d at 10:00)`, `cap reached (…)`, `not ready: …`, `quota: …`, `switched off on this machine`, `not a command of the coding agent: its skill is only under .agents/skills, not .claude/skills`, `not on origin/main: a run's checkout starts from origin/main, and the command's skill is not there`, …), so a dashboard or a person reads why nothing started without a log. A skill whose `schedule` cannot be read gives no command, and every tick names that skill with `unreadable schedule: <reason>`, also when the state is off or the pull failed. An automation kept on this machine [24] that is not listed is named on every tick too, with `unlisted automation: <reason>`. The tick also records the schedule's commands as it read them, each with what its skill says it does (the `description` of the skill's front matter) and its skill's number of agents at once when that is more than one, marked as this machine's when it is an automation kept on this machine [24], and marked as one the tool can show, save again and remove when it is an automation [24] of either kind whose file reads as the tool writes one, so a dashboard lists them, each with this machine's schedule switch [14], pace pick [20], agents pick [21] and publish pick [17], without reading the skills itself.

### A person's own automation

#### Context

**User story**: see the last user story of `## Context`.

**Problem**: everything else a person sets in this tool is their machine's, kept in the state [12], which git does not track. A shared automation [24] is not: it is a file of the project, which every machine that shares the repository gets once it is on origin's default branch, and which starts no run before it is on the start point [23].

**Problem**: not every prompt of a person's is the project's business. One they want for themselves alone must be saved with no file to commit, and must be no command on any other machine.

**Problem**: a shared automation [24] is a skill file among the project's skill files, and the tool keeps no list of the ones it saved. Saving one again writes its whole file anew, and removing one deletes it: done to a skill a person or a package wrote, either would lose their work.

#### Business logic

- An automation [24] is a name, a prompt, and at least one of an interval and a check [25], with one optional plain line saying what the check waits for. `agent-scheduler add` saves it shared with the project, as the skill file `.claude/skills/<name>/SKILL.md` in the person's own checkout: the prompt is the skill's text, its first line, cut at 150 characters, is what the skill says it does, and the front matter makes the skill a command and carries the `schedule` the person picked. Whatever the person typed is written so that it can end neither its own value nor the front matter, three dashes in a row included, and can add or change no other key of the file. The tool stages and commits nothing: the file is the person's to commit.
- `agent-scheduler add --private` saves it kept on this machine instead: the same file, written as `.agent-scheduler/automations/<name>.md` in the tool's own folder, which is hidden from git before the file is written. No file of the project changes, nothing is to commit, and no other machine gets its command. Its text still travels: it is in the record of each of its runs, which is shared where the project shares its records, and the form and the command's usage say so. A prompt longer than 32,000 characters is refused.
- What is saved is what the tick [4] reads: before the file is written, its text is read by the reader the tick reads every skill's `schedule` with, and an automation whose `schedule` that reader cannot read is refused with the reader's reason, and so is one whose file would not read back as typed. So are a name that is no command's name (lower-case letters, digits and dashes, starting with a letter or a digit, never three dashes in a row) or is longer than 64 characters, a blank prompt, and a name that either skills folder of the project, `.claude/skills` or `.agents/skills`, already holds, or that an automation kept on this machine already has, whatever its capitals and for both kinds alike: an automation never replaces a skill or another automation.
- The answer says where the file is and where a run's checkout starts (`origin/main`, or `HEAD` in a repository with no remote), so the person is told where a shared automation's file has to get to. For one kept on this machine the answer also says that it is: its file has to get nowhere.
- After a save, `add` takes out of this machine's state [12] whatever it held under the new command's name, a schedule switch [14], a pace pick [20], an agents pick [21] or a publish pick [17] left by a command of that name that is gone, so the new command starts switched off there, at its own pace. The state is written only when it held something under the name.
- From then on a shared automation is a skill like any other. The next tick lists its command, switched off; a person switches it on with its schedule switch [14] and may set a pace pick [20], an agents pick [21] and a publish pick [17] for it; and it starts no run until its skill's file is on the start point [23], saying `not on origin/main: …` when it is due before that (see "A scheduled run's life").
- An automation kept on this machine is read from its own file on every tick, after the project's skills, and listed with their commands, marked as this machine's. Its command has a schedule switch [14], a pace pick [20], an agents pick [21] and a publish pick [17] like any other, and starts switched off. It is no skill, so it is asked neither whether its skill is in `.claude/skills` nor whether it is on the start point [23], and it can start at the first tick after it was switched on. A run of it has the automation's name as its prompt, with no slash, and counts for it by that name, on this machine alone, whatever its text says and however the text changes: another person's automation of the same name, on their machine, is another one. The text, 32,000 characters at most, is handed to the run with the prompt, as its attached text [22], before what its check printed when a check started the run. It is not listed, and every tick says why under its name with `unlisted automation: <reason>`, when its file's name is no command's name or the file cannot be read, when a skill of the project has its name too (that skill's commands are then not listed either, since the two could not be told apart, until the file is renamed or removed), when its `schedule` is missing or cannot be read, when it has several rows or a word, or when it has no text or too long a one. What this machine gave it, its schedule switch [14] and its picks, goes with it: a tick first takes them out of the state [12] when the automation's file is gone, removed or renamed, and when a skill has its name too, so whatever takes the name next starts switched off. While its file is still there it keeps them, also while a slip in the file keeps it off the list. `agent-scheduler cleanup` leaves it where it is, and says so; its folder goes once nothing is in it.
- The tool shows, saves again and removes an automation [24] only while it can tell that it wrote the file: the file reads as the tool writes one, every line what the tool would write for the name, the prompt, the interval, the check [25] and the plain line it holds, but for what its description says, which is written anew from the prompt's first line with every save; it is a file itself and no link; and, for a shared automation, it is alone in a folder of `.claude/skills` that is no link, a `.DS_Store` beside it not counting. Whoever saved it, and on which machine, is not asked. A skill a person wrote, a skill that comes from a package as a link, a skill with a script beside its file, and an automation whose file was changed by hand into something the tool does not write (one more key, a description written another way) are none. The schedule [2] is the one place that says which commands are such automations: every tick records the mark with the command, the Automations page offers "Edit prompt" and "Remove" on those rows alone, and `show`, `edit` and `remove` read the schedule and take only a command that carries the mark. Any other name they refuse in one sentence: that the schedule lists nothing of that name, the schedule's own reason for an automation or a skill it could not list, or that the files are to be edited or removed by hand.
- `agent-scheduler show <name>` answers such an automation as its file says it at that moment: its name, its prompt, its interval, its check, the plain line, its file, and whether it is kept on this machine. Nothing is written.
- `agent-scheduler edit <name>` saves it again under its name, changing only what it is given: a prompt, an interval, a check or a plain line given takes the place of the one in the file; one left out stays as the file says it; and an interval, a check or a plain line given empty (`--when=`) is taken out, what a check waits for going out with the check. With nothing given the command is a usage error. The whole automation, once the change is laid over what the file says, must be one that could be saved new: a blank prompt, a `schedule` the tick cannot read, as when the check is taken out and no interval is left, and a prompt longer than 32,000 characters for one kept on this machine are refused, and the file stays. Otherwise the file is written anew, whole, where it is: beside the file first and then moved over it, so a write that fails midway leaves the automation as it was. The name does not change, and neither does the kind: a shared automation stays a skill file of the project, one kept on this machine stays in the tool's folder. The command is the same command, so its past runs still count for it, and this machine's state [12] is not touched: its schedule switch [14], pace pick [20], agents pick [21] and publish pick [17] stay. Nothing is committed. The tick reads the schedule from the files on disk, so the next tick follows the new interval and the new check. A run of a shared automation is told the new prompt only once the change is on the start point [23], since its checkout is made from there; a run of one kept on this machine is handed the new text from its next start on. The answer says where the file is and where a run's checkout starts.
- `agent-scheduler remove <name>` deletes its file, and the folder that held it alone. Nothing is committed and nothing git holds is changed. For a shared automation the answer says what git still holds of the file, and where a run's checkout starts: `committed`, the file is in a commit, so the deletion is a change of the person's to commit, and every other machine that has the project keeps the command until the deletion is on origin's default branch; `staged`, the file was added to git's index and never committed, so a commit made now would still add it; `nothing`, git never had the file; `unknown`, git could not be asked. What no commit holds cannot be brought back: a shared automation's file that was never committed, or the last changes to it, and all of an automation kept on this machine, whose answer says only that it was kept there. The command line then takes out of this machine's state [12] what it held for the command, its schedule switch [14] and its picks, and takes the command off the last tick's record, so a dashboard stops listing it at once and not a tick later; the state is written only when there is something to take out. The run records [11] of its past runs stay.
- A removal may come while a tick [4] runs. Just before a tick marks a run, it asks the command's schedule switch [14] once more, as the state holds it at that moment, and a command switched off or removed meanwhile gets `switched off on this machine` and no run. And when a tick writes its record, it leaves out every command whose file went while it ran, taking out of the state what this machine gave an automation kept on this machine that went so: the record never puts a removed command back on a dashboard.
- `agent-scheduler try` runs a check once, before anything is saved, as a tick would run it but within 20 seconds, less than the minute a tick gives a check and less than the 30 seconds a dashboard waits for a command, and gives it the time a day ago as `$LAST_RUN`: a command that does not exist yet has no last start, and "since now" would show nothing. It answers whether the check ran, whether an agent would start, what it printed, cut as a run is handed it, and, when it failed, that it took too long or the last line of its error. Nothing is saved and no run starts.
