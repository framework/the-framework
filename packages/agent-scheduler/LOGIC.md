The `@openagt/agent-scheduler` package: a standalone tool, like `@openagt/agent-driver`, that starts coding agents [1] on a schedule for one project. The project's skills bring the schedule [2]: a skill says, in the front matter of its `SKILL.md`, which commands [3] it schedules, each with when it is due and how many may run at once. Each person switches a scheduled command on for their own machine [14], may set their own pace for it there [20] and their own number of agents at once [21], and picks how far its runs publish there [17]. The tool ticks [4] every minute, pulls the project's `agent-data` branch [5], sweeps [6] what earlier runs [7] left, and for every command that is switched on on this machine, due, under the cap [8] in force and within the account's quota [9], has `agent-runner` start one agent in its own checkout [10], which records the run [11] on the branch, where every machine and the dashboard read it. The tool names no command of its own: a skill's front matter is the only place a command is named, and the skill is what runs, the rest of the command's name being the word the skill gets. The package also brings its own part of a dashboard, its module [18]: the Automations page, where a person switches each scheduled command on or off, sets when it runs and how many agents work on it at once, and picks how far its runs publish, the Scheduler section of the Settings page, the Scheduler card of the Overview and the stop line on the usage bar, each reading through `agent-scheduler status` and saving through `offset`, `switch`, `pace`, `agents` and `publish`. `package.json` (which exports the module as `./dashboard`) and the `tsconfig*.json` files configure the build and the test runner and carry no business logic; `dist/` and `dist-test/` are build output.

## Context

**User story**: the project has a `work-queue` skill whose front matter says `schedule:` with `when: npx queue`, and a `triage` skill whose `schedule` holds `word: quick` and `every: 6h`. The user runs `agent-scheduler start`, switches both commands on for their own machine, and picks `pr` as the publish pick [17] of `work-queue`; from then on, whenever the project's agent queue holds an entry, one agent works it in its own checkout and opens a pull request, never two at once, and at most every six hours one agent triages the tickets, and never past the share of the week's quota that has elapsed; the user reads why nothing started (`not due`, `cap reached (…)`, `quota: …`) in the state file or on a dashboard, changes the model or the spend cushion for their own machine, turns a scheduled command on or off for their own machine with its schedule switch [14] (every scheduled command starts switched off, so a skill that arrives in the project starts no agent by itself), sets how often at most a scheduled command starts on their own machine with its pace pick [20] (`agent-scheduler pace "triage quick" 2d 10:00` for every second day from 10:00 on; until they pick, the command runs at its skill's pace [19]), sets how many agents may work on a scheduled command at once with its agents pick [21] (`agent-scheduler agents work-queue 3`; until they pick, the skill's number holds), changes how far a scheduled command's runs publish on their own machine with its publish pick [17] (until they pick, a run commits its work and pushes nothing), and runs `agent-scheduler stop` to turn it off while the agents in flight run to the end.

**Business logic story**: the daemon of OpenAgent used to watch the branch and start agents on its own rules, in its own memory. This tool replaces that with files and small processes: the schedule is in the project's skill files, each skill bringing its own scheduled commands; the tool's state [12] is an untracked JSON file under `.agent-scheduler/`, per user; a run in flight is a run record [11] on the `agent-data` branch with `status: running`, so two machines sharing the repository count the same runs against a cap; a run is one detached process of `agent-runner`, `agent-runner run`, the same tool a dashboard's Start runs through, that makes a checkout through the `branches` package, prompts the coding agent [1] once through `agent-driver` with no system prompt (the command's skill file is the whole instruction, and the agent publishes its own work, as far as the run's publish level [16] says, with the skills in its checkout), then writes the run record and reclaims [13] the checkout; and the scheduler's process [15] is a loop of ticks that holds nothing a restart would lose. This tool decides when; `agent-runner` runs. The spend-boundary rule is copied from OpenAgent rather than imported, because this tool depends on `@openagt/agent-driver-claude`, which reads the quota, and not on OpenAgent, which draws the panel.

## Glossary

[1] coding agent: the CLI doing the actual work: Claude Code or Codex. A scheduled run is on Claude Code.
[2] the schedule: all the scheduled commands of a project. A skill of the project brings its own with the `schedule` key in the front matter of its `SKILL.md`, called the skill's `schedule`. The tool reads the skills in the project's two skill folders, `.claude/skills` and then `.agents/skills`. A skill with no `schedule` key brings none. A command whose skill is only under `.agents/skills` is listed and never started: every scheduled run is on Claude Code, which reads a project's skills from `.claude/skills`.
[3] command: a scheduled command, one command a skill schedules, named as a person types the command without its slash: the skill's folder name, then at most one word the skill takes as its argument (`triage quick`); the coding agent's harness expands the slash command `/<name>`, and a run's whole prompt is that slash command.
[4] tick: one pass of the scheduler: pull the `agent-data` branch, sweep, then one decision per scheduled command, each decision one line in the state.
[5] the `agent-data` branch: the branch of a project's repository used as a file store for everything agents share: tickets, the agent queue, the runs.
[6] sweep: `agent-runner`'s pass, run on every tick, that records and reclaims the runs of this machine whose process died, and only this machine's.
[7] run: one agent this tool starts: a detached process of `agent-runner` (`agent-runner run`), a checkout, one prompt to the coding agent, and a run record when it ends. Its id is its start time, `2026-09-16T14-01-00-000Z`.
[8] cap: how many runs of one scheduled command a machine lets be in flight at once: the machine starts another run of the command only while fewer than its number are in flight on any machine that shares the repository. Its number is the agents pick [21] made on it, a person's own number for the command there, else the number the command's skill gives, 1 when the skill gives none.
[9] quota: the account's subscription allowance, as the coding agent reports it: a session window and a quota week, each with a percentage used.
[10] checkout: an agent's own working copy of the project: a git worktree under the project's `.branches/` directory, named as its branch.
[11] run record: the `logs` skill's record of a run on the `agent-data` branch: a card (`<id>.json`: what was asked, the branch, the pull request, how it ended, what it cost) and a diary (`<id>.jsonl`: what the agent said). Written by `agent-runner` twice, over the same file: as a marker before the agent exists, and with how it went when the run ends.
[12] the state: `.agent-scheduler/state.json` at the repository root, per user, hidden from git through the repository's exclude file: on or off, keep-alive, the model, the spend cushion, this machine's schedule switches [14], pace picks [20], agents picks [21] and publish picks [17], the scheduler's pid, the last tick's decisions and the schedule it read.
[13] reclaim: removing a finished agent's checkout once its branch holds everything in it.
[14] schedule switch: a person's choice, on one machine, whether a scheduled command runs there; kept in the state, not in the skill. Every scheduled command is off on a machine until a person switches it on there.
[15] the scheduler's process: the tool's own process between `start` and `stop`, ticking every minute; the state holds its pid.
[16] publish level: how far a run of a command publishes its work: `commit` (commit the work and push nothing), `branch` (commit it, push the branch and open no pull request), `pr` (commit it, push the branch and open its pull request) or `merge` (commit it, push the branch and open its pull request, set to merge on its own once its checks pass). A scheduled run's level is this machine's publish pick [17] for its command. A run given no level publishes nothing.
[17] publish pick: a person's choice, on one machine, of how far a scheduled command's runs publish there: `nothing`, or one of the publish levels [16] (`commit`, `branch`, `pr`, `merge`); kept in the state, not in the skill. It is `commit` until the person picks.
[18] module: a package's own part of a dashboard: its browser part, named by the package's `exports["./dashboard"]`, which the dashboard loads for every project that depends on the package and which reads and saves through the package's own command.
[19] pace: how often at most a scheduled command starts, the one in force on a machine: this machine's pace pick [20] for the command, else the interval its skill gives; an interval (a count of minutes, hours, days, weeks of 7 days or months of 30 days), with a time of day when it has one. A command its check alone paces has no pace.
[20] pace pick: a person's choice, on one machine, of a pace for one scheduled command there: "whenever there is work", or an interval with an optional time of day; kept in the state, not in the skill. A command with no pace pick runs at its skill's pace.
[21] agents pick: a person's choice, on one machine, of that machine's number for one scheduled command: the machine starts another run of the command only while fewer than that number are in flight on any machine that shares the repository. A whole number from 1 to 99; kept in the state, not in the skill. A command with no agents pick has its skill's number.
[22] attached text: a text handed to a run's agent with the run's first prompt, apart from the prompt (`agent-runner run --attach`): the agent reads it after the prompt, and no later prompt of the run carries it. A run that a check started is handed what the check printed this way.

## Business logic — TL;DR

- **The executable** (`bin/`) - `agent-scheduler`, the one command line: `tick`, `init`, `start`, `stop [--unless-keep-alive]`, `status`, `model`, `offset`, `switch`, `publish`, `pace`, `agents`, `cleanup`; JSON on stdout, one line for a person on stderr, exit 0, 1 or 2. Running, continuing and checking one run are `agent-runner`'s command line.
- **The rules and the processes** (`src/`) - the schedule as read from the project's skills and the due rule, the state, the pace [19] in force and from when a command is due by it, the cap [8] in force, the spend boundary, a command's runs counted across machines off the run records, the tick's decisions, the scheduler's process, the dashboard's `open` and `close` hooks written by `init`, what the tool left in a project removed by `cleanup` (the state file and the scheduler's log, then `.agent-scheduler/` once it is empty, then the rule hiding it from git), and the command line; told in `src/LOGIC.md`.
- **The dashboard part** (`dashboard/`) - the package's module [18]: the Automations page (per project, each scheduled command with what its skill says it does, when it runs, what the scheduler last decided for it, its schedule switch [14], its pace pick [20], its agents pick [21] and its publish pick [17]), the Settings page's Scheduler section (the spend cushion as a number), the Overview's Scheduler card (each project's scheduler and its last tick), and the usage bar's stop line (the spend cushion as a handle); told in `dashboard/LOGIC.md`.

## Business logic

### A scheduled run's life

#### Context

**User story**: see `## Context`.

#### Business logic

- A person turns the tool on with `start` and switches on, for their machine, the scheduled commands they want run there [14]; the state [12] says `on` and the scheduler's process [15] ticks [4] every minute. `stop` says `off` and ends that process after the tick in flight, which starts nothing more; the agents in flight are `agent-runner`'s processes and run to the end. A scheduler ending clears only its own pid from the state, so the next scheduler, started while it ends (a dashboard's close hook then its open hook), keeps its pid. Stopping one run is `agent-runner`'s: a signal to the run's own process. A dashboard that starts the scheduler when it opens runs `stop --unless-keep-alive` when it closes, which leaves a scheduler whose state says keep-alive running: keep-alive, set with `start --keep-alive`, is per user and read by that line only.
- A tick first pulls the `agent-data` branch [5] (a pull that fails ends the tick: a stale branch must start nothing), then runs `agent-runner`'s sweep [6], then, when the state is on, decides per command [3] of the schedule [2] in the cheapest order: the command's skill is in `.claude/skills`, where the coding agent of scheduled runs, Claude Code, reads it; the command is switched on on this machine [14]; it is due by its pace [19], this machine's pace pick [20] or else its skill's interval: the interval has passed since its last start on any machine, or, for a pace with a time of day, that time has come on a day at least the interval's days after the day of its last start; the check says due; the cap [8] in force, this machine's agents pick [21] or else the skill's number, is not reached, counted from the run records [11] saying `running` on the branch, whatever the machine; the coding agent's CLI is installed and logged in on this machine; the quota [9] has headroom, read only when everything else says start. A command that passes gets a run record written as a marker through `agent-runner`, `status: running`, with the prompt `/<command>`, the state's model and `agent-runner`'s mark (`caller.runner`: this machine, and the publish level [16] in force when there is one: this machine's publish pick [17] for the command, `commit` where nobody picked, and no level for a pick of `nothing`); the tool counts again, withdraws the marker if another machine's landed first past the cap in force on this machine, and otherwise has `agent-runner` spawn the run [7] as a detached process, on the state's model and at the publish level in force, handing it, when a check started it, what the check printed, as its attached text [22]. A record names no command: a run counts for the scheduled command its prompt names, else for its prompt's first word, so a run a person started from a dashboard or a shell with `/work-queue` holds the `work-queue` cap and interval too. What says a run's process lives is not the marker but the run's lock, `agent-runner`'s, which the spawn takes before the run's process exists and hands to it.
- From there the run is `agent-runner`'s: it makes the checkout [10], prompts the coding agent [1] once with `/<command>`, lets the agent's own loop run to the end (the agent commits and names its branch itself, and publishes as far as the publish level [16] in force says, which `agent-runner` tells it in one sentence after the prompt; a run with no level in force, this machine's publish pick [17] for its command being `nothing`, publishes nothing; a run that a check started is handed its attached text [22] with the prompt, after it: words saying that the command's check printed what follows and that it says why the run started, not what the work is, then what the check printed, at most its first 8000 characters), records the run over the marker and reclaims [13] the checkout; a run whose last turn asked a question ends `waiting` and keeps its checkout for a person's answer.
- On every tick `agent-runner`'s sweep records and reclaims what a run of this machine could not: a run whose lock a live process holds is left alone; otherwise a live card still `running` is recorded `failed`; one that ended but was never recorded is recorded as it ended, and kept when it is `waiting`; a marker of this machine with no checkout behind it is recorded `failed` with the spawn's stderr, else `stopped`. A running record from another machine is never touched: only that machine's sweep, or a person, changes it, and a machine that never comes back leaves its command capped on purpose.
- Every decision of the tick is one line in the state (`started <id>`, `not due`, `not due (last start 2h ago, every 6h)`, `not due (next start from 2026-10-10 10:00, every 2d at 10:00)`, `cap reached (…)`, `not ready: …`, `quota: …`, `switched off on this machine`, `not a command of the coding agent: its skill is only under .agents/skills, not .claude/skills`, …), so a dashboard or a person reads why nothing started without a log. A skill whose `schedule` cannot be read gives no command, and every tick names that skill with `unreadable schedule: <reason>`, also when the state is off or the pull failed. The tick also records the schedule's commands as it read them, each with what its skill says it does (the `description` of the skill's front matter) and its skill's number of agents at once when that is more than one, so a dashboard lists them, each with this machine's schedule switch [14], pace pick [20], agents pick [21] and publish pick [17], without reading the skills itself.
