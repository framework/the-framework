The `@openagt/agent-scheduler` package's module [1] for the dashboard: the Automations page, the Scheduler section of the Settings page, the Scheduler card of the Overview, and the stop line [6] on the Overview's usage bar. All four show what each project's scheduler keeps in its state [2], and all but the card change it, reading it with `agent-scheduler status` and saving with `agent-scheduler offset`, `switch`, `pace`, `agents` and `publish`, the same commands a person types. The Automations page also holds the "New automation" form, where a person saves a prompt of their own as an automation [11] of a project with `agent-scheduler add`, after trying its check [12] with `agent-scheduler try`: the one thing the module has written that is not the state, a skill file of the project. The package exports the module as `./dashboard` (`dist/dashboard/dashboard.js` and its stylesheet), which is how the dashboard finds it; the dashboard itself never names this package, reads no scheduler file and has no hook line for a scheduler setting.

## Context

**User story**: a project depends on this package. On the Overview the user finds a Scheduler card saying the project's scheduler is on and what its last tick [7] decided, and a handle on the usage bar that sets how far past the quota boundary scheduled work may start. In the sidebar the user finds Automations: a page with one page row [8] per scheduled command of each project, saying what the command does, when it runs and what the scheduler last decided for it, with a checkbox (does it run on this machine) and, behind "Edit", when it runs on this machine (as its skill says, whenever there is work, or every so many minutes, hours, days, weeks or months, with a time of day beside days or more), how many agents may work on it at once (as its skill says, or up to a number) and a menu (how far its runs publish on this machine). Beside each project's name on that page the user finds "New automation": a form for a name, what the agent is told and when it runs (every so often, by a shell line that prints what is new, or both), with "Try it" to run the shell line once, and Save, which writes the automation [11] into the project as a skill file the user commits. In Settings, after the dashboard's own sections, the user finds Scheduler: the same number as the usage bar's handle, as a typed value. A dashboard with no project depending on this package shows none of it.

**Business logic story**: the scheduler's settings are this machine's, in a file only this package's command reads and writes (`../src/state.ts`). The project's skills say which commands are scheduled, what each does and when each is due, the same for every machine; whether a scheduled command runs on this machine is its schedule switch [3], how often at most it starts here is its skill's interval until a person sets a pace pick [9], how many of its runs this machine lets be in flight at once is its skill's number until a person sets an agents pick [10], and how far its runs publish here is its publish pick [4], all four this machine's alone and one project's, so all four are on the Automations page, under the project's name. An automation [11] is no setting of this machine: it is a skill of the project, the same for every machine once its file is on origin's default branch, written into the person's own checkout by `agent-scheduler add` (`../src/automation.ts`), never by the module itself. It is made on the Automations page because that is where its command is then listed, with the same four choices as any other. The spend cushion [5] is one number for every project, so it is read as the loosest any project holds and saved to all of them, from the Settings page or the usage bar. The `open` and `close` lines that start and stop the scheduler with the dashboard are still hook lines of the dashboard's (`../src/init.ts`); nothing else of the scheduler is.

## Glossary

[1] module: a package that adds to the dashboard (pages, Overview cards, Settings sections, the usage bar's stop line, and more): its browser part, named by the package's `exports["./dashboard"]`, reads and saves its data through its own package's command. A module comes from a project's dependencies.
[2] the state: `.agent-scheduler/state.json` at the project's root, per user, hidden from git: on or off, keep-alive, the model, the spend cushion, this machine's schedule switches, pace picks, agents picks and publish picks, the scheduler's pid, the last tick's decisions and the schedule it read. `agent-scheduler status` prints it, plus whether the scheduler's process is alive.
[3] schedule switch: a person's choice, on one machine, whether a scheduled command (a command one of the project's skills schedules in the front matter of its `SKILL.md`) runs there; kept in the state, not in the skill. Every scheduled command is off on a machine until a person switches it on there.
[4] publish pick: a person's choice, on one machine, of how far a scheduled command's runs publish there: nothing, a commit, the branch, a pull request, or a pull request set to merge on its own once its checks pass; kept in the state, not in the skill. Until the person picks, the command's runs commit their work and push nothing.
[5] spend cushion: how far past the quota boundary (the share of the account's quota week that may be spent by now) a scheduled run may still start, in percentage points of the week; the state's `spendOffset`. Positive is lenient, negative is strict. The dashboard calls it the spend offset.
[6] stop line: where a module's unattended work stops on the Overview's usage bar, as an offset from the quota boundary in percentage points; the module reads the offset and saves a new one, the bar draws the line and its handle. This module's stop line is the spend cushion [5].
[7] tick: one pass of the scheduler, every minute: one decision per scheduled command, each one line in the state.
[8] page row: one line of the Automations page: one scheduled command of one project, with its checkbox and its "Edit". It is not a row of a skill's `schedule` key (the key in the front matter of its `SKILL.md` where the skill says which commands it schedules), which the module never reads.
[9] pace pick: a person's choice, on one machine, of a pace for one scheduled command there: "whenever there is work", or an interval with an optional time of day; kept in the state, not in the skill. A command with no pace pick runs at its skill's pace.
[10] agents pick: a person's choice, on one machine, of that machine's number for one scheduled command: the machine starts another run of the command only while fewer than that number are in flight on any machine that shares the repository. A whole number from 1 to 99; kept in the state, not in the skill. A command with no agents pick has its skill's number.
[11] automation: a person's own prompt saved as a command skill of the project (a skill run as the slash command `/<name>`, never picked up by the coding agent on its own): the file `.claude/skills/<name>/SKILL.md`, whose text is the prompt and whose front matter carries the `schedule` the person picked (the key where a skill says when its command is due), an interval, a check [12] or both. Written by `agent-scheduler add` or the "New automation" form of the Automations page; from then on a skill like any other, and its command a scheduled command like any other.
[12] check: the shell line a skill's `schedule` gives a scheduled command as `when`: the scheduler runs it in the project, every minute at most, while the command is switched on and the time between two of its starts has passed, when it has one, and starts an agent when it prints something. The "New automation" form calls it "a shell line".

## Business logic — TL;DR

- **The module's definition** (`index.tsx`) - one page at `/automations`, labelled Automations with a calendar-and-clock icon; one Overview card, Scheduler, at order 90; one Settings section, Scheduler, at order 20; the usage bar's stop line [6], read as the loosest spend cushion [5] and saved to every project; and the stylesheet beside the module.
- **What is read and how it is saved** (`schedulers.ts`, `schedulers.test.ts`) - each project's scheduler as `agent-scheduler status` printed it, with each scheduled command's schedule switch [3] (on when the state holds the time it was switched on), pace pick [9], agents pick [10], publish pick [4] and last decision folded in, what its skill says it does and how many agents at once its skill allows, and the skills whose `schedule` key the last tick [7] could not read; the loosest spend cushion; the save of the cushion to every project; and the words the page, the section and the card use: the scheduler's status, a command's pace, how many agents at once, how far it publishes, what the scheduler last decided for it, and which publish picks a project is offered; and what the page's Edit box holds of a pace and of a number of agents while a person picks them.
- **The Automations page** (`AutomationsPage.tsx`, `AutomationsPage.test.tsx`) - one group per project under its name, with its scheduler's status, and one page row [8] per scheduled command: the command, what its skill says it does, when it runs, how far its runs publish, what the scheduler last decided for it, and a checkbox for its schedule switch [3]; a page row whose pace is a person's own says "your pick", and one with more than one agent at once, or with an agents pick [10], says how many, with "your pick" after the number when it is the person's own; "Edit" opens the page row in place to save its pace pick [9], then its agents pick [10], then its publish pick [4]; read every 10 seconds; saves go one at a time, and a save not taken says why on its own page row; a scheduler that is off, or on with no live process, is said under the project's name; beside each project's name, "New automation" opens the form below in that project, one form at a time, no project offering the button while a form is open, none for a project that could not be read, and the page rows are read again once an automation [11] was saved.
- **The "New automation" form** (`NewAutomation.tsx`, tested through `AutomationsPage.test.tsx`) - a name, what the agent is told, and when it runs: an interval that can be unticked, a check [12], and plain words for what the check waits for; one line saying what is missing or when the automation [11] would run; "Try it" runs the check once in the project with `agent-scheduler try`, for 20 seconds at most, and shows what it printed and whether an agent would start, the answer shown always being for the check as it stands and only the latest try's answer taken; "Save" runs `agent-scheduler add`, and a panel then says where the file is, that it is the person's to commit, where it has to get to before its page row [8] can start, and when the page row shows: within a minute where the project's scheduler is running, not yet where it is not; a save not taken says why and keeps what was typed; Cancel closes the form and saves nothing, and Escape closes only a form nothing was typed into.
- **The form as data** (`new-automation.ts`, `new-automation.test.ts`) - the draft the form opens with (once a day, no check), what still keeps a draft from being saved, the first thing first, a prompt, a check or plain words longer than the 4000 characters the form can hand over among them, the words beside the interval, whether anything was typed into a draft yet, the words of `agent-scheduler add` for a draft, each text one argument together with its flag, the sentence a draft's page row [8] would say for when it runs, what `agent-scheduler try` answered as a verdict for a person, and what `agent-scheduler add` answered: the file and where it has to get to; and when the saved automation's page row shows, by whether the project's scheduler is running.
- **The Scheduler section** (`SchedulerSettings.tsx`, `SchedulerSettings.test.tsx`) - "Spend offset" alone, the spend cushion [5] as a number saved to every project; read every 10 seconds; saves go one at a time; a save not taken says why; a project that cannot be read is named with the reason.
- **The Scheduler card** (`SchedulerCard.tsx`, `SchedulerCard.test.tsx`) - one card row per project: on, off or on but not running, keep-alive, the model, and the last tick's [7] decisions, a decision that started a run opening that agent; read every 10 seconds.
- **What the tests share** (`fixtures.ts`) - a fake dashboard host whose command answers what a test says, and what `status` prints for a scheduler that ticked once in a project whose skills schedule two commands.
- **Built to share, not to bundle** (`vite.config.ts`, `vitest.config.ts`, `vitest.setup.ts`, `dashboard.css`, `tsconfig.json`) - the module leaves React and `@openagt/dashboard/module` as bare imports the dashboard supplies, and its stylesheet holds only its own utilities, coloured by the dashboard's theme file; these files carry no business logic beyond that.
