The `@openagt/agent-scheduler` package's module [1] for the dashboard: the Automations page, the Scheduler section of the Settings page, the Scheduler card of the Overview, and the stop line [6] on the Overview's usage bar. All four show what each project's scheduler keeps in its state [2], and all but the card change it, reading it with `agent-scheduler status` and saving with `agent-scheduler offset`, `switch`, `pace`, `agents` and `publish`, the same commands a person types. The Automations page also holds the automation form [13]. Opened by "New automation", it is where a person saves a prompt of their own as an automation [11] of a project with `agent-scheduler add`, after trying its check [12] with `agent-scheduler try`: shared with the project, it is a skill file of the project, the one thing the module has written that is not this machine's; kept on this machine, it is a file beside the state. On the page row [8] of such an automation, while its file reads as the tool writes one, "Edit prompt" opens the same form, filled in from the file with `agent-scheduler show`, to save the automation again under its name with `agent-scheduler edit`, and "Remove" asks first and then deletes it with `agent-scheduler remove`. The package exports the module as `./dashboard` (`dist/dashboard/dashboard.js` and its stylesheet), which is how the dashboard finds it; the dashboard itself never names this package, reads no scheduler file and has no hook line for a scheduler setting.

## Context

**User story**: a project depends on this package. On the Overview the user finds a Scheduler card saying the project's scheduler is on and what its last tick [7] decided, and a handle on the usage bar that sets how far past the quota boundary scheduled work may start. In the sidebar the user finds Automations: a page with one page row [8] per scheduled command of each project, saying what the command does, when it runs and what the scheduler last decided for it, with a checkbox (does it run on this machine) and, behind "Edit", when it runs on this machine (as its skill says, whenever there is work, or every so many minutes, hours, days, weeks or months, with a time of day beside days or more), how many agents may work on it at once (as its skill says, or up to a number) and a menu (how far its runs publish on this machine). Beside each project's name on that page the user finds "New automation": a form for a name, what the agent is told and when it runs (every so often, by a shell line that prints what is new, or both), with "Try it" to run the shell line once, a choice of who gets it, and Save, which writes the automation [11] into the project as a skill file the user commits, or, with "Only on this machine" picked, keeps it on this machine, with nothing to commit. On the page row of an automation saved that way the user finds "Edit prompt", which opens the same form holding the automation, its name fixed, to save it again with other words, and "Remove", which says what will be deleted and what of it can be brought back before it deletes anything. In Settings, after the dashboard's own sections, the user finds Scheduler: the same number as the usage bar's handle, as a typed value. A dashboard with no project depending on this package shows none of it.

**Business logic story**: the scheduler's settings are this machine's, in a file only this package's command reads and writes (`../src/state.ts`). The project's skills say which commands are scheduled, what each does and when each is due, the same for every machine; whether a scheduled command runs on this machine is its schedule switch [3], how often at most it starts here is its skill's interval until a person sets a pace pick [9], how many of its runs this machine lets be in flight at once is its skill's number until a person sets an agents pick [10], and how far its runs publish here is its publish pick [4], all four this machine's alone and one project's, so all four are on the Automations page, under the project's name. A shared automation [11] is no setting of this machine: it is a skill of the project, the same for every machine once its file is on origin's default branch, written into the person's own checkout by `agent-scheduler add`, written anew there by `agent-scheduler edit` and deleted there by `agent-scheduler remove` (`../src/automation.ts`), never by the module itself. An automation kept on this machine [11] is this machine's alone, like the four choices, but it is no part of the state: it is a file of its own beside it, written, written anew and deleted by the same commands. Either is made on the Automations page because that is where its command is then listed, with the same four choices as any other. The spend cushion [5] is one number for every project, so it is read as the loosest any project holds and saved to all of them, from the Settings page or the usage bar. The `open` and `close` lines that start and stop the scheduler with the dashboard are still hook lines of the dashboard's (`../src/init.ts`); nothing else of the scheduler is.

## Glossary

[1] module: a package that adds to the dashboard (pages, Overview cards, Settings sections, the usage bar's stop line, and more): its browser part, named by the package's `exports["./dashboard"]`, reads and saves its data through its own package's command. A module comes from a project's dependencies.
[2] the state: `.agent-scheduler/state.json` at the project's root, per user, hidden from git: on or off, keep-alive, the model, the spend cushion, this machine's schedule switches, pace picks, agents picks and publish picks, the scheduler's pid, the last tick's decisions and the schedule it read. `agent-scheduler status` prints it, plus whether the scheduler's process is alive.
[3] schedule switch: a person's choice, on one machine, whether a scheduled command (a command one of the project's skills schedules in the front matter of its `SKILL.md`, or an automation kept on this machine [11]) runs there; kept in the state, not in the skill. Every scheduled command is off on a machine until a person switches it on there.
[4] publish pick: a person's choice, on one machine, of how far a scheduled command's runs publish there: nothing, a commit, the branch, a pull request, or a pull request set to merge on its own once its checks pass; kept in the state, not in the skill. Until the person picks, the command's runs commit their work and push nothing.
[5] spend cushion: how far past the quota boundary (the share of the account's quota week that may be spent by now) a scheduled run may still start, in percentage points of the week; the state's `spendOffset`. Positive is lenient, negative is strict. The dashboard calls it the spend offset.
[6] stop line: where a module's unattended work stops on the Overview's usage bar, as an offset from the quota boundary in percentage points; the module reads the offset and saves a new one, the bar draws the line and its handle. This module's stop line is the spend cushion [5].
[7] tick: one pass of the scheduler, every minute: one decision per scheduled command, each one line in the state.
[8] page row: one line of the Automations page: one scheduled command of one project, with its checkbox and its "Edit". It is not a row of a skill's `schedule` key (the key in the front matter of its `SKILL.md` where the skill says which commands it schedules), which the module never reads.
[9] pace pick: a person's choice, on one machine, of a pace for one scheduled command there: "whenever there is work", or an interval with an optional time of day; kept in the state, not in the skill. A command with no pace pick runs at its skill's pace.
[10] agents pick: a person's choice, on one machine, of that machine's number for one scheduled command: the machine starts another run of the command only while fewer than that number are in flight on any machine that shares the repository. A whole number from 1 to 99; kept in the state, not in the skill. A command with no agents pick has its skill's number.
[11] automation: a person's own prompt saved as a scheduled command, with the `schedule` the person picked (the key where a skill says when its command is due), an interval, a check [12] or both. Written by `agent-scheduler add` or the "New automation" form of the Automations page, as one of two kinds, the person's choice. While its file reads as the tool writes one, the tool shows it, saves it again under its name and removes it (`agent-scheduler show`, `edit` and `remove`, or "Edit prompt" and "Remove" on the Automations page); an automation whose file was changed by hand into something the tool does not write is edited and removed by hand. A shared automation is a command skill of the project (a skill run as the slash command `/<name>`, never picked up by the coding agent on its own): the file `.claude/skills/<name>/SKILL.md`, whose text is the prompt and whose front matter carries that `schedule`; the person commits it, and from then on it is a skill like any other, and its command a scheduled command like any other. An automation kept on this machine is one file written the same way, `.agent-scheduler/automations/<name>.md`, in the tool's own folder, which is hidden from git: nothing is to commit and nobody else gets its command, though its text is in the record of each of its runs, which is shared where the project shares its records. It is no skill and no slash command: its command is listed, switched and started like any other scheduled command, a run of it has the automation's name as its prompt, with no slash, and is handed the file's text with it, its runs are counted on this machine alone (where a command's runs in flight or its last start are said to be counted on any machine, for it that is this machine's), and what is said of a command's skill (the interval and the check its skill gives, its skill's number of agents, what its skill says it does) is, for it, said of that file.
[12] check: the shell line a skill's `schedule` gives a scheduled command as `when`: the scheduler runs it in the project, every minute at most, while the command is switched on and the time between two of its starts has passed, when it has one, and starts an agent when it prints something. The automation form [13] calls it "a shell line".
[13] automation form: the form of the Automations page in which a person types an automation [11]. Opened by "New automation" beside a project's name, it is empty, is named "New automation" and saves a new automation. Opened by "Edit prompt" on a page row [8], it holds that page row's automation as its file says it, is named "Prompt of <the page row's name>" and saves that automation again under its name.

## Business logic — TL;DR

- **The module's definition** (`index.tsx`) - one page at `/automations`, labelled Automations with a calendar-and-clock icon; one Overview card, Scheduler, at order 90; one Settings section, Scheduler, at order 20; the usage bar's stop line [6], read as the loosest spend cushion [5] and saved to every project; and the stylesheet beside the module.
- **What is read and how it is saved** (`schedulers.ts`, `schedulers.test.ts`) - each project's scheduler as `agent-scheduler status` printed it, with each scheduled command's schedule switch [3] (on when the state holds the time it was switched on), pace pick [9], agents pick [10], publish pick [4] and last decision folded in, what its skill says it does, how many agents at once its skill allows, whether it is an automation kept on this machine [11] and whether it is an automation [11] the tool can show, save again and remove, the skills whose `schedule` key the last tick [7] could not read, and the automations kept on this machine it did not list; the loosest spend cushion; the save of the cushion to every project; and the words the page, the section and the card use: the scheduler's status, the name a page row [8] is written with (the command with its slash, or the name alone for an automation kept on this machine), a command's pace, how many agents at once, how far it publishes, what the scheduler last decided for it, and which publish picks a project is offered; and what the page's Edit box holds of a pace and of a number of agents while a person picks them.
- **The Automations page** (`AutomationsPage.tsx`, `AutomationsPage.test.tsx`) - one group per project under its name, with its scheduler's status, and one page row [8] per scheduled command: the command, written without its slash and followed by "only on this machine" when it is an automation kept on this machine [11], what its skill says it does, when it runs, how far its runs publish, what the scheduler last decided for it, and a checkbox for its schedule switch [3]; a page row whose pace is a person's own says "your pick", and one with more than one agent at once, or with an agents pick [10], says how many, with "your pick" after the number when it is the person's own; "Edit" opens the page row in place to save its pace pick [9], then its agents pick [10], then its publish pick [4], the box of an automation kept on this machine saying "As it was saved" where a skill's says "As the skill says"; read every 10 seconds; saves go one at a time, and a save not taken says why on its own page row; a scheduler that is off, or on with no live process, is said under the project's name; beside each project's name, "New automation" opens the automation form [13] below in that project, one form at a time on the page, no project offering the button while a form is open, none for a project that could not be read, and the page rows are read again once an automation [11] was saved; the page row of an automation the last tick recorded as one the tool can show, save again and remove has "Edit prompt" and "Remove", and no other page row has them: "Edit prompt" runs `agent-scheduler show` and opens the form in the page row, holding what the file says, or says on the page row why it could not be opened; "Remove" asks in the page row what is about to be deleted and what of it can be brought back, with the focus on "Cancel", then runs `agent-scheduler remove` as one of the saves that go one at a time, the page row gone at the next read and a note under the project's name saying what is left for the person to do, by what git still holds of the file, until they put it away; a form or a question whose page row is no longer listed is closed by the page.
- **The automation form** (`AutomationForm.tsx`, tested through `AutomationsPage.test.tsx`) - a name, what the agent is told, and when it runs: an interval that can be unticked, a check [12], and plain words for what the check waits for, then, for a new automation, who gets it, the project or this machine alone; one line saying what is missing or when the automation [11] would run; "Try it" runs the check once in the project with `agent-scheduler try`, for 20 seconds at most, and shows what it printed and whether an agent would start, the answer shown always being for the check as it stands and only the latest try's answer taken; "Save" runs `agent-scheduler add`, and a panel then says where the file is, what the person has to do with it (a shared automation is theirs to commit and has to get where its page row [8] can start; one kept on this machine needs nothing and can start as soon as it is switched on), and when the page row shows: within a minute where the project's scheduler is running, not yet where it is not; a save not taken says why and keeps what was typed; Cancel closes the form and saves nothing, and Escape closes only a form nothing was typed into; opened from a page row [8], the form is named "Prompt of <the page row's name>" and holds the automation as its file says it, the name cannot be changed, who gets it is not asked, a note says so where the person's own pace pick [9] stays in force over the pace typed, "Save" waits until the form says something else than the file, Escape closes the form only until then, and "Save" then runs `agent-scheduler edit` with every part the form holds, a part it does not hold as an empty flag that takes it out of the file, and the panel says that a shared automation is a change to commit, that an agent is told the new words only once the change is where an agent's checkout starts, that one kept on this machine needs nothing, and that its past runs, its switch and the person's picks stay.
- **The form as data** (`automation-form.ts`, `automation-form.test.ts`) - the draft a new form opens with (once a day, no check, shared with the project), the draft and the file read from what `agent-scheduler show` answered for an automation opened from its page row [8], nothing opening for an answer the form cannot show, what still keeps a draft from being saved, the first thing first, a prompt, a check or plain words longer than the 4000 characters the form can hand over among them, the words beside the interval, whether anything was typed into a draft yet, the words of `agent-scheduler add` for a draft, each text one argument together with its flag, `--private` last for a draft kept on this machine, the words of `agent-scheduler edit` for a draft opened from a page row, always all four flags, an empty one for a part the draft does not have, never with `--private`, whether such a draft says anything else than the one it opened on, the words that say where a draft is or will be saved, the sentence a draft's page row [8] would say for when it runs, what `agent-scheduler try` answered as a verdict for a person, and what `agent-scheduler add` answered: the file, whether the automation is kept on this machine, and what the person has to do with it, new or saved again; when the page row shows what was saved, by whether the project's scheduler is running; and what the page says before an automation is removed and, from what `agent-scheduler remove` answered, after.
- **The Scheduler section** (`SchedulerSettings.tsx`, `SchedulerSettings.test.tsx`) - "Spend offset" alone, the spend cushion [5] as a number saved to every project; read every 10 seconds; saves go one at a time; a save not taken says why; a project that cannot be read is named with the reason.
- **The Scheduler card** (`SchedulerCard.tsx`, `SchedulerCard.test.tsx`) - one card row per project: on, off or on but not running, keep-alive, the model, and the last tick's [7] decisions, a decision that started a run opening that agent; read every 10 seconds.
- **What the tests share** (`fixtures.ts`) - a fake dashboard host whose command answers what a test says, and what `status` prints for a scheduler that ticked once in a project whose skills schedule two commands.
- **Built to share, not to bundle** (`vite.config.ts`, `vitest.config.ts`, `vitest.setup.ts`, `dashboard.css`, `tsconfig.json`) - the module leaves React and `@openagt/dashboard/module` as bare imports the dashboard supplies, and its stylesheet holds only its own utilities, coloured by the dashboard's theme file; these files carry no business logic beyond that.
