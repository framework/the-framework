The `@openagt/agent-scheduler` package's module [1] for the dashboard: the Automations page, the Scheduler section of the Settings page, the Scheduler card of the Overview, and the stop line [6] on the Overview's usage bar. All four show what each project's scheduler keeps in its state [2], and all but the card change it, reading it with `agent-scheduler status` and saving with `agent-scheduler offset`, `switch` and `publish`, the same commands a person types. The package exports the module as `./dashboard` (`dist/dashboard/dashboard.js` and its stylesheet), which is how the dashboard finds it; the dashboard itself never names this package, reads no scheduler file and has no hook line for a scheduler setting.

## Context

**User story**: a project depends on this package. On the Overview the user finds a Scheduler card saying the project's scheduler is on and what its last tick [7] decided, and a handle on the usage bar that sets how far past the quota boundary scheduled work may start. In the sidebar the user finds Automations: a page with one page row [8] per scheduled command of each project, saying what the command does, when it runs and what the scheduler last decided for it, with a checkbox (does it run on this machine) and, behind "Edit", a menu (how far its runs publish on this machine). In Settings, after the dashboard's own sections, the user finds Scheduler: the same number as the usage bar's handle, as a typed value. A dashboard with no project depending on this package shows none of it.

**Business logic story**: the scheduler's settings are this machine's, in a file only this package's command reads and writes (`../src/state.ts`). The project's skills say which commands are scheduled, what each does and when each is due, the same for every machine; whether a scheduled command runs on this machine is its schedule switch [3], and how far its runs publish here is its publish pick [4], both this machine's alone and one project's, so both are on the Automations page, under the project's name. The spend cushion [5] is one number for every project, so it is read as the loosest any project holds and saved to all of them, from the Settings page or the usage bar. The `open` and `close` lines that start and stop the scheduler with the dashboard are still hook lines of the dashboard's (`../src/init.ts`); nothing else of the scheduler is.

## Glossary

[1] module: a package that adds to the dashboard (pages, Overview cards, Settings sections, the usage bar's stop line, and more): its browser part, named by the package's `exports["./dashboard"]`, reads and saves its data through its own package's command. A module comes from a project's dependencies.
[2] the state: `.agent-scheduler/state.json` at the project's root, per user, hidden from git: on or off, keep-alive, the model, the spend cushion, this machine's schedule switches and publish picks, the scheduler's pid, the last tick's decisions and the schedule it read. `agent-scheduler status` prints it, plus whether the scheduler's process is alive.
[3] schedule switch: a person's choice, on one machine, whether a scheduled command (a command one of the project's skills schedules in the front matter of its `SKILL.md`) runs there; kept in the state, not in the skill. Every scheduled command is off on a machine until a person switches it on there.
[4] publish pick: a person's choice, on one machine, of how far a scheduled command's runs publish there: nothing, a commit, the branch, a pull request, or a pull request set to merge on its own once its checks pass; kept in the state, not in the skill. Until the person picks, the command's runs commit their work and push nothing.
[5] spend cushion: how far past the quota boundary (the share of the account's quota week that may be spent by now) a scheduled run may still start, in percentage points of the week; the state's `spendOffset`. Positive is lenient, negative is strict. The dashboard calls it the spend offset.
[6] stop line: where a module's unattended work stops on the Overview's usage bar, as an offset from the quota boundary in percentage points; the module reads the offset and saves a new one, the bar draws the line and its handle. This module's stop line is the spend cushion [5].
[7] tick: one pass of the scheduler, every minute: one decision per scheduled command, each one line in the state.
[8] page row: one line of the Automations page: one scheduled command of one project, with its checkbox and its "Edit". It is not a row of a skill's `schedule` key (the key in the front matter of its `SKILL.md` where the skill says which commands it schedules), which the module never reads.

## Business logic — TL;DR

- **The module's definition** (`index.tsx`) - one page at `/automations`, labelled Automations with a calendar-and-clock icon; one Overview card, Scheduler, at order 90; one Settings section, Scheduler, at order 20; the usage bar's stop line [6], read as the loosest spend cushion [5] and saved to every project; and the stylesheet beside the module.
- **What is read and how it is saved** (`schedulers.ts`, `schedulers.test.ts`) - each project's scheduler as `agent-scheduler status` printed it, with each scheduled command's schedule switch [3], publish pick [4] and last decision folded in, what its skill says it does, and the skills whose `schedule` key the last tick [7] could not read; the loosest spend cushion; the save of the cushion to every project; and the words the page, the section and the card use: the scheduler's status, a command's pace, how far it publishes, what the scheduler last decided for it, and which publish picks a project is offered.
- **The Automations page** (`AutomationsPage.tsx`, `AutomationsPage.test.tsx`) - one group per project under its name, with its scheduler's status, and one page row [8] per scheduled command: the command, what its skill says it does, when it runs, how far its runs publish, what the scheduler last decided for it, and a checkbox for its schedule switch [3]; "Edit" opens the page row in place to save its publish pick [4]; read every 10 seconds; saves go one at a time; a refused save says which and why.
- **The Scheduler section** (`SchedulerSettings.tsx`, `SchedulerSettings.test.tsx`) - "Spend offset" alone, the spend cushion [5] as a number saved to every project; read every 10 seconds; saves go one at a time; a refused save says which project and why; a project that cannot be read is named with the reason.
- **The Scheduler card** (`SchedulerCard.tsx`, `SchedulerCard.test.tsx`) - one card row per project: on, off or on but not running, keep-alive, the model, and the last tick's [7] decisions, a decision that started a run opening that agent; read every 10 seconds.
- **What the tests share** (`fixtures.ts`) - a fake dashboard host whose command answers what a test says, and what `status` prints for a scheduler that ticked once in a project whose skills schedule two commands.
- **Built to share, not to bundle** (`vite.config.ts`, `vitest.config.ts`, `vitest.setup.ts`, `dashboard.css`, `tsconfig.json`) - the module leaves React and `@openagt/dashboard/module` as bare imports the dashboard supplies, and its stylesheet holds only its own utilities, coloured by the dashboard's theme file; these files carry no business logic beyond that.
