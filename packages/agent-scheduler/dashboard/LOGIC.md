The `agent-scheduler` package's module [1] for the dashboard: the Scheduler section of the Settings page, the Scheduler card of the Overview, and the stop line [6] on the Overview's usage bar. All three show and change what each project's scheduler keeps in its state [2], reading it with `agent-scheduler status` and saving with `agent-scheduler offset`, `switch` and `publish`, the same commands a person types. The package exports the module as `./dashboard` (`dist/dashboard/dashboard.js` and its stylesheet), which is how the dashboard finds it; the dashboard itself never names this package, reads no scheduler file and has no hook line for a scheduler setting.

## Context

**User story**: a project depends on this package. On the Overview the user finds a Scheduler card saying the project's scheduler is on and what its last tick [7] decided, and a handle on the usage bar that sets how far past the quota boundary scheduled work may start. In Settings, after the dashboard's own sections, the user finds Scheduler: the same number as a typed value, and one row per scheduled command with a checkbox (does it run on this machine) and a menu (how far its runs publish on this machine). A dashboard with no project depending on this package shows none of it.

**Business logic story**: the scheduler's settings are this machine's, in a file only this package's command reads and writes (`../src/state.ts`). The tracked `agent-schedule.md` stays the team's default; a schedule switch [3] and a publish pick [4] sit on top of it for one machine. The spend cushion [5] is one number for every project, so it is read as the loosest any project holds and saved to all of them. The `open` and `close` lines that start and stop the scheduler with the dashboard are still hook lines of the dashboard's (`../src/init.ts`); nothing else of the scheduler is.

## Glossary

[1] module: a package that adds to the dashboard (pages, Overview cards, Settings sections, the usage bar's stop line, and more): its browser part, named by the package's `exports["./dashboard"]`, reads and saves its data through its own package's command. A module comes from a project's dependencies.
[2] the state: `.agent-scheduler/state.json` at the project's root, per user, hidden from git: on or off, keep-alive, the model, the spend cushion, this machine's schedule switches and publish picks, the scheduler's pid, the last tick's decisions and the schedule it read. `agent-scheduler status` prints it, plus whether the scheduler's process is alive.
[3] schedule switch: a person's choice, on one machine, whether a scheduled command (a line of the project's `agent-schedule.md`) runs there; kept in the state, not in the schedule. The schedule line is the default where nobody switched the command: on, unless the line says `off`.
[4] publish pick: a person's choice, on one machine, of how far a scheduled command's runs publish there: nothing, the branch, a pull request, or a pull request set to merge on its own once its checks pass; kept in the state, where it stands in for the level the command's schedule line says until the person takes it back.
[5] spend cushion: how far past the quota boundary (the share of the account's quota week that may be spent by now) a scheduled run may still start, in percentage points of the week; the state's `spendOffset`. Positive is lenient, negative is strict. The dashboard calls it the spend offset.
[6] stop line: where a module's unattended work stops on the Overview's usage bar, as an offset from the quota boundary in percentage points; the module reads the offset and saves a new one, the bar draws the line and its handle. This module's stop line is the spend cushion [5].
[7] tick: one pass of the scheduler, every minute: one decision per scheduled command, each one line in the state.

## Business logic — TL;DR

- **The module's definition** (`index.tsx`) - one Overview card, Scheduler, at order 90; one Settings section, Scheduler, at order 20; the usage bar's stop line [6], read as the loosest spend cushion [5] and saved to every project; and the stylesheet beside the module.
- **What is read and how it is saved** (`schedulers.ts`, `schedulers.test.ts`) - each project's scheduler as `agent-scheduler status` printed it, with each scheduled command's schedule switch [3] and publish pick [4] folded in; the loosest spend cushion; the save of the cushion to every project; and the words a row uses: the scheduler's status, a command's pace, how far it publishes, and which publish picks a project is offered.
- **The Scheduler section** (`SchedulerSettings.tsx`, `SchedulerSettings.test.tsx`) - "Spend offset" as a number, and one row per scheduled command of every project with a checkbox and a publish menu; read every 10 seconds; saves go one at a time; a refused save says which and why.
- **The Scheduler card** (`SchedulerCard.tsx`, `SchedulerCard.test.tsx`) - one row per project: on, off or on but not running, keep-alive, the model, and the last tick's [7] decisions, a decision that started a run opening that agent; read every 10 seconds.
- **What the tests share** (`fixtures.ts`) - a fake dashboard host whose command answers what a test says, and what `status` prints for a scheduler that ticked once with a two-line schedule.
- **Built to share, not to bundle** (`vite.config.ts`, `vitest.config.ts`, `vitest.setup.ts`, `dashboard.css`, `tsconfig.json`) - the module leaves React and `framework/module` as bare imports the dashboard supplies, and its stylesheet holds only its own utilities, coloured by the dashboard's theme file; these files carry no business logic beyond that.
