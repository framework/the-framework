The rules and the processes of `agent-scheduler`: the schedule [1] the project's skills bring and the due rule, the state [2] the tool keeps per user, the spend boundary [3] copied from OpenAgent, the pace [16] of a command and the pace pick [17] a person sets for it, the agents pick [18] a person sets for it, the runs [5] a command has, counted off the run records [4] across machines, the start point [20] of a run and whether a skill's file is on it, the tick's [8] decisions, the scheduler's process [9] and the command line. One run, its marker, its lock and the sweep [7] are `agent-runner`'s, which every run the tool starts is. Every file here has a `LOGIC.md` of its own.

## Context

**User story**: the user runs `agent-scheduler start` and switches on, for their machine, the scheduled commands they want with each one's schedule switch [14]; one agent per due command works the project in its own checkout [6], within the cap [10] and the quota [11]; a command whose skill they wrote in their own checkout starts no agent until the skill is on the start point [20], and says so when it is due; the user reads why nothing started in the state file, changes the model or the spend cushion for their machine, sets how often at most a scheduled command starts on their machine with its pace pick [17], sets how many agents may work on a scheduled command at once with its agents pick [18], turns a scheduled command off again for their machine, and stops the scheduler while the agents in flight finish.

**Business logic story**: the scheduler's process [9] (`scheduler.ts`) ticks every minute; a tick (`tick.ts`) reads the schedule (`schedule.ts`) and the state (`state.ts`), runs `agent-runner`'s sweep, counts each command's runs in flight and its last start off the run records (`records.ts`), asks `pace.ts` which pace [16] is in force for the command and from when it is due, runs the command's check with the time of that last start as `$LAST_RUN`, or the time the command was switched on on this machine when that is later, asks `start-point.ts`, for a command that would otherwise start a run, whether the command's skill's file is on the start point [20], and starts nothing when it is not, asks `agent-runner` whether the coding agent can start and itself the spend boundary (`quota-boundary.ts`), writes a marker through `agent-runner` and has `agent-runner` spawn the run with the state's model, the publish level [15] in force on this machine and, when a check started the run, what the check printed, as the run's attached text [19]. From there the run is `agent-runner`'s own process, which records itself and reclaims [12] its checkout. A person's shell reaches the scheduler through the command line (`cli.ts`). The branch's pull is the `agent-data` package's rule; the run, the record and the checkout are `agent-runner`'s, `logs`' and `branches`'.

## Glossary

[1] the schedule: all the scheduled commands of a project. A skill of the project brings its own with the `schedule` key in the front matter of its `SKILL.md`, called the skill's `schedule`. The tool reads the skills in the project's two skill folders, `.claude/skills` and then `.agents/skills`. A skill with no `schedule` key brings none. A command whose skill is only under `.agents/skills` is listed and never started: every scheduled run is on Claude Code, which reads a project's skills from `.claude/skills`. The skills are read as they are on disk in the person's own checkout: a command whose skill is not on the start point [20] is listed and not started until it is.
[2] the state: `.agent-scheduler/state.json` at the repository root, per user, hidden from git through the repository's exclude file: on or off, keep-alive, the model, the spend cushion, this machine's schedule switches [14], pace picks [17], agents picks [18] and publish picks, the scheduler's pid, the last tick's decisions and the schedule it read.
[3] spend boundary: the share of the account's quota week that has elapsed, as a percentage rising continuously with the clock; unattended work stands down once a quota window in force is used past the boundary plus the spend cushion.
[4] run record: the `logs` skill's record of a run on the `agent-data` branch: a card (`<id>.json`) and a diary (`<id>.jsonl`), written by `agent-runner`. Written twice, over the same file: as a marker before the agent exists, and with how it went when the run ends.
[5] run: one agent this tool starts: a detached process of `agent-runner` (`agent-runner run`), a checkout, one prompt to the coding agent, and a run record when it ends. Its id is the time it was minted, `2026-09-16T14-01-00-000Z`; the start on its record is the moment the tick turned to its command, before its check ran.
[6] checkout: an agent's own working copy of the project: a git worktree under the project's `.branches/` directory, named as its branch.
[7] sweep: `agent-runner`'s pass, run on every tick, that records and reclaims the runs of this machine whose process died, and only this machine's.
[8] tick: one pass of the scheduler: pull the `agent-data` branch, sweep, then one decision per scheduled command, each decision one line in the state.
[9] the scheduler's process: the tool's own process between `start` and `stop`, ticking every minute; the state holds its pid.
[10] cap: how many runs of one scheduled command a machine lets be in flight at once: the machine starts another run of the command only while fewer than its number are in flight on any machine that shares the repository. Its number is the agents pick [18] made on it, a person's own number for the command there, else the number the command's skill gives, 1 when the skill gives none.
[11] quota: the account's subscription allowance, as the coding agent reports it: a session window and a quota week, each with a percentage used.
[12] reclaim: removing a finished agent's checkout once its branch holds everything in it.
[13] command: a scheduled command, one command a skill schedules: the skill's folder name and at most one word the skill takes as its argument (`triage quick`), which the coding agent's harness expands from the slash command `/<name>`.
[14] schedule switch: a person's choice, on one machine, whether a scheduled command runs there; kept in the state, not in the skill. Every scheduled command is off on a machine until a person switches it on there. A switch that is on holds the time it was switched on.
[15] publish level: how far a run of a command publishes its work: `commit` (commit the work and push nothing), `branch` (commit it, push the branch and open no pull request), `pr` (commit it, push the branch and open its pull request) or `merge` (commit it, push the branch and open its pull request, set to merge on its own once its checks pass). A scheduled run's level is the publish pick a person made for its command on this machine, kept in the state: `commit` until they pick, and no level, so nothing is published, when they picked `nothing`.
[16] pace: how often at most a scheduled command starts, the one in force on a machine: this machine's pace pick [17] for the command, else the interval its skill gives; an interval (a count of minutes, hours, days, weeks or months), with a time of day when it has one. A command its check alone paces has no pace.
[17] pace pick: a person's choice, on one machine, of a pace for one scheduled command there: "whenever there is work", or an interval with an optional time of day; kept in the state, not in the skill. A command with no pace pick runs at its skill's pace.
[18] agents pick: a person's choice, on one machine, of that machine's number for one scheduled command: the machine starts another run of the command only while fewer than that number are in flight on any machine that shares the repository. A whole number from 1 to 99; kept in the state, not in the skill. A command with no agents pick has its skill's number.
[19] attached text: a text handed to a run's agent with the run's first prompt, apart from the prompt (`agent-runner run --attach`): the agent reads it after the prompt, and no later prompt of the run carries it. A run that a check started is handed what the check printed this way.
[20] start point: the commit a scheduled run's checkout starts from: origin's default branch (`origin/main`), or, in a repository with no remote, the commit the person's own checkout is on (`HEAD`). Never the files in a person's own checkout: a skill written there and not committed, or committed and not yet on origin's default branch, is not on the start point.

## Business logic — TL;DR

- **The names** (`names.ts`) - the state directory and file, the scheduler's log, the folder the coding agent of scheduled runs reads skills from (`.claude/skills`), the name of a skill's file, and the defaults: `opus`, the publish level `commit`, a spend cushion of half a day, a cap of 1, a tick every minute, 5 seconds at most for the fetch of origin's default branch that brings the start point [20] up to date before a tick starts a run, at most 8000 characters of what a check printed handed to the run it starts, a check's budget of one minute; the name a check reads the time of its command's last start under, `$LAST_RUN`; the rule for what a number of agents at once is, a skill's or a person's: a whole number from 1 to 99; and the rule for what a time is, in the state and on a run record: an ISO date and time.
- **The schedule** (`schedule.ts`, `schedule.test.ts`) - how a skill's `schedule` [1], in the front matter of its `SKILL.md`, names the skill's commands [13] (the skill's folder name, and at most one word after it for the skill), each with its check, its interval (`every: 6h`, in minutes, hours, days, weeks or months: at most that often, from the command's last start) or both, one plain line saying what the check waits for, and its cap [10] (`agents`); each command also carrying what its skill says it does, the `description` of the same front matter; which skills are read, from `.claude/skills` and then `.agents/skills`, each once, in name order, each command carrying the folder its skill was read from; the file a command's skill is, as a path from the repository root (`.claude/skills/triage/SKILL.md` for `triage quick`), which the tick looks for on the start point [20]; a skill whose `schedule` cannot be read gives no command and is named with the reason; a check's output says due when it is non-empty JSON; the time a check is given as `$LAST_RUN` is written in UTC to the whole second, the fraction dropped; a command's prompt is its slash command, and a run's prompt is counted under the scheduled command it names, else its first word; the attached text [19] of a run a check started is words saying what follows and why the run started, then what the check printed, cut when it is longer than 8000 characters, a last line then saying how much was printed and the time the check was given.
- **The state** (`state.ts`, `state.test.ts`) - the JSON file and its defaults, hidden from git on the first write, read as the default when missing or unreadable; a schedule switch [14] kept only for a command switched on, as the time it was switched on, every other command being off; a pace pick [17] per command, kept only where a person set one; an agents pick [18] per command, kept only where a person set one, and the cap [10] in force, that number else the skill's; a publish pick per command, `commit` where there is none; a scheduler ending clears only its own pid.
- **The pace** (`pace.ts`, `pace.test.ts`) - an interval (a count from 1 to 9999 and a unit, `m`, `h`, `d`, `w` of 7 days, `mo` of 30 days) and a time of day (`HH:MM`, only beside days, weeks or months) read from text; the pace [16] in force, this machine's pace pick [17] else the skill's interval; from when a command is due: the interval after its last start, or, with a time of day, that time on the day the interval's days after the day of its last start, a missed time being due once and a pace pick starting nothing before its first time of day, counted from when the pick was made or the command was last switched on with it.
- **The spend boundary** (`quota-boundary.ts`, `quota-boundary.test.ts`) - the reset prose read as an instant, the elapsed share of the week, the windows in force, the limit the cushion moves, and the one line that says why a run may not start.
- **A command's runs** (`records.ts`, `records.test.ts`) - the command a run counts for, read off its prompt against the schedule, for the runs `agent-runner` started only; a command's runs in flight and its last start, on any machine, a record whose start time is no time left out.
- **The start point** (`start-point.ts`, `start-point.test.ts`) - the start point [20] as git names it, origin's default branch, fetched first as a run's own checkout fetches it, waited for 5 seconds at most, with whether origin was reached, or `HEAD` in a repository with no remote; one tick's question whether a file is on it, the start point read and fetched the first time a tick asks and once only; a file is on a commit as a checkout of that commit would have it, a link on the way followed (a link to the skill's folder, a link for the whole skills folder, a link to the file), 8 links at most, a link whose target is not on the commit, that leaves the repository or that turns in a circle leading nowhere; a start point that cannot be read counts the file as there, so no command is held back.
- **The tick** (`tick.ts`, `tick.test.ts`) - one decision per skill whose `schedule` cannot be read, on every tick, then pull, sweep, and per command in order: its skill is in `.claude/skills`, the schedule switch [14], due by the pace [16] in force, the check (given the command's last start as `$LAST_RUN`, or the time it was switched on on this machine when that is later or it never started), due, the cap [10] in force, the command's skill's file is on the start point [20] (asked only now that a run would otherwise start, the start point fetched once per tick), the coding agent can start, the quota, not stopped meanwhile, the marker, the re-count, the spawn, the marker and the spawned run carrying, as the run's start, the moment the tick turned to the command, before its check ran, the marker and the spawned run carrying the publish level [15] in force on this machine, a run that a check started spawned with what the check printed as its attached text [19] and a run its pace alone started with none; every outcome's exact line; the schedule as read, each command with what its skill says it does and its skill's number of agents at once when that is more than one, on every tick record.
- **The processes** (`scheduler.ts`) - the tick wired to the real project, with one question per tick whether a file is on the start point [20], answered from the repository with git, and to `agent-runner` (its sweep, its readiness check, its markers, its spawn with the state's model and the publish level in force on this machine), `start`, `stop` (which leaves a keep-alive scheduler running when asked to) and `status`, and the loop that ticks every minute and, stopped, lets the tick in flight end without starting anything and clears only its own pid.
- **The dashboard's hooks** (`init.ts`, `init.test.ts`) - this tool's `open` and `close` lines written into the dashboard's `.openagent/hooks.yml` by `agent-runner`'s writer, so the scheduler starts when the dashboard opens and stops when it closes. The spend cushion, the schedule switches, the pace picks, the agents picks and the publish picks need no hook: the package's own dashboard part (`../dashboard/`) saves them through the command line.
- **The clean-up** (`cleanup.ts`, `cleanup.test.ts`) - what this tool left in a project removed, what a dashboard asks for by the declared `cleanup` kind when a project is removed with its files: `state.json` and `scheduler.log`, then `.agent-scheduler/` once it is empty, then the rule hiding the directory from git, only when no checkout of the repository still has one; anything else in the directory stays, and the project's skills are not touched; refused while the state names a live scheduler.
- **The command line** (`cli.ts`, `cli.test.ts`) - the twelve commands, `switch … on`, `publish`, `pace` and `agents` refused for a command no skill of the project schedules, with the reason when its skill's `schedule` cannot be read, `pace … work` refused for a command with no check, `switch … off`, `pace … skill` and `agents … skill` taken for any name, the same pace picked again keeping the time it counts from, `switch … on` writing the time the command is switched on, kept when it is already on, and counting a pace's time of day from then, JSON on stdout, a line on stderr, exit 0, 1 or 2, and the project found from inside a checkout.
- **The entry point** (`index.ts`) - re-exports everything a program or a dashboard imports.
- **A test helper** (`test-repo.ts`) - a throwaway project with an origin and an `agent-data` branch, and a writer of a skill under `.claude/skills` with a given front matter, for the tests.
