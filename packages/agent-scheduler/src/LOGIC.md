The rules and the processes of `agent-scheduler`: the schedule [1] the project's skills bring and the due rule, the state [2] the tool keeps per user, the spend boundary [3] copied from OpenAgent, the pace [16] of a command and the pace pick [17] a person sets for it, the agents pick [18] a person sets for it, the runs [5] a command has, counted off the run records [4] across machines, the start point [20] of a run and whether a skill's file is on it, a person's own automation [21], saved as a skill file of the project or kept on this machine, read back from its file, saved again under its name and removed, and a check [22] tried once before it is saved, the tick's [8] decisions, the scheduler's process [9] and the command line. One run, its marker, its lock and the sweep [7] are `agent-runner`'s, which every run the tool starts is. Every file here has a `LOGIC.md` of its own.

## Context

**User story**: the user runs `agent-scheduler start` and switches on, for their machine, the scheduled commands they want with each one's schedule switch [14]; one agent per due command works the project in its own checkout [6], within the cap [10] and the quota [11]; a command whose skill they wrote in their own checkout starts no agent until the skill is on the start point [20], and says so when it is due; the user reads why nothing started in the state file, changes the model or the spend cushion for their machine, sets how often at most a scheduled command starts on their machine with its pace pick [17], sets how many agents may work on a scheduled command at once with its agents pick [18], turns a scheduled command off again for their machine, and stops the scheduler while the agents in flight finish. A user who wants a scheduled command no skill of the project brings saves a prompt of their own as an automation [21] with `agent-scheduler add`, after running its check [22] once with `agent-scheduler try`: the project gets a skill file that is theirs to commit, and its command is listed, switched and started like any other. With `agent-scheduler add --private` the automation is kept on this machine instead: nothing is written into the project, nobody else gets its command, and its command is listed and switched like any other and can start as soon as it is switched on. A user who wants other words in an automation they saved reads it as it stands with `agent-scheduler show`, saves it again under its name with `agent-scheduler edit`, and deletes it with `agent-scheduler remove`; `edit` changes only the parts it is given and leaves the rest as the file says them. A skill of the project, and an automation whose file was changed by hand into something the tool does not write, are refused by all three and are edited and removed by hand.

**Business logic story**: the scheduler's process [9] (`scheduler.ts`) ticks every minute; a tick (`tick.ts`) reads the schedule (`schedule.ts`) and the state (`state.ts`), runs `agent-runner`'s sweep, counts each command's runs in flight and its last start off the run records (`records.ts`), asks `pace.ts` which pace [16] is in force for the command and from when it is due, runs the command's check with the time of that last start as `$LAST_RUN`, or the time the command was switched on on this machine when that is later, asks `start-point.ts`, for a command that would otherwise start a run, whether the command's skill's file is on the start point [20], and starts nothing when it is not (an automation kept on this machine [21] is no skill and is not asked about), asks `agent-runner` whether the coding agent can start and itself the spend boundary (`quota-boundary.ts`), writes a marker through `agent-runner` and has `agent-runner` spawn the run with its prompt (the command's slash command, or the name alone of an automation kept on this machine), the state's model, the publish level [15] in force on this machine and, when a check started the run, what the check printed, as the run's attached text [19]; a run of an automation kept on this machine is handed its text that way, before what a check printed. From there the run is `agent-runner`'s own process, which records itself and reclaims [12] its checkout. A person's shell reaches the scheduler through the command line (`cli.ts`). Five of its commands are no part of that loop: `add` has `automation.ts` write a person's automation [21], into the project as a skill file or, kept on this machine, into the tool's own folder, the file being `automation-file.ts`'s; `show` has it find the automation of a name, by asking the schedule whether the command is one the tool can show, save again and remove, and read it back from its file, which `automation-file.ts` takes for an automation only when the file reads as the tool writes one; `edit` has it lay a change over what the file says and write the file anew, and `remove` has it delete the file, after which the command line takes out of the state what this machine held for the command; the next tick reads the schedule from disk again each time; and `try` has it run a check [22] once through the tick's own runner. The branch's pull is the `agent-data` package's rule; the run, the record and the checkout are `agent-runner`'s, `logs`' and `branches`'.

## Glossary

[1] the schedule: all the scheduled commands of a project. A skill of the project brings its own with the `schedule` key in the front matter of its `SKILL.md`, called the skill's `schedule`. The tool reads the skills in the project's two skill folders, `.claude/skills` and then `.agents/skills`. A skill with no `schedule` key brings none. A command whose skill is only under `.agents/skills` is listed and never started: every scheduled run is on Claude Code, which reads a project's skills from `.claude/skills`. The skills are read as they are on disk in the person's own checkout: a command whose skill is not on the start point [20] is listed and not started until it is. An automation kept on this machine [21] is one more scheduled command, read from its own file under `.agent-scheduler/automations`, after the skills; being no skill, it is held to neither of those two rules.
[2] the state: `.agent-scheduler/state.json` at the repository root, per user, hidden from git through the repository's exclude file: on or off, keep-alive, the model, the spend cushion, this machine's schedule switches [14], pace picks [17], agents picks [18] and publish picks, the scheduler's pid, the last tick's decisions and the schedule it read.
[3] spend boundary: the share of the account's quota week that has elapsed, as a percentage rising continuously with the clock; unattended work stands down once a quota window in force is used past the boundary plus the spend cushion.
[4] run record: the `logs` skill's record of a run on the `agent-data` branch: a card (`<id>.json`) and a diary (`<id>.jsonl`), written by `agent-runner`. Written twice, over the same file: as a marker before the agent exists, and with how it went when the run ends.
[5] run: one agent this tool starts: a detached process of `agent-runner` (`agent-runner run`), a checkout, one prompt to the coding agent, and a run record when it ends. Its id is the time it was minted, `2026-09-16T14-01-00-000Z`; the start on its record is the moment the tick turned to its command, before its check ran.
[6] checkout: an agent's own working copy of the project: a git worktree under the project's `.branches/` directory, named as its branch.
[7] sweep: `agent-runner`'s pass, run on every tick, that records and reclaims the runs of this machine whose process died, and only this machine's.
[8] tick: one pass of the scheduler: pull the `agent-data` branch, sweep, then one decision per scheduled command, each decision one line in the state.
[9] the scheduler's process: the tool's own process between `start` and `stop`, ticking every minute; the state holds its pid.
[10] cap: how many runs of one scheduled command a machine lets be in flight at once: the machine starts another run of the command only while fewer than its number are in flight on any machine that shares the repository. Its number is the agents pick [18] made on it, a person's own number for the command there, else the number the command's skill gives, 1 when the skill gives none.
[11] quota: the account's subscription allowance, as the coding agent reports it: a session window and a quota week, each with a percentage used.
[12] reclaim: removing a finished agent's checkout once its branch holds everything in it.
[13] command: a scheduled command, one command a skill schedules: the skill's folder name and at most one word the skill takes as its argument (`triage quick`), which the coding agent's harness expands from the slash command `/<name>`. An automation kept on this machine [21] is a scheduled command too, named as its file, with no word after the name: no skill schedules it, and a run of it has that name as its prompt, with no slash, and is handed its text with it. Its runs are counted on this machine alone.
[14] schedule switch: a person's choice, on one machine, whether a scheduled command runs there; kept in the state, not in the skill. Every scheduled command is off on a machine until a person switches it on there. A switch that is on holds the time it was switched on.
[15] publish level: how far a run of a command publishes its work: `commit` (commit the work and push nothing), `branch` (commit it, push the branch and open no pull request), `pr` (commit it, push the branch and open its pull request) or `merge` (commit it, push the branch and open its pull request, set to merge on its own once its checks pass). A scheduled run's level is the publish pick a person made for its command on this machine, kept in the state: `commit` until they pick, and no level, so nothing is published, when they picked `nothing`.
[16] pace: how often at most a scheduled command starts, the one in force on a machine: this machine's pace pick [17] for the command, else the interval its skill gives; an interval (a count of minutes, hours, days, weeks or months), with a time of day when it has one. A command its check alone paces has no pace.
[17] pace pick: a person's choice, on one machine, of a pace for one scheduled command there: "whenever there is work", or an interval with an optional time of day; kept in the state, not in the skill. A command with no pace pick runs at its skill's pace.
[18] agents pick: a person's choice, on one machine, of that machine's number for one scheduled command: the machine starts another run of the command only while fewer than that number are in flight on any machine that shares the repository. A whole number from 1 to 99; kept in the state, not in the skill. A command with no agents pick has its skill's number.
[19] attached text: a text handed to a run's agent with the run's first prompt, apart from the prompt (`agent-runner run --attach`): the agent reads it after the prompt, and no later prompt of the run carries it. A run that a check started is handed what the check printed this way. A run of an automation kept on this machine [21] is handed the automation's text this way, before what its check printed.
[20] start point: the commit a scheduled run's checkout starts from: origin's default branch (`origin/main`), or, in a repository with no remote, the commit the person's own checkout is on (`HEAD`). Never the files in a person's own checkout: a skill written there and not committed, or committed and not yet on origin's default branch, is not on the start point.
[21] automation: a person's own prompt saved as a scheduled command [13], with the `schedule` the person picked, an interval, a check [22] or both. Written by `agent-scheduler add` or the "New automation" form of the Automations page, as one of two kinds, the person's choice. While its file reads as the tool writes one, the tool shows it, saves it again under its name and removes it (`agent-scheduler show`, `edit` and `remove`, or "Edit prompt" and "Remove" on the Automations page); an automation whose file was changed by hand into something the tool does not write is edited and removed by hand. A shared automation is a command skill of the project (a skill run as the slash command `/<name>`, never picked up by the coding agent on its own): the file `.claude/skills/<name>/SKILL.md`, whose text is the prompt and whose front matter carries that `schedule`; the person commits it, and from then on it is a skill like any other, and its command a scheduled command like any other. An automation kept on this machine is one file written the same way, `.agent-scheduler/automations/<name>.md`, in the tool's own folder, which is hidden from git: nothing is to commit and nobody else gets its command, though its text is in the record of each of its runs, which is shared where the project shares its records. It is no skill and no slash command: its command is listed, switched and started like any other scheduled command, a run of it has the automation's name as its prompt, with no slash, and is handed the file's text with it, its runs are counted on this machine alone (where a command's runs in flight or its last start are said to be counted on any machine, for it that is this machine's), and what is said of a command's skill (the interval and the check its skill gives, its skill's number of agents, what its skill says it does) is, for it, said of that file.
[22] check: the shell command line a skill's `schedule` gives a command [13] as `when`, run at the repository root on every tick [8]; its output says whether the command is due. It may read `$LAST_RUN`: the time of its command's last start, or the time the command was switched on on this machine when that is later.

## Business logic — TL;DR

- **The names** (`names.ts`) - the state directory and file, the scheduler's log, the folder of the automations kept on this machine [21] under the state directory, the folder the coding agent of scheduled runs reads skills from (`.claude/skills`), the name of a skill's file, and the defaults: `opus`, the publish level `commit`, a spend cushion of half a day, a cap of 1, a tick every minute, 5 seconds at most for the fetch of origin's default branch that brings the start point [20] up to date before a tick starts a run, at most 8000 characters of what a check printed handed to the run it starts, at most 32,000 characters for the text of an automation kept on this machine [21], a check's budget of one minute, and of 20 seconds for a check a person only tries; the name a check reads the time of its command's last start under, `$LAST_RUN`; the rule for what a number of agents at once is, a skill's or a person's: a whole number from 1 to 99; the rule for what a time is, in the state and on a run record: an ISO date and time; and the rules for the name of an automation [21]: lower-case letters, digits and dashes, starting with a letter or a digit, with no three dashes in a row, 64 characters at most.
- **The schedule** (`schedule.ts`, `schedule.test.ts`) - how a skill's `schedule` [1], in the front matter of its `SKILL.md`, names the skill's commands [13] (the skill's folder name, and at most one word after it for the skill), each with its check, its interval (`every: 6h`, in minutes, hours, days, weeks or months: at most that often, from the command's last start) or both, one plain line saying what the check waits for, and its cap [10] (`agents`); each command also carrying what its skill says it does, the `description` of the same front matter; which skills are read, from `.claude/skills` and then `.agents/skills`, each once, in name order, each command carrying the folder its skill was read from; a command marked as one the tool can show, save again and remove when it is a person's own automation [21] whose file reads as the tool writes one, a shared one only alone in a folder of `.claude/skills` that is no link, one kept on this machine only when its file is no link, the schedule being the one place that says so; the automations kept on this machine [21], read after the skills from `.agent-scheduler/automations`, in name order, each one command carrying its text, 32,000 characters at most, and one that is not listed (its file is badly named or cannot be read, a skill of the project has its name too, in which case that skill's commands are not listed either, its `schedule` is missing or cannot be read, it has several rows or a word, it has no text or too long a one) kept aside with the reason, marked as an automation; the file a command's skill is, as a path from the repository root (`.claude/skills/triage/SKILL.md` for `triage quick`), which the tick looks for on the start point [20]; a skill whose `schedule` cannot be read gives no command and is named with the reason; a check's output says due when it is non-empty JSON; the time a check is given as `$LAST_RUN` is written in UTC to the whole second, the fraction dropped; a command's prompt is its slash command, or its name alone, with no slash, for an automation kept on this machine, and a run's prompt is counted under the skill's command it names with a slash, else under the one its first word is, or, with no slash, under the automation kept on this machine whose name it is and nothing else, and under no command otherwise; the attached text [19] of a run a check started is words saying what follows and why the run started, then what the check printed, cut when it is longer than 8000 characters, a last line then saying how much was printed and the time the check was given; the attached text of a run of an automation kept on this machine is its text, then, when a check started the run, words saying so and what the check printed; a person who only tries a check is shown what it printed cut the same way.
- **The state** (`state.ts`, `state.test.ts`) - the JSON file and its defaults, hidden from git on the first write, read as the default when missing or unreadable; a schedule switch [14] kept only for a command switched on, as the time it was switched on, every other command being off; a pace pick [17] per command, kept only where a person set one; an agents pick [18] per command, kept only where a person set one, and the cap [10] in force, that number else the skill's; a publish pick per command, `commit` where there is none; everything held under one command's name taken out together, for a command saved anew under that name, the very same state answered when it holds nothing under the name; a command taken off the last tick's record, out of the schedule that tick read and out of what it decided, for an automation [21] removed since that tick or while it ran, the very same state answered when the record names no such command; the names given up before a tick, an automation kept on this machine [21] that the last tick listed and whose file is gone, and a name a skill and such an automation both have, one whose file is still there keeping what it was given also while it is not listed, and everything under such a name taken out, the commands that are that name and a word included; a scheduler ending clears only its own pid.
- **The pace** (`pace.ts`, `pace.test.ts`) - an interval (a count from 1 to 9999 and a unit, `m`, `h`, `d`, `w` of 7 days, `mo` of 30 days) and a time of day (`HH:MM`, only beside days, weeks or months) read from text; the pace [16] in force, this machine's pace pick [17] else the skill's interval; from when a command is due: the interval after its last start, or, with a time of day, that time on the day the interval's days after the day of its last start, a missed time being due once and a pace pick starting nothing before its first time of day, counted from when the pick was made or the command was last switched on with it.
- **The spend boundary** (`quota-boundary.ts`, `quota-boundary.test.ts`) - the reset prose read as an instant, the elapsed share of the week, the windows in force, the limit the cushion moves, and the one line that says why a run may not start.
- **A command's runs** (`records.ts`, `records.test.ts`) - the command a run counts for, read off its prompt against the schedule, for the runs `agent-runner` started only; a command's runs in flight and its last start, on any machine for a skill's command and on this machine alone for an automation kept on this machine [21], a record whose start time is no time left out.
- **The start point** (`start-point.ts`, `start-point.test.ts`) - the start point [20] as git names it, origin's default branch, fetched first as a run's own checkout fetches it, waited for 5 seconds at most, with whether origin was reached, or `HEAD` in a repository with no remote; one tick's question whether a file is on it, the start point read and fetched the first time a tick asks and once only; a file is on a commit as a checkout of that commit would have it, a link on the way followed (a link to the skill's folder, a link for the whole skills folder, a link to the file), 8 links at most, a link whose target is not on the commit, that leaves the repository or that turns in a circle leading nowhere; a start point that cannot be read counts the file as there, so no command is held back.
- **An automation's file** (`automation-file.ts`, tested through `automation.test.ts`) - what an automation [21] is made of as a person fills it in: a name, a prompt, an interval, a check [22] and one plain line saying what the check waits for; the skill file it becomes: the prompt as its text, the prompt's first line, cut at 150 whole characters, as what the skill says it does, the front matter that makes it a command, and the `schedule` the person picked; every text the person typed written as a quoted value in which whatever could end the value, the line or the front matter is an escape, three dashes in a row among them, since a coding agent's reader ends the front matter at the first three dashes anywhere; the check as a block, line for line, where a block holds it as typed, else quoted; a file read back as an automation: its interval, its check and its plain line from the `schedule` in its front matter and its prompt from the text after it, taken for an automation only when the file's third line is a description of one quoted text with nothing after it and the skill file written again from them is, but for that line, the file itself, character for character, so a skill somebody wrote and an automation changed by hand into something the tool does not write are none, while a description that says something else than the prompt's first line changes nothing; whether a skill's folder stands alone: a folder under `.claude/skills` that is no link, holding its `SKILL.md`, no link either, and nothing else but a `.DS_Store`; and whether a path is a file itself and no link.
- **An automation** (`automation.ts`, `automation.test.ts`) - why one cannot be saved: its name, a blank prompt, a `schedule` the tick's own reader cannot read, with that reader's reason, a file that would not read back as typed; the save, of one of two kinds: shared, `.claude/skills/<name>/SKILL.md` written into the person's own checkout, nothing committed, a write that fails leaving no empty folder; or kept on this machine, the same file written as `.agent-scheduler/automations/<name>.md`, the tool's folder hidden from git first; either refused when the name is taken, whatever its capitals, by anything in either skills folder of the project or by an automation kept on this machine; kept on this machine, refused for a prompt longer than 32,000 characters, and a write that fails leaving no empty folder either; answered with the file, where a run's checkout starts and, for one kept on this machine, that it is; the automation [21] of a name found by asking the schedule: only a command the schedule marks as one the tool can show, save again and remove is found, read from its file at that moment, and anything else is refused with one sentence saying why the tool leaves the name alone (the schedule lists nothing of that name, the schedule's own reason for an automation or a skill it could not list, a file changed by hand, a skill of the project); an automation saved again under its name: found first, a change laid over what its file says, a part given taking the place of the file's, a part taken out gone, a part left out staying, what a check waits for going out with the check, refused for what could not be saved new either, its file written anew, whole, where it is, beside the file first and then moved over it, so a write that fails leaves the automation as it was, its name and its kind unchanged, nothing committed and the state untouched; an automation removed: found first, its file deleted and the folder that held it alone, with a `.DS_Store` beside it, nothing committed and nothing git holds changed, answered, for a shared one, with what git still holds of the file, `committed`, `staged`, `nothing`, or `unknown` when git could not be asked; and a check tried once, run as a tick would run it but within 20 seconds, asking what is new since a day ago: whether it ran, whether an agent would start, what it printed, cut as a run is handed it, and that it took too long or the last line of its error.
- **The tick** (`tick.ts`, `tick.test.ts`) - one decision per skill whose `schedule` cannot be read, and per automation kept on this machine [21] that is not listed, on every tick, then pull, sweep, and per command in order: its skill is in `.claude/skills`, the schedule switch [14], due by the pace [16] in force, the check (given the command's last start as `$LAST_RUN`, or the time it was switched on on this machine when that is later or it never started, its input closed at once), due, the cap [10] in force, the command's skill's file is on the start point [20] (asked only now that a run would otherwise start, the start point fetched once per tick), the coding agent can start, the quota, not stopped meanwhile, the schedule switch [14] asked once more as it is at that moment, a command switched off or removed while the tick ran starting nothing, the marker, the re-count, the spawn, the marker and the spawned run carrying, as the run's start, the moment the tick turned to the command, before its check ran, the marker and the spawned run carrying the publish level [15] in force on this machine, a run that a check started spawned with what the check printed as its attached text [19] and a run its pace alone started with none; an automation kept on this machine [21] asked neither whether its skill is in `.claude/skills` nor whether it is on the start point, and its run spawned with its name as its prompt and its text as the first part of its attached text; every outcome's exact line; the schedule as read, each command with what its skill says it does, its skill's number of agents at once when that is more than one, a mark when it is an automation kept on this machine, and a mark when it is an automation [21] the tool can show, save again and remove, on every tick record.
- **The processes** (`scheduler.ts`) - the tick wired to the real project, which first takes out of the state what this machine gave an automation kept on this machine [21] whose file is gone, or whose name a skill has too, with one question per tick whether a file is on the start point [20], answered from the repository with git, with the question whether a command is still switched on, answered from the state read anew just before a run is marked, with its record written, answered and logged without the commands whose file went while the tick ran, an automation kept on this machine that went so giving up its switch and picks, and to `agent-runner` (its sweep, its readiness check, its markers, its spawn with the state's model and the publish level in force on this machine), `start`, `stop` (which leaves a keep-alive scheduler running when asked to) and `status`, and the loop that ticks every minute and, stopped, lets the tick in flight end without starting anything and clears only its own pid.
- **The dashboard's hooks** (`init.ts`, `init.test.ts`) - this tool's `open` and `close` lines written into the dashboard's `.openagent/hooks.yml` by `agent-runner`'s writer, so the scheduler starts when the dashboard opens and stops when it closes. The spend cushion, the schedule switches, the pace picks, the agents picks and the publish picks need no hook: the package's own dashboard part (`../dashboard/`) saves them through the command line.
- **The clean-up** (`cleanup.ts`, `cleanup.test.ts`) - what this tool left in a project removed, what a dashboard asks for by the declared `cleanup` kind when a project is removed with its files: `state.json` and `scheduler.log`, then `.agent-scheduler/` once it is empty, then the rule hiding the directory from git, only when no checkout of the repository still has one; anything else in the directory stays, the automations kept on this machine [21] among it, and the directory with them, their folder going too once nothing is in it, and the project's skills are not touched; refused while the state names a live scheduler.
- **The command line** (`cli.ts`, `cli.test.ts`) - the seventeen commands, `switch … on`, `publish`, `pace` and `agents` refused for a name the project's schedule holds no command of, with the reason when its skill's `schedule` cannot be read, and in an automation's own words when it is one kept on this machine that is not listed, `pace … work` refused for a command with no check, `switch … off`, `pace … skill` and `agents … skill` taken for any name, the same pace picked again keeping the time it counts from, `switch … on` writing the time the command is switched on, kept when it is already on, and counting a pace's time of day from then, `add` saving an automation [21], shared with the project or, with `--private`, kept on this machine, taking out of the state what this machine held under its name and writing the state only when it held something, and refused with why for a name that is taken, by a skill of the project or by an automation kept on this machine, a name that is no command's, a blank prompt and a `schedule` that could not run as written, `show` answering an automation as its file says it, `edit` saving it again under its name, a flag given replacing that part, a flag left out leaving it, a schedule flag given empty taking it out, no flag at all a usage error, and leaving the state as it is, `remove` deleting its file, taking out of the state what this machine held for the command and taking the command off the last tick's record, the state written only when there is something to take out, all three refused, in one sentence saying why, for a name the schedule does not mark as such an automation, `try` answering what a check [22] printed and whether an agent would start, a check that fails being an answer and not a failure of the command, JSON on stdout, a line on stderr, exit 0, 1 or 2, and the project found from inside a checkout.
- **The entry point** (`index.ts`) - re-exports everything a program or a dashboard imports.
- **A test helper** (`test-repo.ts`) - a throwaway project with an origin and an `agent-data` branch, and a writer of a skill under `.claude/skills` with a given front matter, for the tests.
