What the tests cover, on the file-only commands against a real repository (the commands that spawn or talk to Claude are covered by their modules; running and checking a run are `agent-runner`'s):

- **`status`, `model`, `offset`, `stop`** - `status` answers the default state with `running: false`; `model` and `offset` write the state and answer it; `stop` answers the state off; every answer is one JSON object with `ok`; from a subdirectory the same command still acts on the project.
- **`stop --unless-keep-alive`** - with keep-alive on and the scheduler's pid being the test's own process, the command signals nothing, leaves the state as it is, answers it with `kept: true` and says `keep-alive is on, the scheduler keeps running` on stderr; with keep-alive off it turns the state off like `stop`; a plain `stop` turns a keep-alive state off too.
- **Usage errors and refusals** - no command, an unknown command (`run` and `check` among them: they are `agent-runner`'s), a missing argument, an offset that is not a number, an extra argument (to `status` or `init`), a `switch` with one argument, a `switch` to a value neither `on` nor `off`, a `publish` with one argument, and a `publish` to a word that is no pick (`push`, `file`) each exit 2 with the usage on stderr and nothing on stdout; outside a repository `status` exits 1 with `{"ok":false,"reason":"not-a-repo"}` and `not inside a git repository`.
- **`switch`** - in a project whose one skill schedules nothing, switching `work-queue` on is refused `not-scheduled` with `no skill of this project schedules work-queue` on stderr; once the project's skills schedule `work-queue`, `triage quick` and `triage consensual`, switching `triage quick` and `work-queue` on keeps both in the state as `true`, switching off `triage consensual`, which nobody switched on, changes nothing, and switching both off again leaves no `switches`; `triage` alone, the name of a skill whose scheduled commands each carry a word, is refused `not-scheduled`; once the skill's `schedule` holds a typo, switching `triage quick` on is refused `unreadable-schedule` with the skill, the reason (`unknown key evry`) and `the schedule of triage cannot be read: unknown key evry` on stderr, and `publish` for it says the same on stderr; the switch left on for `triage quick` is still switched off, leaving no `switches`; and switching off a name no skill ever had exits 0.
- **`publish`** - in a project whose one skill schedules nothing it is refused `not-scheduled`; once the project's skills schedule `work-queue` and `triage quick`, picking `nothing` for one and `pr` for the other keeps both publish picks in the state; picking `commit`, what a command nobody picked for gets anyway, is kept all the same; a name no skill schedules (`triage-quick`) is refused `not-scheduled` with `no skill of this project schedules <name>` on stderr.
- **`pace`** - in a project whose skills schedule `work-queue`, by a check, and `triage quick`, every 6 hours:
  - `pace "triage quick" 2d` keeps the interval with no time of day and records the time it counts from; `2w 9:05` replaces it and keeps the time of day as `09:05`; the same `2w 09:05` again keeps the time the pick counts from, and `2w 10:00` records a new one; `work` for `work-queue` is kept as "whenever there is work"; `skill` for each takes the pick back and leaves no `paces` in the state.
  - With the state edited by hand to hold null for one command and plain text for the other, an interval for each is taken.
  - With "every day at 10:00" picked for `triage quick`, `switch "triage quick" on` keeps the interval and the time of day and moves the time they count from to the switch; switching it on again while it is on moves nothing; `switch … off` leaves the pace pick as it is; switching on `work-queue`, which has no pace pick, writes no `paces`.
  - `work` for `triage quick`, which has no check, is refused `no-check` with `triage quick has no check, so nothing would say when there is work` on stderr; an interval for `triage` alone is refused `not-scheduled`, and a refusal writes nothing.
  - Once the skill's `schedule` holds a typo, a new interval for `triage quick` is refused with `the schedule of triage cannot be read: unknown key evry` on stderr, while `skill` still takes the pick back; `skill` for a name no skill ever had exits 0.
  - A missing value, a word that is no pace (`often`), `0h`, `10000d`, a time that is none (`25:00`), a time beside hours, a time beside `work`, and a fourth argument each exit 2 with nothing on stdout; a time beside hours says `a time of day goes with days, weeks or months`.
- **`agents`** - in a project whose skill schedules `work-queue`: `agents work-queue 3` keeps 3 in the state and answers it; `1` replaces it and is kept, since one is a pick too; `099` is kept as 99, the top; `skill` takes it back and leaves no `agents` in the state; a number for `triage`, which no skill schedules, is refused `not-scheduled`; `skill` for a name no skill ever had exits 0; once a `triage` skill's `schedule` holds a typo, a number for `triage` is refused with `the schedule of triage cannot be read: unknown key evry` on stderr; a missing value, `0`, `1.5`, `-2`, `many`, `100` and a third argument each exit 2 with nothing on stdout; `many` says `many is neither skill nor a whole number from 1 to 99`; a usage error writes no `agents`.
- **`tick` with the scheduler off** - the branch is pulled, nothing is decided, the answer's note is `off`, the answer lists the command the project's skill schedules (its name, its check and what its check waits for), and the state remembers the tick.
