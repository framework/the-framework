The names the tool hangs off, and its defaults. The tool's own directory is `.agent-scheduler` at the repository root, hidden from git by the tool itself; in it, the state [2] is `state.json`, `scheduler.log` is the scheduler's process's own log (a spawned run's lock and stderr are `agent-runner`'s, under `.agent-runner/`), and the folder `automations` holds the automations kept on this machine [6], one file each, `<name>.md`, written like a skill's file: being under the tool's own directory, they are never tracked by git and never in a run's checkout. The coding agent every scheduled run is on, Claude Code, reads a project's skills from `.claude/skills`: a skill that is only in another folder is no command to it. A skill's file is `SKILL.md` in the skill's folder: its front matter is where the skill says what it adds to the schedule [1]. The defaults: a scheduled run starts on `opus` when the state names no model; a run of a command [3] publishes at the level `commit`, so it commits its work and pushes nothing, on a machine where nobody picked a level for that command; the spend cushion is 100/14 percentage points, half a day of the week's allowance, the cushion OpenAgent's daemon used; a command for which neither its skill nor a person names a number runs 1 at a time, its cap [4]; a number of agents at once, a skill's or a person's, is a whole number from 1 to 99, and anything else is no such number (0, a fraction, 100, text): the one rule the state, the skill reader, the command line and the dashboard part all read; a tick that is about to start a run waits 5 seconds at most for origin's default branch to be fetched, which brings the start point [5] up to date before the tick asks whether the command's skill is on it (`start-point.ts`): the wait a run's own checkout gives the same fetch; a started scheduler ticks every 60 seconds; a run that a command's check started is handed at most 8000 characters of what the check printed; the text of an automation kept on this machine [6] is 32,000 characters at most, since it reaches its run as one command-line argument, a longer one is refused when it is saved (`automation.ts`) and not listed when it is there all the same (`schedule.ts`); a command's check may run 60 seconds before it counts as failed; a check that a person only tries (`automation.ts`) may run 20 seconds, less than a tick gives one and less than the 30 seconds a dashboard waits for the answer of a command it runs; a check reads the time of its command's last start in the environment variable `$LAST_RUN`; a time, as the tools write one, is an ISO date and time that a date reads (`2026-10-09T10:00:00.000Z`): what the state holds for a command that is switched on, and what the start time on a run record is; anything else is no time (`true`, `"on"`, a number, and text a date would read loosely, `1`, `2026`, `October 9`): the one rule the state, the count of a command's last start and the dashboard part all read; a text can name an automation [6] when it is lower-case letters, digits and dashes, starting with a letter or a digit, with no three dashes in a row (`a--b` is a name, `a---b` is none): three dashes in a row end a skill file's front matter for a coding agent wherever they stand, in the name as anywhere; and the name of an automation is 64 characters at most, being a folder's name and a command a person types for a shared automation [6], and a file's name for an automation kept on this machine [6]: the two rules the save of an automation (`automation.ts`) and the dashboard part's "New automation" form both read.

## Glossary

[1] the schedule: all the scheduled commands of a project. A skill of the project brings its own with the `schedule` key in the front matter of its `SKILL.md`, called the skill's `schedule`. An automation kept on this machine [6] is one more scheduled command, read from its own file.
[2] the state: `.agent-scheduler/state.json` at the repository root, per user, hidden from git through the repository's exclude file.
[3] command: a scheduled command, one command a skill schedules: the skill's folder name and at most one word the skill takes as its argument, which the coding agent's harness expands from the slash command `/<name>`. An automation kept on this machine [6] is a scheduled command too, named as its file, with no word after the name: no skill schedules it, and a run of it has that name as its prompt, with no slash, and is handed its text with it. Its runs are counted on this machine alone.
[4] cap: how many runs of one scheduled command a machine lets be in flight at once: the machine starts another run of the command only while fewer than its number are in flight on any machine that shares the repository. Its number is the agents pick made on it, a person's own number for the command there, else the number the command's skill gives, 1 when the skill gives none.
[5] start point: the commit a scheduled run's checkout starts from: origin's default branch (`origin/main`), or, in a repository with no remote, the commit the person's own checkout is on (`HEAD`). Never the files in a person's own checkout: a skill written there and not committed, or committed and not yet on origin's default branch, is not on the start point.
[6] automation: a person's own prompt saved as a scheduled command [3], with the `schedule` the person picked, an interval, a check (a shell line whose output says whether the command is due) or both. Written by `agent-scheduler add` or the "New automation" form of the Automations page, as one of two kinds, the person's choice. A shared automation is a command skill of the project (a skill run as the slash command `/<name>`, never picked up by the coding agent on its own): the file `.claude/skills/<name>/SKILL.md`, whose text is the prompt and whose front matter carries that `schedule`; the person commits it, and from then on it is a skill like any other, and its command a scheduled command like any other. An automation kept on this machine is one file written the same way, `.agent-scheduler/automations/<name>.md`, in the tool's own folder, which is hidden from git: nothing is to commit and nobody else gets its command, though its text is in the record of each of its runs, which is shared where the project shares its records. It is no skill and no slash command: its command is listed, switched and started like any other scheduled command, a run of it has the automation's name as its prompt, with no slash, and is handed the file's text with it, its runs are counted on this machine alone (where a command's runs in flight or its last start are said to be counted on any machine, for it that is this machine's), and what is said of a command's skill (the interval and the check its skill gives, its skill's number of agents, what its skill says it does) is, for it, said of that file.
