What the tests cover, one run end to end on a real repository with the coding agent faked. Every line of a recorded diary a test reads is checked to carry its time as an ISO 8601 timestamp:

- **A run that commits** - the marker, the checkout under `.branches/` for the run's id, the live card mid-run (`running`, the intent, the birth branch, the mark with the pid and the host, the workspace), the branch the agent renamed and the pull request read back from the git host for that branch, the cost, the record (`done`, branch, pull request, cost, model, driver, the session id and the mark under `caller`) with a diary of the prompt, what the agent said, its result, the cost and the end, and the checkout reclaimed once the branch is on origin.
- **A run that commits nothing** - `done`, no pull request, the checkout and its empty branch gone.
- **A driver that throws** - `failed` with the error as the detail, on the outcome, the card and the diary's last line.
- **The tick's run** - a given id and "already marked" writes no second marker and still records the run; a dirty tree keeps the checkout with the reason `dirty`.
- **A signal mid-run** - SIGINT to the run's process while the agent works: the session is aborted, the outcome, the card and the diary's last line say `stopped` with the detail `stopped by a signal to its process`, what the agent said before is kept, and the checkout is reclaimed.
- **A question, then the answer** - a run whose last turn asked ends `waiting`, keeps its checkout, and records the session id; resuming it with the answer starts the session by that id, sends the continuation prompt naming the question and the answer, goes on in the same record (the same id, the original start time, the diary continued after the `waiting` end), ends `done` and reclaims the checkout.
- **A line in the inbox** - a message appended to the inbox during the first turn becomes the run's second turn, in the same record.
- **A line written as the run ends** - a message appended to the inbox after the last turn took it, while the card still said running (as the pull request is read back), is sent by the same process as a further turn of the same session before the run ends: one record, `done`, the diary two rounds of start, said, result and end, the second one's prompt the message, and the checkout reclaimed.
- **A signal while the run records and reclaims** - SIGINT to the run's process after the agent's last turn is ignored: the process lives on, the run ends `done` as it ended, recorded so, and the checkout is reclaimed.
- **A run with a follow-up** - the first agent's prompt ends with the line not to arm the merge while the record keeps the bare prompt; the record's mark names the follow-up; a fresh run with its own id, on the coding agent made for that id, works the first run's branch in a checkout of its own id with the prompt `/post-merge-cleanup <first run's id>`, without that line, and sees nothing merged while it works; its record has its own intent and a mark with no follow-up; its commit is on the same branch, pushed; once it ends done the first run's pull request is merged once through the git host, and its checkout is reclaimed.
- **A follow-up that fails** - the first run is `done`, the follow-up `failed` with no merge: nothing merged. A run that opened no request starts no follow-up.
- **A run with a follow-up that ends waiting** - its agent was told not to arm the merge, and no follow-up yet; the answer resumes it with the same line, and once it ends done the follow-up runs with the first run's id and the request is merged once.
- **A run with a follow-up continued after its checkout went** - a first run that opened no request ends `done` with no follow-up and its checkout reclaimed; resumed, it gets a new checkout and the line not to arm the merge again, publishes, and its follow-up runs, the request merged once, after the follow-up.
- **The git host by declaration** - with a package declared in the project's `package.json` as the git host (its own `package.json` names the `git-host` kind), a run reads its branch's pull request through that package's command, and the follow-up's end merges through it: the command sees `requests --branch <branch>` once per run and `merge <number>` once.
- **A resume waits for the run's lock** - while another live process holds the run's lock, a resume of a `waiting` run does not start the coding agent and the record stays `waiting`; once the lock is let go, the resume goes on and ends `done`.
- **A run holds its lock while the agent works** - mid-turn, the lock names the run's process, and a sweep on the same machine records nothing, reclaims nothing and keeps nothing: the live card still says `running` and the checkout is still there; once the run has answered, the lock is gone.
