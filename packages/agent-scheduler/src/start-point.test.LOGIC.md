What the tests cover, against real git repositories: a project with an origin whose default branch, `main`, tracks the skill `.claude/skills/work-queue`, a second clone of that origin, and repositories with no remote:

- **Written, committed, on origin** - asked for the tracked skill's file, the answer is the start point [1] `origin/main`, origin reached, the file there; the file of a skill written in the person's own checkout is not there; neither is it once committed there and not pushed; once `main` is pushed to origin it is. The folder of a skill is not a file on the commit, and neither is a file the folder does not hold: only the skill's `SKILL.md` counts.
- **Brought up to date, once for a whole tick** - another clone puts one skill on origin's `main` and takes the tracked one off. This clone's own copy of the branch, not fetched, still has the old skill. One tick's question then answers that the new skill's file is there and the removed one's is not, origin reached both times, with one fetch for the two questions, of the default branch alone.
- **Origin that cannot be reached** - with the origin gone, the start point is `origin/main`, origin not reached; the question still answers, from the copy this clone last saw: the file of a skill written in the person's own checkout is not there, the tracked skill's file is, each answer saying origin was not reached.
- **Links on the way to the file** - a skill kept under `.agents/skills` and linked from `.claude/skills` is there under both paths; a `SKILL.md` that is itself a link to a file on the commit is there; a link whose target was never committed, a link that leaves the repository and two links pointing at each other lead nowhere, and the file is not there. In a repository whose whole `.claude/skills` folder is a link to `.agents/skills`, a skill under `.agents/skills` is there through the link, and a skill that folder does not hold is not.
- **No remote** - in a repository with no remote and no commit yet, whether a file is on `HEAD` has no answer, and the question says the start point is `HEAD`, reached, the file there: nothing is held back; after a first commit that holds a skill, that skill's file is there; the file of a second skill, written and not committed, is not.

## Glossary

[1] start point: the commit a scheduled run's checkout starts from: origin's default branch (`origin/main`), or, in a repository with no remote, the commit the person's own checkout is on (`HEAD`). Never the files in a person's own checkout: a skill written there and not committed, or committed and not yet on origin's default branch, is not on the start point.
