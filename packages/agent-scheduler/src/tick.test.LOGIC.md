What the tests cover, with every reading injected (the wiring to a real project is `scheduler.ts`'s) and, unless a test says otherwise, every command switched on on this machine and its skill read from `.claude/skills`:

- **This machine's pace** - with three commands last started 20 minutes ago and no pace pick, the one whose skill says 15 minutes starts and the two whose skills say 6 hours are `not due (last start 20m ago, every 6h)`; with this machine's pace picks, the first, slowed to one hour, is `not due (last start 20m ago, every 1h)` and its check never runs, the second, set to "whenever there is work", asks its check alone and starts, and the third, set to 10 minutes, starts; the recorded schedule still lists each skill's own interval.
- **A pace with a time of day** - with "every 2 days at 10:00" and a last start on the 14th at 10:02: on the 16th at 09:00 the command is `not due (next start from 2026-09-16 10:00, every 2d at 10:00)` and no check runs; on the 16th at 10:00 its check runs and it starts; with the scheduler not running on the 16th, on the 17th at 08:00 the missed time is due and it starts; having started then, on the 17th at 10:05 it is `not due (next start from 2026-09-19 10:00, every 2d at 10:00)`.
- **A start** - a due command under its cap with quota to spare gets a running marker (the prompt `/<command>`, the state's model, `agent-runner`'s mark with this host and, nobody having picked a publish level here, `commit`), is spawned with the same id and `commit`, and the decision is `started <id>` with the run's id.
- **A publish pick** - with this machine picking `nothing` for one command and `merge` for a second, and nobody picking for a third, the first marker's mark names only this host and its run is spawned with no level, the second carries `merge`, the third `commit`; the recorded schedule lists what the skills say (the name, the check or the interval, what the check waits for, and what the skill says it does for the command whose skill says) and no publish level.
- **An interval** - a command never started is due and its check decides; a start younger than the interval is `not due (last start 2h ago, every 6h)` (`1m` for a minute) with no check run and no marker written; a start older than the interval is due again.
- **A word after the folder** - for `triage quick` and `triage consensual`, with only `triage quick` switched on here, the first starts and the second is `switched off on this machine`; the decisions, the spawn and the recorded schedule carry the whole name; the marker's prompt is `/triage quick`; with both switched on, a last start under `triage consensual` holds that command alone (`not due (last start 1d ago, every 7d)`) while `triage quick` starts.
- **A schedule switch** - with nobody switching, every command is `switched off on this machine`, no check runs, and the tick records the schedule as the skills say it (the name, the check or the interval); with this machine switching one command on, that one starts and the other stays switched off, its check not run; a switch written by hand that is not `true` is off.
- **Off** - the pull and the sweep still run, no check runs, the note is `off`.
- **A failed pull** - the note is `agent-data could not be pulled: <error>` and nothing is spawned.
- **No scheduled command** - with no skill scheduling a command, the note is `no skill of this project schedules a command` and the recorded schedule is empty.
- **The order of the checks** - a command whose skill was read from `.agents/skills` is `not a command of the coding agent: its skill is only under .agents/skills, not .claude/skills`, with no check run and nothing spawned, and it says so even while the command is switched off on this machine; `check failed: <last stderr line>`; `not due`; `cap reached (1 in flight: <id> on <host>)` without reading the quota or writing a marker; `quota: <window> is 90% used, at or past day 4 of the week's N%` with nothing spawned.
- **A coding agent that cannot start** - with two due commands, each decision is `not ready: <the problem>`, the readiness is read once, the quota is not read and no marker is written; a command at its cap is decided before the readiness is read.
- **An unreadable quota** - `quota: the quota could not be read, so there is no way to tell what is spare`.
- **Two machines** - a marker ranked past the cap by an earlier id that landed meanwhile is withdrawn with `cap reached (…)` naming the other; with a cap of two the marker within the cap keeps its place; a marker whose push failed twice is withdrawn with `another machine got there first: …` and nothing spawned.
- **Skills whose `schedule` cannot be read** - a skill whose `schedule` cannot be read is named with `unreadable schedule: <reason>` while the readable command still starts; with no readable command at all, the skill is still named and the tick has no note; with the state off the skill is named all the same beside the note `off`, and so it is when the pull failed.
- **One quota read per tick** - two commands start on one reading.
- **A stop during the tick** - a tick told the scheduler was stopped writes no marker and spawns nothing, with the line `not started: the scheduler was stopped`; the readings before it still ran.
