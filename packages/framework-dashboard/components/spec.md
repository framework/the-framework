The view layer: ~75 components, almost entirely wiring over `lib/`'s decisions. Vendored primitives (`ui/` — hand-ported shadcn Base UI variants; `animate-ui/`) need no documentation.

## TLDR

Clusters:
- **Shell** — sidebar/history rail, brand, theme, notifications bell, error boundary (the net under a no-SSR app — a render error otherwise unmounts to a blank root), and a dependency-free Markdown renderer that builds React nodes and **never injects HTML**, so agent-written content cannot smuggle markup.
- **Overview** — usage/quota bar (draggable spend slider), Human Queue, agents working now, AI Queue (every project's `TODO_AGENTS.md` in full — a collapsed plan is one you cannot read; a row's play button starts one agent on that one **raw line**, because the agent must match it to check it off), routine work (the list *is* the daemon's own catalog import, so screen and daemon cannot disagree; opting **out** is what's stored, so a later-added routine runs for people who saved earlier), hot tickets, onboarding checklist (every "done" is derived from a real fact — a step cannot be ticked by clicking, and one done outside the dashboard shows ticked anyway).
- **Session view** — `RunView` is one component for live *and* finished runs (two components swapping on status used to remount at the exact moment you were reading). Its hard part is channel-vs-archive arbitration: an *empty* archive never replaces the feed (empty means both "gone" and "not archived yet", and Stop races the archive write); a *stale* archive never wins over a resumed run's live leg; "the channel knows more" is trusted only when both read the **same journal** (fingerprinted by first event), because an ended run's channel resolves to the project-root journal, which may hold a longer foreign feed. Around it: the feed (inline choice panels with an autopilot countdown cancelled by mouse movement), changed files + diffs (read from **git in the run's worktree**, never from the agent's tool calls — git is honest about outcome vs intent; the server hands over real git patches, the client only colours lines), the handoff panel (branch-addressed, survives worktree removal), the browser panel (MJPEG in an `<img>` — the browser is the player; a still frame is kept so an ended run degrades to a picture), and the cloud/actions/remote notices for runs whose work is elsewhere.
- **Composer** — one shared surface (editor + presets + context + agent/model + options gear + submit slot). A synchronous latch sits beside the async busy state because two fast ⌘↵ both read stale state and fired two starts. In-session it is three-valued: live (gear hidden — options were baked at spawn), ended-resumable (resume-relevant options only), launcher (everything). `StartRunForm` owns pre-flight warnings *before* the run is spent (untrusted project for a web run, missing `gh` when a publish rung is armed, a model known to skip the finish protocol, repo auto-merge disabled) and builds options through the daemon's own mapping so submit and preview cannot disagree. `RunComposer` has three send behaviors (live → queued message; ended-with-session → resume the same run; ended-without → new run, said in the placeholder) and two deliberate latches (stop is released on liveness change, not run-id change — resume keeps the run id; a resuming window covers the gap between the RPC and the first event). The prompt editor is a Tiptap tokenizer whose chips serialize to the **exact plain text the agent parses** (raw, unescaped), with one suggestion plugin per trigger character and chip deletion undoing the context focus it added.
- **Project home / settings / tickets** — launcher + open questions (every session's parked gate in one place; auto-accept countdown deliberately off — a hub rendering every gate must not mass-accept), settings (writes the **global** tier only, because `/settings` carries no project id; device rows say on-screen that they are *not* preferences), tickets pages (cross-project; import/update button prompts read from the presets rather than being restated, so one label cannot mean two behaviors).
