The dashboard's client-side logic: routing, data plumbing, live-run derivation, preferences/options, and the pure formatting helpers. This is where the package's real behavior lives — components mostly render what these modules decide.

## TLDR

- **Routing** (`route.ts`, `use-route.ts`): parse/format are inverses; reserved words (`settings`, `tickets`, `plan`) are safe by construction because real project ids always carry a hash suffix, run ids derive from start times, and ticket slugs are filenames. Reads the live pathname, not baked route params (the shell is prerendered for `/`); `go()` no-ops when already there, `replace` is for corrections only.
- **Data plumbing** (`use-async.ts`, `use-action.ts`, `use-runs.ts`, `use-daemon-health.ts`, …): one loaded/polled hook pattern instead of twelve hand-rolled copies. A rejected read keeps the last value rather than blanking (an empty usage bar reads as "nothing used"); `loaded` flips only on success and resets on dep change, which is how callers tell "gone" from "not fetched yet"; a liveness token retires in-flight reads on dep change and unmount.
- **Live-run derivation** (`use-live-events.ts`, `live-state.ts`, `run-status.ts`, `event-times.ts`): the one streaming subscription, per **run** (changing runs resubscribes to that run's own journal), with reconnect backoff and — crucially — **buffered replay swapped in atomically** on the server's sync marker or a grace deadline, so a mid-run reconnect never blanks the feed while history restreams. `live-state.ts` is pure selectors over the event list (pending choices keyed by gate id and expired by `end`; "active"/"outcome" ask the current segment only, because a resumed session carries its earlier segment's end in the same journal; "the agent parked on you" is distinct from "the process exited"; a "publishing…" window between a clean end and the handoff report). Status is one exclusive ranked pill shared by all surfaces so they cannot drift.
- **Preferences & options** (`preferences.ts`, `run-option-rows.ts`, `profiles.ts`, `remote-target.ts`, `draft-handoff.ts`): a module-scoped external store, three tiers resolved nearest-wins (global file ← repo yml ← project), writes split by key (project-overridable keys imported from the framework so there is no second copy) and sending **only changed keys** — a long-open tab used to replay stale values over someone else's change. The option table is pure data rendered by two surfaces; `checked` is the *effective* value, so no surface can claim an option is on while the run ignores it; the publish ladder (push → PR → merge) makes the contradictory states unrepresentable, with merge default-off because publishing is reversible and landing on the default branch is not. Device profiles are localStorage on purpose — "a device I have" is a *connection* (switching navigates the browser to that daemon's origin), and its token is a per-browser secret that must never reach the daemon's registry. Typed drafts move out of the URL into sessionStorage at boot so a prompt never sits in history or a Referer.
- **Pure helpers**: date formatting through a parse guard (unparseable input once rendered the literal string "Invalid Date"); the quota bar's week math re-derives local midnights each step so DST doesn't slide boundaries; queue-entry parsing takes only a *leading* link as the title; the resume command re-creates the (removed) worktree directory because the CLI matches sessions by directory; notification identity is imported from the framework so browser and Discord notifiers agree, with the first observations absorbed as baseline so page load never flushes a backlog.
