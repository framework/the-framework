What the tests cover:

- **One backlog across projects** - every registered project's tickets are read and listed under that project's own name, one section each; a project with no ticket still shows its own "Update from GitHub" button rather than a dead end; with no project registered the page says so ("No projects registered yet.") instead of showing an empty list.
- **Opening a row** - clicking a ticket's title opens that ticket's page addressed by the ticket's own project and file name, in a project section and in the flat list alike.
- **Importing from a section** - an import started from one project's section reports that project, its prompt and the started agent's id, so the dashboard can show the new agent.
- **The default order** - the page keeps the order the daemon sends, newest first, and does not reorder it.
- **Sorting** - choosing "Priority" from the sort menu puts the highest priority first and writes `?sort=priority` into the address; two tickets of the same priority fall back to newest first rather than an arbitrary order.
- **Searching** - typing in the search box narrows the rows and writes `?q=` into the address; the count beside the heading reads `2/2` unfiltered and `1/2` once one row is hidden.
- **The address is the initial state** - opening the page at an address that already carries a filter starts filtered, with the non-matching rows absent.
- **Click-to-filter from a row** - a row's topic badge adds that topic to the filter (`?topics=dx`); a badge whose topic is capitalized filters by its lowercase form (`UX` writes `?topics=ux`) and keeps its own row shown; a row's claim marker narrows to claimed tickets (`?stage=claimed`).
- **Filtered down to nothing** - a project whose tickets are all hidden reads "2 tickets hidden by the current filters" and offers "Clear filters" there and then, and does not offer "Update from GitHub", because those tickets exist and are merely hidden; clearing empties the address's query string and brings the rows back.
- **The flat cross-project list** - `group=none` renders one list ordered across projects (a priority 9 ticket of one project above a priority 2 ticket of another), each row carrying its own project's name, and no per-project "Update from GitHub" bar.
- **Starting from a flat row** - "Start work on …" starts a prompt agent in that row's own project, unattended, with the ticket named as `tickets/<file>` and that file named in the prompt, then reports the started agent under that same project.
- **"Configure first, then run" from a flat row** - lands on that row's own project's launcher, not on the first project listed, starts no agent, and leaves the row's work prompt waiting as a draft for the composer.
- **Queueing the shown tickets** - "Add all 2 tickets shown below to the AI queue" adds one entry per shown ticket to that ticket's own project's agent queue, the ticket's title as the entry, the ticket named so the entry links back, and the ticket's priority carried when it has one; no agent is started; the button then reads "Queued" and is disabled, and arms again the moment the shown set changes, counting the new set ("Add the ticket shown below to the AI queue").
- **Never queued twice** - a ticket an open queue entry already links to is skipped, even when the entry carries an agent's own note after the link; an entry that is checked off does not count as queued, so its ticket is added.
- **Claimed tickets are left alone** - a claimed ticket is never queued, and the label counts only what the click adds ("Add the one unclaimed ticket shown below to the AI queue").
- **No offer when there is nothing to offer** - with every ticket hidden by the filters, or with every shown ticket claimed, neither the queue button nor the plan button appears.
- **Queueing plans** - "Queue plans for all 2 tickets shown below" adds one plan ask per shown ticket, carrying the ticket's priority so the entry lands in its section; it adds no implementation entry and starts no agent; the button then reads "Plans queued" and is disabled.
- **Which tickets still need a plan** - tickets already planned and tickets claimed are skipped, and the label counts what is left ("Queue a plan for the one unplanned ticket shown below"); a ticket whose plan ask is already an open entry, recognized by its exact `Create tickets/<stem>.plan.md` text, is skipped, and so is a ticket already queued for implementation.
- **All planned already** - with every shown ticket planned, no plan button appears while the queue button still offers.
- **Selection scopes the queue buttons** - every row carries a checkbox; ticking rows shows "2 selected" and makes both heading buttons speak for and act on the selection only ("Add the 2 selected tickets to the AI queue", "Queue a plan for the selected ticket"), leaving the rest of the shown set untouched; changing the selection re-arms a rested button for the new set.
- **Clearing the selection** - "Clear selection" removes the readout and hands both buttons back to the whole shown set.
- **A claimed ticket in the selection** - is still skipped, and the label counts without it ("Add the one unclaimed selected ticket to the AI queue").
- **A selected ticket the filters hide** - is neither counted in the readout nor acted on, the buttons speak for the shown set again, and the tick itself survives the filter and comes back with its row.
- **Selecting in the flat list** - works the same way, and each selected row is queued on its own project.
