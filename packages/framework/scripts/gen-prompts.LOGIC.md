Compiles every prompt an agent [1] receives, authored as markdown under `packages/framework/prompts/`, together with the `SKILL.md` of three skills [2], into one generated module of plain string constants, `src/prompts.generated.ts`, which is what the product's code imports. The markdown is the only source of truth: the generated module is ignored by git and rebuilt on every build, test and type check, so it can never drift from the prompts.

## Context

**User story**: the user sees, before an agent starts, the exact prompt the agent will receive, rendered in the dashboard; and a change to what agents are told is reviewed as a readable markdown diff, never as a change to code.

**Problem**: the dashboard renders the built-in system prompt [3] and the presets in the browser, where no file can be read from disk; and the published package ships only its build output, not the prompt files. A module of strings crosses both boundaries, while reading the markdown at run time would break the browser build.

## Glossary

[1] agent: the unit of work: one task worked by a coding agent under The Framework's control, in its own checkout, on its own branch, streaming events, handed off when it ends.
[2] skill: one of the four capabilities an agent is taught (`branches`, `tickets`, `queue`, `logs`), each a package with the instructions the agent reads (its `SKILL.md`), a command on the agent's PATH, and an API the product calls.
[3] the built-in system prompt: the standing instructions every agent starts with (`prompts/system_prompt.md`).

## Business logic — TL;DR

- **What is compiled** - every `.md` under `prompts/` except `README.md` and any `LOGIC.md`, plus the `SKILL.md` of the `tickets`, `queue` and `logs` skills with their front matter dropped.
- **How a file becomes a constant** - the file's exact bytes minus one trailing newline, under a name derived from its path, in a stable order and encoded so that no character of a prompt is ever altered.
- **The markdown is the only source of truth** - the generated module is ignored by git, marked "Do not edit", and regenerated by every build, test, type check and development watch.

## Business logic

### What is compiled

#### Context

See `## Context`. The three skills' texts ride along because an agent [1] running outside a checkout The Framework created has no skills [2] linked into it: `prompts/tickets_yourself.md` is followed by the skills' own texts, so the formats come from one place, the skill packages, and are never copied into a prompt. The `branches` skill is not among them, since `prompts/branch_yourself.md` replaces it entirely for such an agent.

#### Business logic

The sources are, in this order:

1. Every file ending in `.md` anywhere under `prompts/`, recursively, except `README.md` and any file whose name ends in `LOGIC.md`: those are documentation for humans, not prompts. The files are sorted by path so the output is the same on every machine.
2. The `SKILL.md` of the `tickets` skill [2], then of the `queue` skill, then of the `logs` skill, each read from wherever the skill's package is installed. Their leading front matter block, the skill catalog's metadata, is dropped: it is not instructions.

A skill package that cannot be found stops the generation, and with it the build that ran it.

### How a file becomes a constant

#### Context

**Problem**: the prompts contain backticks and `${{ ... }}` template fragments, exactly the characters a hand-written string escape corrupts silently; a corrupted prompt would reach the agent [1] without anyone noticing.

#### Business logic

Each source becomes one exported constant holding the file's exact bytes minus exactly one trailing newline: the files end with one so they are well-formed on disk, the prompts they carry do not.

A prompt file's constant is named after its path under `prompts/`: drop the `.md`, replace every run of characters that is not a letter or a digit by one underscore, and uppercase the result, so `presets/security_audit.md` becomes `PRESETS_SECURITY_AUDIT` and adding `foo/bar.md` adds `FOO_BAR`. The three skills' constants are named `TICKETS_SKILL`, `QUEUE_SKILL` and `LOGS_SKILL`.

Every text is encoded as a JSON string, never as a template literal, so backticks and template fragments pass through unaltered; the output is not meant to be read by anyone. Each constant carries a comment naming its source file. The module starts with a header stating that it is generated, must not be edited, and is rebuilt on every build, test and type check.

When it finishes, the script prints how many prompts it compiled and where, as "[gen-prompts] <count> prompts -> src/prompts.generated.ts".

### The markdown is the only source of truth

#### Context

**Problem**: a prompt kept in two places, the markdown and a copy in code, drifts as soon as one is edited without the other; a generated copy that is rebuilt before every use cannot.

#### Business logic

The generated module is listed in the repository's git ignore rules, so it is never committed. It is regenerated by the framework package's `build`, `test`, `typecheck` and `dev` scripts, each of which runs this script right after building the skill and driver packages and before compiling anything that imports the prompts; the package's `clean` script deletes it, and `gen:prompts` regenerates it alone. Editing the markdown and running any of those is therefore the whole procedure for changing what an agent [1] is told.
