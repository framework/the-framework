# Bug analysis: packages/framework/src/daemon-services.ts

## Business logic (high-level)

Wires every background service onto the daemon's one clock (E4) and encodes the rules self-starting work obeys. Checked against `daemon-services.SPEC.md`:

- **One clock, fixed job list**: order matches the spec exactly — worktree sweep first (its start-up turn must land before the daemon owns agents), branch links, data sync (before auto PM so a same-tick sweep reads the freshly pulled queue), CI watch, Discord watchers, auto PM, cloud scratch sweep, cloud work adoption. Cadences: `AUTO_PM_EVERY = round(600000/30000) = 20` ticks (10 min), data sync/CI/Discord every 2 (≈1 min), cloud scratch `120` (hourly). All match the spec's stated cadences.
- **Unattended forced, not read**: all three run-starters (auto-PM `start`, CI `fix`, and by extension the wake paths) go through `startUnattended`, which overlays `unattended: true` on top of resolved options + extras, so no starter can forget it (#846).
- **Quota measured for the model that would run** (#1619): `quotaFor` resolves the *same* options as the start and asks `boundaryFor(options.model)`; both self-starting gates use it. The CI fix resolves before reading the meter and logs a stand-down once per `<cwd>\0<pr>\0<headSha>` (in-memory, so a restart says it once more — documented).
- **Auto PM wiring**: preference and opt-outs read per tick; queue passed as entries (per-drain pinning, #1204); active slots passed as labels via `describeSlot`; maintenance schedule persisted in the checkout; routine locks minted/released with both outcomes logged and dead-lock release guarded by "a run of this machine started since is still going" (`startedAt >= since` — ISO strings, lexical order is chronological, both sides same format); plan candidates = unplanned ∧ unlocked, priority-desc (non-numeric priority ranks lowest); the daemon (never the agent) writes/pushes ticket locks; drain locks skip only on existing locks; `releaseLock` only for the known-dead `no-commits` case.
- **Promote/check-off (#1582/#1583)**: not settled while the agent is unknown or `running`; `handoffSkip` and `handoffPending` (only for `done` with no report — "still publishing") ride along; published requires `done` ∧ (`handoffReport === 'done'` ∨ `handoffSkip === 'already-open'`); the check-off is a funneled data-branch write of `checkOffEntry`; a write that neither succeeded nor committed stays unsettled and is retried; `promoted: result.ok ? result.changed : true` — the `: true` branch is only reachable when `committed` is true (the earlier guard returns otherwise), i.e. the entry did land locally. All per spec.
- **CI watch**: merge half ungated (inside ci-watch.ts); fix half gated on `autoPm` preference per attempt + headroom, starts with `handoff: 'local'` (must not push/open on the red PR's branch). Per spec.
- **Discord (#1095/#627)**: one group keyed by the credentials; `reloadDiscord` chains rebuilds on one promise (two saves cannot interleave start/stop), checks `stopped`, logs failures; watchers are passive (`poll` driven by the clock job over `discordWatchers`), preference checked at post time, baseline seeded by the first whole read (in `SeenTracker`), delivery failures logged. Start-up goes through the same reload path (`void reloadDiscord()`), unawaited by design.
- **Data sync (#1599)**: `syncProjectData` sets or unconditionally clears the project's `data-sync` error by outcome.
- **Quiesce**: `stopped = true`, `await clock.stop()` (waits out the in-flight turn at a job boundary), then stops Discord and every service. Ordered before the daemon suspends agents (daemon.ts calls it first). One theoretical race noted, not reported: a `reloadDiscord` whose chain already passed the `stopped` check when quiesce runs can rebuild watchers *after* `stopDiscord()` — but the clock is stopped so nothing ever polls them, `KeyedWatcher` owns no timer (E4), and nothing leaks; the window is a single awaited registry read wide.

## Functions (low-level)

- `AUTO_PM_EVERY` / `CLOUD_SCRATCH_EVERY` — exact integer ratios of the verified constants. Correct.
- `syncProjectData(path, errors, log)` — `pullDataBranch` result → clear or set `data-sync`. Relies on `pullDataBranch` returning results rather than throwing (it does); a throw would surface as the tick job's logged failure, leaving a stale error at worst one tick. Correct.
- `listSummaries` / `readPrefs` — registry reads with `catch → []` / `{}` fallbacks (defaults are what a run would use anyway). Correct.
- `resolveProjectAgentOptions(id, env)` — global prefs, then the project's `the-framework.yml` mapped via `preferencesFromFileConfig`, folded through `agentOptionsFromPreferences`. Unknown id → file tier skipped (home is always registered by the daemon, so the home lookup resolves). Exported for continuation starts (#1467). Correct.
- `describeSlot(slot)` — id or "a run in the project checkout"; `(starting)` vs `(pid N)`. `pid` is always set for live slots by the producer. Correct.
- `startBackgroundServices(deps)` — the wiring analyzed above. `startUnattended` ordering `{...options, ...extra, unattended: true}` lets a job's `handoff: 'merge'`/`'local'` override the project tier while `unattended` overrides everything. `quotaFor` re-resolves options per call (registry + yml read per gate — a few reads per tick, accepted). Auto-PM `start` derives the ticket for drains from the pinned entry (fallback: first open queue entry) and for plan fan-outs from `job.ticket`, sets `planAgent` only for non-drain ticketed jobs, `handoff: 'merge'` only when `job.autoMerge`. `releaseDeadLocks` filters running agents to this hostname before comparing. `startDiscord`'s stop closure resets `discordWatchers` only if still the same array. `wakeAutoPm` forwards opts and swallows rejections while still resolving when the tick does (#1433). `autoPmReport` passthrough. Correct.
