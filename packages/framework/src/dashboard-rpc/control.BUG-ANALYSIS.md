# Bug analysis: packages/framework/src/dashboard-rpc/control.ts

## Business logic (high-level)

The write side of the dashboard, per `control.SPEC.md`:

- **Steering is a file** (`sendStop`/`sendChoice`/`sendMessage`/`sendSetHandoff`/`sendMerge` on a running agent): one `ControlEntry` appended to the checkout the agent id resolves to (`resolveAgentPath`: live meta cwd → worktree dir → project root), which is the file the agent tails. Verified against `agent-addressing.test.ts`: worktree agents get their own channel, the #766 no-meta-yet worktree still resolves, no-worktree ids fall back to the root. `appendControlFor` no-ops when the project is unknown (relay/read-only host) — matching "only a host that owns the workspace writes".
- **Relay** (#1067): every agent-scoped action goes through `relayOr` — local when `contextRemote().target(agentId)` is empty (also the device side, by `context.ts` design), forwarded otherwise; actions that report an outcome return `could not reach the device` on relay failure, while void steering returns undefined. Relayed args are the *raw* inputs (`sendMessage` forwards untrimmed `text`), and the device side re-runs the same function, so validation (trim, `isHandoffLevel`) is re-applied where the write happens. Consistent.
- **Start** (`sendStart`): throws on an unwired context (D3, by design); requires a non-empty prompt except for `research`; resolves the queue-ticket server-side (`ticketForStart` via `ticketForPrompt`, catch→undefined) with an explicit `options.ticket` winning — exactly what `control.test.ts` pins. `kind` is typed but not runtime-validated; it flows to the daemon's own start (the same trust boundary as every other option the browser sends, and the spec routes everything through the daemon's start anyway). Noted, not a bug.
- **Publish** (`sendPushBranch`/`sendOpenPullRequest`): resolve the target (`handoffTargetFor`: project + `isSafeAgentId` + `findAgent`), commit-then-push/open **inside `withAgentLock(target.checkout)`** — the same key teardown locks (`worktreePath` == live meta cwd for a worktree agent), covering both the commit race and the push-vs-teardown ref race the comments document. A failed commit reports `could not commit…` instead of publishing a partial result. `sendOpenPullRequest` records the opened PR onto the archive via `patchArchivedAgentOnDataBranch` only when `ok && number !== undefined && url` — the E6 write. Correct. (`handoffTargetFor`'s `?? cwd` on `resolveAgentPath` is dead — the store's resolution never returns undefined for a known project — harmless.)
- **Merge** (#1391): running → control entry; else direct `mergeAgentPr`; the end-between-check-and-write race is accepted and documented (second click gets the direct merge). Matches the SPEC verbatim.
- **Bridge** (#1237): `sendBridgeAnswer` gates on a strict session-id shape and non-empty string labels, then defers to the store's own label validation (`queueAnswer` returns an error string for labels not offered); `sendBridgeAnswerCancel` is a silent no-op on bad ids/delivered answers. Local only, never relayed. Matches.
- **Worktree removal** (`sendRemoveWorktree`/`sendDeleteAgent` via `withWorktreeRemoval`): local-path-required, then the shared `removeProjectWorktree`/`deleteProjectAgent` under `withAgentLock(worktreePath(cwd, agentId))` — unsafe ids are refused inside those (pinned by tests), and locking an out-of-tree key for a garbage id is harmless (in-process map). **But the "stop the preview first" story is dead** — see Bugs.
- **Queue writes** (`sendQueueTicket`/`sendQueueTicketPlan`/`sendReleaseTicketLock`): trim/`isTicketFile` gates before any project resolution, priority-section placement, link-back only for implementation entries (the plan ask deliberately is not a link, with the reader-semantics rationale), release reported as `released`/`no-lock`/commit-failure. Matches SPEC and tests.
- **Open in app** (`sendOpenInApp`): agent checkout when named, stored editor preference honored (`contextPreferences()?.read().catch(...)` — the `?.` is dead since the accessor throws rather than returning undefined; style only). Matches.

## Functions (low-level)

- **`appendControlFor(projectId, entry, agentId?)`** — resolve + append (`appendControl` mkdirs first). Unknown project → silent no-op (spec'd). Correct.
- **`sendStop` / `sendChoice` / `sendMessage` / `sendSetHandoff`** — relay-or-append; `sendMessage` drops empty-after-trim before even relaying; `sendSetHandoff` validates the rung locally (and again on the device). Correct.
- **`sendBridgeAnswer` / `sendBridgeAnswerCancel`** — shape gates + store delegation. Correct.
- **`withWorktreeRemoval(projectId, agentId, remove)`** — shared body; passes `beforeRemove: async () => {}` (see Bugs). Correct behaviorally.
- **`sendRemoveWorktree` / `sendDeleteAgent`** — thin wrappers over the shared removal implementations (#982/#1032). Correct.
- **`sendStart(projectId, prompt, kind, options)`** — analyzed above. Correct.
- **`ticketForStart`** — unknown project → undefined; lookup failure → undefined. Correct.
- **`sendOpenInApp`** — analyzed above. Correct.
- **`handoffTargetFor`** — undefined for unknown project/unsafe id/unknown agent. Correct.
- **`sendPushBranch` / `sendOpenPullRequest` / `sendMerge`** — analyzed above. Correct.
- **`sendReleaseTicketLock` / `sendQueueTicket` / `sendQueueTicketPlan`** — analyzed above. Correct.

## Bugs found

1. **L136–138, L157, L165–166 (and `control.SPEC.md` L90, `dashboard-rpc/SPEC.md` L80, `daemon.ts` L260): the promised "stop the preview serving the checkout before removal" does not exist — stale spec/docs and dead plumbing.** The doc comments on `sendRemoveWorktree`/`sendDeleteAgent` say the one thing this layer adds is stopping a dev-server preview before the directory goes, and both SPECs state it as behavior ("Before the directory comes off disk, a preview serving that checkout is stopped"). In code, `withWorktreeRemoval` passes `beforeRemove: async () => {}` — a no-op — and the app-preview feature has been removed from the product entirely: no preview RPC exists anywhere (`sendPreview`/`sendStopPreview` are gone; `FEATURES-SPEC.md` lists no preview; `ProjectRuntime.dispose` only drops relay state; `daemon-runtime.ts`'s `projectKeyFor` "preview key" helper is dead code). So nothing can be serving the checkout and the no-op is behaviorally harmless — but the SPECs describe behavior the system does not have, and the explicit no-op `beforeRemove` argument plus the doc paragraphs exist only to keep that fiction alive, in a project whose rules demand SPECs match reality (sdd) and no leftover code. Scenario: a reader (or agent) implementing against `control.SPEC.md` assumes removals coordinate with a preview subsystem that is gone. Severity: minor (spec/doc drift + dead parameter). Fix: drop `beforeRemove` from the `withWorktreeRemoval` call (it is optional in `worktrees.ts`), delete the preview sentences from the two doc comments, from `control.SPEC.md`'s removal section and `dashboard-rpc/SPEC.md`'s closing paragraph, and the "before the previews they may be serving" line in `daemon.ts`.
