What the tests cover, partly against a real git repository:

- **The branch an agent's work is on** - the branch recorded on the agent wins, whatever its name; an agent that recorded none falls back to its birth branch `agent-<agent id>`, and to nothing else. A branch is recognized as an agent's by its `agent-` prefix; a hand-made branch and a slashed name are nobody's.
- **Reading what a finished agent left behind** - a directory that is not a git repository yields no handoff at all; a branch that no longer exists reports itself gone and empty, still saying whether the repository has a remote, instead of failing; a branch that changed nothing reads empty, with no commits and zero counts; a branch with work lists its commits (seven-character id and subject, spaces kept), its files with lines inserted and deleted, a binary file listed without counts, the detected base (`origin/main`), and counts as pushed when the remote holds the same commit; an unpushed branch and a repository with no remote are told apart; the pull request is looked up for the agent's branch, never for whatever branch the project's working copy is on. Against a real repository: a branch outlives its checkout and still reports its commits, files and counts when read from the project's working copy sitting on `main`, with no remote and not merged, and reads as merged once it is merged into the base; a branch whose only commits are the base's own, because the base moved on, reads empty with no files, so no pull request GitHub would refuse is ever offered.
- **Nothing to hand off** - a branch whose commits touch only files under `.the-framework/` is empty and the automatic handoff skips it as having no commits; bookkeeping beside real work does not make a branch empty.
- **Uncommitted work** - the files left uncommitted are read from the agent's own checkout and listed by path while the branch itself reads empty; when no checkout is named the list is absent rather than empty, and no working tree is inspected.
- **Opening a pull request for a branch** - the branch is pushed to `origin` with its upstream set before the pull request is created for that head against the given base, ready for review rather than draft, and the result carries the URL `gh` printed and the number parsed out of it; a failed push opens nothing and reports the push's reason; the base `origin/main` is passed to GitHub as `main` (`origin/release/2.x` as `release/2.x`, a bare `main` unchanged) and still passed.
- **A pull request for a branch only the remote has** - opened as a draft, with nothing pushed and no base named; the agent's own description becomes the body in place of what was asked for, with the "Opened from The Framework session" line still riding along; without a description the body says what was asked for; a refusal by `gh` is a reported failure, never a thrown error.
- **The automatic handoff** - an armed agent opens a draft pull request and pushes on the way, reporting done with the URL and number; with only the push armed the branch is pushed and nothing is opened; a disarmed agent touches neither git nor `gh` and reports "not armed"; a branch with an open pull request is never given a second one and reports "already open"; an agent that kept committing after its pull request merged gets a fresh pull request; a merged pull request whose head is still the branch tip reports "already landed", and so does a merged pull request with no head to compare, since a duplicate is never risked on a guess; an agent that committed nothing reports "no commits"; a repository with no remote is a skip, not a failure; a failed push is reported as a failure at the push step with git's own reason line, so the page can offer a retry.
- **The merge half** - an armed merge follows the pull request it just opened: the pull request opens ready rather than draft, GitHub's auto-merge is armed with a squash, and the outcome is done with the merge reported as armed; without the merge armed no merge is attempted; a merge that fails is reported as a failed merge on a handoff that still succeeded; an armed merge takes the already-open pull request a predecessor left, reporting the skip and the merge together.
- **Which pull request is the agent's** - an open pull request counts whatever its age; a predecessor's merged pull request never does; among the pull requests created after the agent started, the oldest answers identity and the latest answers the handoff decision; without a start time only an open pull request is trusted; a gone branch still reports its pull request.
- **The pull request the agent recorded** - the recorded pull request is the answer and only its state is read live, for that one branch; an agent that recorded none gets nothing and costs no `gh` read; a record the live read cannot confirm still answers with its number and URL and an unknown state; a different pull request on the branch is not the agent's answer.
- **Configuration arms the merge, the agent authorizes it** - without the ready-for-merge signal the merge is withheld as not ready, whatever the TODO file says; with the signal but open entries in the agent's own TODO file it is withheld for that reason; with the signal and an empty TODO file it may run.
- **The pull request's title** - an agent implementing a ticket carries the issue reference as "(fix #42)" after its session name; the agent's own title wins over the session name; an agent that named nothing is titled "Session <agent id>" and never with the prompt it was given, with the issue reference still appended.
- **The "Merge" button on a finished agent** - the agent's open pull request is merged through GitHub's auto-merge with a squash and the result carries the pull request's URL and number; an agent with no pull request is refused with "this session has no pull request to merge" and one whose pull request already landed with "this session's PR is already merged"; a merge the remote refuses comes back as that error, not as a success.
