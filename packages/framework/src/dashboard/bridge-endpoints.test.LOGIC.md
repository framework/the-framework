What the tests cover, against a real HTTP server wired the way the daemon wires the bridge:

- **A question is recorded and stamped by the daemon** - a valid question is accepted with 204 and recorded with its title and options, and the time it was received is the daemon's own, never the one the caller sent.
- **The question's flags travel whole** - multi-select, a pre-checked default and a stop flag reach the record as posted; a false flag, a blank detail and a field the daemon does not know are dropped.
- **Off unless the bridge is on** - with no bridge token configured, a question is answered 404 and nothing is recorded.
- **The bridge token** - a missing token, a wrong token of the right length and a token of the wrong length are all refused with 401 before anything is recorded, and the answer, start and status routes demand the token exactly like the question route; the ping is guarded too.
- **Validation with a reason** - a body that is not JSON, not an object, a session id that is not one (a path, for instance), a blank title, no options, an option with no label, more than twenty options, a recommendation that names no option, two options sharing a label, and a multi, default or stop flag that is not a boolean are each refused with 400 and a message naming the field; nothing partial is recorded.
- **An oversized body** - a body past the cap is refused, or the connection torn down, and nothing is recorded.
- **Methods and the ping** - a GET on the question route is 405; a GET on the ping answers 200 with the body "ok", which is what tells the bridge apart from a dashboard that has no bridge and serves its app shell for any path.
- **No CORS headers** - a response carries no `Access-Control-Allow-Origin`, so a page cannot post on the user's behalf.
- **Answers and their delivery report** - the answer queued for a session is served with its id and text, an unknown session gets null with a 200, a malformed session id 400; the delivery report is handed on with its session, answer id, outcome and note, and a report whose outcome is not a boolean is refused; a daemon with no answer source answers null rather than failing.
- **The version gate** - with no version header the call is refused 426 as "unknown", naming the expected version and the update steps at `chrome://extensions`; a wrong version is refused on every route, the ping included; the matching version passes; every claim, blocked or not, is recorded; a caller without the token is refused before any version is looked at, so nothing about versions is recorded for it; the version the daemon expects equals the version in the extension's manifest.
- **The queue of sessions to create** - the next session request is served with its id, repository, branch, prompt and model, and a second read gets null because the first claimed it; the creation report is handed on with the created session id; a daemon with no queue answers null and accepts a report it drops; a report without an id, with an id over 64 characters, with a non-boolean outcome, a malformed session id or a non-string note is refused, a plain failure is accepted, and a POST on the start route is 405.
- **The sessions to serve** - the list the daemon supplies is served as is, each session with its id, URL and whether an answer is queued.
- **List statuses** - a batch is accepted with 204, each status stamped with the daemon's time and not the caller's; a label on an unknown status travels cut to 80 characters and a blank label is dropped; a body that is not an object, an empty batch, a malformed session id, a status the daemon does not know and a non-string label are refused, and one bad entry refuses the whole batch with nothing reaching the store; a GET is 405; a daemon that keeps no statuses accepts and drops them.
