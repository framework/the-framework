What the tests cover, against a throwaway loopback server standing in for the device:

- **Starting the agent on the device** - the start is posted to the device's relay start with the prompt, the kind and the options as its body, the token as the `fw_daemon` cookie and no `Origin` header; the device's answer, with the device's own agent id, is the start's result; a refusal from the device comes back as a failed result naming the device or the status, never as an exception.
- **Checking that a device is reachable** - the ping reaches the device's relay ping with the cookie; a success status means reachable; a failure status means not reachable; a port nothing listens on means not reachable.
- **Streaming the agent's events back** - the lines arrive as events in order and the stream ends when the device closes it; a line split across two chunks is reassembled rather than dropped; a 401, as a rotated token earns, ends the stream cleanly with no events, not as an error to retry.
- **The register of relayed agents** - a registered agent's local stream replays the device's events and ends when the device closes, after which the stream, and with it the token, is gone; a 401 closes the stream cleanly with no events; a project's list carries the relayed agent as a row of its own, running, with what was asked, and another project sees none of it; the row's status follows the device's end event to done, stopped or failed, and becomes stopped when the stream drops with no end event; a device that reports the agent settled while keeping it alive makes the row read as waiting, still running; the device an agent runs on stays known after its stream has ended; shutdown clears every row and forgets every device.
- **Forwarding a call to the device** - the call is posted to the device's relay call endpoint with its name and arguments, the cookie and no `Origin`, and the device's own result comes back unwrapped; a failure status from the device fails the call.
