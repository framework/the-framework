What the tests cover, against the daemon's real HTTP server bound to a loopback address:

- **A broken install** - without a built dashboard, the root answers 503 and says the dashboard is "not installed".
- **The built dashboard** - `/` serves the app shell, a fingerprinted asset under `/assets/` is served with a JavaScript content type, and an unknown client route is served as the app shell so client-side routing boots.
- **Bad requests never take the daemon down** - a malformed percent-escape in a path (`/%zz`) is served as the app shell; the same escape inside a browser preview path (`/browser/p/%zz/stream`) is served as the app shell; an absolute-form request target that cannot be parsed is answered 400. After each, the daemon is still serving.
- **The RPC mount's guards, through the whole server** - a cross-origin POST to an RPC is 403 and says "cross-origin"; a POST whose `Host` names another site while the browser believes it is same-origin (DNS rebinding) is 403 and names the `Host`; the same POST with the host the user actually typed is not refused.
- **The shared token, when one is configured** - the app shell, an asset, an RPC and the browser preview all answer 401 "unauthorized" without a cookie or `?token=`; a valid `?token=` answers 302 to the same path with the token removed and sets the cookie `fw_daemon` marked `HttpOnly`, `SameSite=Lax` and `Path=/`; a wrong token is 401 whether it has the right length or not; the `fw_daemon` cookie admits the app shell, `/_rpc` and `/browser`; with no token configured, which is what a loopback bind does, a request with neither cookie nor token is admitted and the guard does not exist.
- **The relay endpoints behind the shared token** - the relay's start (`/_relay/start`) is 401 without the cookie and starts nothing; with the cookie it answers 200 with the start's result, and exactly one agent was started with the posted prompt and no project, so it runs in the device's own home checkout; a start whose options name a further device is stripped of that device before the agent starts, so a relayed agent never relays onward, while its other options survive; the relay's events (`/_relay/events`) are 401 without the cookie and, with it, stream the named agent's events as one JSON object per line in order; the relay's ping (`/_relay/ping`) is 401 without the cookie, 200 with an empty body with it, and starts nothing.
- **The relay on a loopback bind** - with no token configured, a cross-origin POST and a rebound-`Host` POST to the relay's start are both 403 and start nothing, while a caller with no `Origin` and a loopback `Host`, which is what a real device sends, starts the agent.
- **The same-origin rule** - an absent `Origin` passes; an `Origin` equal to the request's own host passes; a loopback `Origin` passes whatever its port, for `127.0.0.1` and `[::1]` alike; an `Origin` on another site fails; `127.evil.com` fails, being a registrable name rather than a loopback address; a malformed `Origin` fails.
- **The expected-Host rule** - bound to `127.0.0.1`, a `Host` of `127.0.0.1:4200`, `localhost:4200` or `[::1]:4200` passes, the IPv6 colons surviving the port split; `evil.com` with or without a port, `127.evil.com` and `127.0.0.1.evil.com:4200` all fail; a missing `Host` fails; bound to `0.0.0.0`, or with no bound host at all, any `Host` passes because the shared token gates that case instead; the bound address itself passes even when it is not a loopback spelling, such as a bind to `localhost`.
- **A web agent's start reaches the extension** - with a bridge token configured and the extension having spoken recently, a web agent's start request (repository, branch, prompt and model) posted to the web-start endpoint is accepted with 202 and an id, and the extension's next read of the bridge's start route is handed exactly that request, the model included.
