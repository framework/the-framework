What the tests cover, for the dashboard's HTTP server:

- **Serving the app** — an install with no built app answers every request saying the dashboard is not installed; otherwise the app shell is served at the root, its assets are served with the right type, and any unknown path falls back to the shell so the browser app can route it itself.
- **Surviving bad requests** — a malformed percent-encoded path, a malformed path inside the browser preview's routes, and a request target that cannot be parsed at all each answer sanely (the app shell, or a bad-request status) and the daemon keeps serving afterwards; unguarded, each of these used to kill the process.
- **Cross-origin and rebound-name refusal** — a call carrying another site's origin is refused; a call from a page whose name resolves to this machine — which looks same-origin to the browser — is refused on the strength of the name it arrived under, while the same call under the address the user actually typed goes through.
- **Which origins and names count** — a request declaring no origin passes (a non-browser caller); this server's own address and any loopback address pass; another site, a name that merely looks loopback-like, and a malformed origin all fail. On a loopback bind only loopback names or the bound address itself pass, including the bracketed IPv6 spelling, while a name resolving here but calling itself something else fails, as does a request with no name at all. On a non-loopback bind there is no name to check against, so the check stands aside and the shared token guards instead.
- **The shared token** — with a token configured every route is unauthorized without it: the app, its assets, the calls surface, the browser preview. A correct token in the address is answered with a redirect to the address without it, setting a cookie that page scripts cannot read, scoped to the whole site, and deliberately not restricted to same-site requests so it survives the cross-site hop to another device. A wrong token is refused, including one of exactly the right length, since the comparison is constant-time. The cookie then admits the app, the calls surface and the browser preview alike. With no token configured — the normal loopback case — the guard does nothing and local use is unchanged.
- **The device relay** — starting an agent over the relay requires the token and, with it, actually starts the agent in the device's own checkout; a nested run target inside the options is stripped so a relayed agent never relays onward, while the rest of the options survive. The event stream requires the token too and then streams the agent's events one per line. The reachability ping requires the token, answers with an empty body, and never starts an agent. On a loopback bind, where the token guard is off, the relay still refuses a cross-origin call and a rebound name, and neither reaches the agent spawn — while a genuine device call, which declares no origin and addresses a loopback name, goes through.
