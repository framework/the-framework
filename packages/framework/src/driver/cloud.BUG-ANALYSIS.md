# Bug analysis: packages/framework/src/driver/cloud.ts

## Business logic (high-level)

The `web` run target's hand-off driver: the first `prompt` pushes a hand-off anchor (empty commit on HEAD) to `refs/heads/<session id>`, queues a session request on the daemon's `/_web-start` endpoint, polls until the browser extension reports the created claude.ai session, and resolves the turn with the link; every later prompt reports the same session and spends nothing. Checks against the SPEC:

- **Missing-prerequisite messages, in order** — no `extension` config → NO_DAEMON; no GitHub `origin` slug → NO_REMOTE (checked before pushing — test pins that nothing was pushed or queued); daemon 409 → NO_EXTENSION; daemon 404 → BRIDGE_OFF (cross-checked `web-start-endpoints.ts`: bridge-off really answers 404 on this exact path, and the constant `WEB_START_PREFIX = '/_web-start'` is slash-prefixed so URL assembly with the trailing-slash-stripped base is well-formed). ✔
- **Anchor push (#1601/#1320)** — `git commit-tree HEAD^{tree} -p HEAD -m …` then `push origin <sha>:refs/heads/<id>`; failure stops the run naming the remote; the anchor sha rides the `result` event (`anchorSha`) once handed off. ✔ Note: `anchorSha`/`handedOff` are set only after `createViaExtension` succeeds — if the extension step fails *after* a successful push, a retried prompt on the same session would mint a *second* anchor commit and push it to the *same* ref, which the remote would reject as non-fast-forward (different commit, same parent). In practice a failed turn fails the run and a fresh run gets a fresh session id, so no caller retries the same session; reliance noted.
- **One agent, one session** — `handedOff` guard before any controller/pre-push work; later prompts emit `result` (with the same link) but the `action` link event fires once. Pinned by tests. ✔ The narrower promise the guard cannot keep: a wait aborted after the POST was queued may still produce a cloud session daemon-side while the turn fails — inherent to fire-and-forget hand-off, daemon-side concern, out of scope here.
- **Prompt for a human (#1497)** — task first, labelled rule, then framing and per-call system; bare task when nothing injected. Exact string pinned by test. ✔
- **The turn ends when the session exists** — no readCode, no readQuota, both explained. ✔
- **Abort naming** — a user abort (session or per-call signal) anywhere in the try is renamed `claude-web prompt aborted`; pre-aborted signals refuse before any side effect (test pins zero daemon requests). ✔

Two real defects found in the wait machinery, both in `createViaExtension` (details under Bugs): the per-poll abort listener accumulates on the controller's signal, and an internal timeout that lands mid-fetch surfaces as a raw `AbortError` instead of the promised "gave up waiting… " message.

Minor listener notes (not filed): the two `{once:true}` listeners hooked onto the session/per-call signals per first-prompt attempt are never removed on completion — bounded at one failed attempt per session (later prompts take the `handedOff` early return), and aborting a stale controller is a no-op, so no observable harm. `dispose` aborts all live controllers and blocks further prompts; idempotent.

## Functions (low-level)

- **`CloudDriver.start`** — wraps into a `CloudSession`. Verdict: correct.
- **`cloudHandOffPrompt(task, ...injected)`** — filters falsy blocks; header before the first block only, rules between blocks. Matches the pinned test string; SPEC's "each behind a labelled rule" is satisfied in the sense the tests define (one label introducing the framework's blocks). Verdict: correct.
- **`CloudSession` ctor** — id `cloud-<counter>-<tag>`; the random 8-char tag keeps ids unique across daemon restarts (the ref name derives from it — collision would corrupt another run's ref; 8 hex chars of UUID is plenty for per-user refs). Verdict: correct.
- **`prompt(text, opts)`** — flow analyzed above. The `finally` clears the 120 s timer and drops the controller. Errors thrown after a concurrent user abort are renamed; a timeout abort keeps the underlying error (see bug 2). Verdict: two bugs in the machinery it drives; otherwise correct.
- **`createViaExtension(ext, repo, ref, prompt, signal)`** — POST then poll loop. `queued.json()` without an `id` degrades to a 404-ish "lost the session request undefined" — acceptable. Poll: non-ok → named loss; `failed` state → extension's note; `created` requires both `sessionId` and `url` (partial payload keeps polling — safe). Sleep resolves on abort so the loop re-checks and throws the gave-up error. Verdict: bugs 1 and 2 below.
- **`report(session, when)`** — `first` emits the `cloud <url>` action; both emit `result` with `sessionId`, `sessionLink`, and (when known) `anchorSha`. Returns `{text, sessionId}`. Verdict: correct.
- **`dispose()`** — aborts and clears controllers, flags disposed. Verdict: correct.

## Bugs found

1. **L227** (the poll sleep): every iteration does `signal.addEventListener('abort', …, { once: true })`, and when the timer fires normally the listener is never removed — one leaked listener per 2 s poll on the same `AbortSignal`, up to ~60 over the default 120 s wait. Node warns at 11 EventTarget listeners, so any hand-off that takes more than ~20 s prints `MaxListenersExceededWarning: Possible EventTarget memory leak detected. 11 abort listeners added to [AbortSignal]` in the daemon, and the listeners (plus their timer closures) accumulate until the prompt settles. Severity: minor (bounded leak + alarming console noise on the happy-but-slow path). Fix sketch: name the abort handler, and in the timeout arm `signal.removeEventListener('abort', onAbort)` before resolving (or use `once(signal, 'abort')`-style cleanup / `AbortSignal.any`).
2. **L218** (also L203): the internal 120 s timeout aborts `controller`, and when that abort lands while a `doFetch` is in flight the fetch rejects with a raw `AbortError` ("This operation was aborted"); `prompt`'s catch only renames *user* aborts, so the turn fails with the bare AbortError instead of the SPEC-promised "gave up waiting for the browser extension to create the session" (SPEC: "A wait past the hand-off's timeout also stops the run, naming the extension"). The mid-fetch case is precisely the unresponsive-daemon scenario the timeout exists for; the existing timeout test only exercises the abort-during-sleep window, so it passes. Severity: minor (wrong failure message, correct failure). Fix sketch: in `createViaExtension`, catch fetch rejections and, when `signal.aborted` (and the user signals are not), throw the gave-up error instead.
