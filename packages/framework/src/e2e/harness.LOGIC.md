The world the backend end-to-end stories run in: one daemon runtime per story, its business logic wired exactly as the real daemon wires it, on throwaway state, with every fixture project's hooks file naming `fake-run-bin.ts` as its start and resume hooks [2], so an agent [1] is a real detached process writing the files the dashboard reads, against a scripted fake in the coding agent's [3] seat.

## Glossary

[1] agent: the unit of work: one task worked by a coding agent in its own checkout, on its own branch. The Framework starts none itself: the tool the project's start hook names runs it, and the dashboard shows it from the files that tool keeps.
[2] start hook / resume hook: the one shell line under `start`, and the one under `resume`, in a project's `.the-framework/hooks.yml`; each answers the agent's id as JSON on stdout.
[3] coding agent: the CLI doing the actual work: Claude Code or Codex.
[4] registry: `~/.the-framework.json`, the file that lists the projects and keeps the user's preferences.
[5] preferences: the user's dashboard settings, kept in the registry.
[6] relay: running an agent on a device: the local daemon forwards the start, streams the events back and forwards steering, so the agent renders like a local one.
[7] quota: the account's subscription allowance, as the coding agent reports it: a session window and a quota week, each with a percentage used.
[8] bridge browser: the Chrome for Testing the daemon runs for the Claude web bridge.
[9] the agent queue: every task agents will work next, in the order they will be taken; the `queue` skill keeps it as `TODO_AGENTS.md` on the `agent-data` branch, in priority sections, and the dashboard reads it through the `queue` command that package declares.
[10] the `agent-data` branch: the branch of a project's repository used as a file store for everything agents share: tickets, the agent queue, the runs.
[11] checkout: an agent's own working copy of the project: a git worktree under the project's `.branches/` directory.
[12] launcher: the Start form on a project's own page in the dashboard.
[13] diary: what an agent said and did, one line per event: `<id>.jsonl`, in the agent's checkout while it has one, answered by the project's runs provider once finished.
[14] run: only the record of one finished agent, kept by the `logs` skill on the `agent-data` branch: a card (what was asked, the branch, the pull request, how it ended, what it cost) and a diary (what the agent said). Never the unit of work.

## Business logic — TL;DR

- **A daemon on throwaway state** - each story stands up its own home directory and its own configuration home, where the registry [4], the preferences [5] and the daemon's state live, so story files running side by side never see each other's projects in the cross-project reads; closing the world stops every agent [1] it started that is still working, the way the Stop button does, waits for it to end, and removes everything it made.
- **The dashboard's context, as the daemon wires it** - every dashboard RPC a story calls addresses this world: starting agents, adding projects, the events source, relayed [6] agents, the preferences and the Discord credentials from the registry; what the daemon keeps live is replaced by values the story sets: the quota [7] reading, no project errors, and a bridge browser [8] that is off.
- **Projects are real repositories** - a project is a real git repository with an initial commit and a bare `origin`, registered through the same Add-project RPC as the dashboard's dialog, and then given a hooks file whose `start` and `resume` lines run the stand-in tool, and the `logs` and `queue` skills' packages as installed dependencies (links to this workspace's copies), which make them the project's runs provider and queue provider, as a real project has them; the tickets and the agent queue [9] a story seeds land on the `agent-data` branch [10], where the product reads them, never in the working tree; the `origin` is there because a checkout [11] is reclaimed only once its work is on the remote, and a fixture with nowhere to push would keep every checkout forever.
- **Agents are started and observed as the dashboard does it** - an agent starts through the same Start RPC as the launcher [12], with the prompt and the picks the story gives; a story waits for a status through the same agents list the sidebar reads; waits for the checkout to be reclaimed, since an agent's card says done before its tool records it and reclaims the checkout, and acting on the agent in that window races the tool's own git; waits for the run [14] to be answered by the project's runs provider, which is the only wait that serves an agent whose checkout is kept — one waiting on a question — because until the record lands its card in the checkout is the single copy there is; and follows the agent's diary [13] through the same relocating tail the dashboard's live feed uses, each line turned into the event the dashboard draws, so the final lines are seen even after the diary leaves the checkout.
- **What the hooks were handed** - every start and resume line's environment (the id, the prompt, the driver and model, the text or the answer) can be read back, oldest first: the agent is detached, so this is the only place the contract is observable.
- **Letting a held agent go** - a story can release an agent whose prompt said "hold" by writing the go file in its checkout.
