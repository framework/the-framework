What the tests cover: tickets are proposals and the agent queue holds confirmed work, and both belong to a project package The Framework reads through the command that package declares.

- **Browsing the ticket backlog** - the Tickets page is the tickets package's widget, and its reads are that package's command run by the dashboard in the project: `list --local` lists every ticket with its parsed title, priority and summary; `show <file> --local` carries the ticket's full text; a name that escapes the tickets directory is refused by the command. The Framework's own reads see only what it composes: the dashboard's project row says the project provides tickets and has some.
- **A claim released by hand is seen at once** - a ticket seeded claimed on the `agent-data` branch (converged with the fixture's origin) shows its holder on `show --local`; the tickets package's `release <file> --force`, run as an act (the way the dashboard runs a widget's action), lifts the claim on origin, and the very next `show --local` shows no holder, because The Framework converged its copy of the branch after the act instead of waiting for its next sync; the released ticket still lists through the package's command, unclaimed.
- **A queued ticket, read through the queue provider** - a queue seeded on the `agent-data` branch (and converged with the fixture's origin, as the daemon keeps it) with a link back to a ticket, in that ticket's priority section, is what the framework reads by running the queue command the fixture's package declares: the project's block carries the entry as the command prints it.
- **The queue widget's action is seen at once** - the queue package's command run as an act (the way the dashboard runs "Add to queue") adds a second link in a lower priority section, and the very next read of the queue shows both entries in the file's order, high to low: the framework converged its copy of the branch after the act instead of waiting for its next sync.
