# Bug analysis: packages/framework/src/on-before-mergeable-prompt.ts

## Business logic (high-level)

A 42-line binding layer: it names the generated on-before-mergeable prompt constant, declares the
context shape that prompt's `${{ }}` fragments read, and renders it.

Responsibilities and invariants, per `on-before-mergeable-prompt.SPEC.md`:

- **Queues, never runs.** The prompt text (`prompts/on_before_mergeable_prompt.md`) instructs the
  finished agent to append entries to `TODO_AGENTS.md`; nothing here spawns anything. The module
  is pure string production, so there is no lifecycle, no I/O, and no concurrency surface at all.
- **Every entry names the session.** `session_name` is required and appears in four fragments. A
  render without it must fail loudly rather than queue "changes introduced by undefined" -
  delivered by `renderTemplate`, which throws `TemplateFragmentError` on any fragment evaluating
  to `undefined`. That is the SPEC's "fails loudly", and it is a real backstop rather than a
  restatement: `String(undefined)` would otherwise have produced the exact bad entry the SPEC
  forbids.
- **The preset entries point at real files.** `presets` defaults to `presetContext()`, i.e. the
  six `PRESET_STEMS` mapped to `.the-framework/presets/<stem>.md`, which `materializePresets`
  actually writes at install time. The prompt reads only `maintainability` and `security_audit`;
  the other four stems are harmless extras in the context.
- **Flat fragments only.** The template language's fragment regex is non-greedy, so a nested
  `${{ ... }}` closes the outer fragment on the inner `}}` and the leftover is evaluated as JS.
  The module's header documents that the shipped prompt is deliberately flattened; the test file
  pins it mechanically.

Drift risk is handled outside this file: `prompts.generated.ts` is regenerated by
`scripts/gen-prompts.mjs` on every `build`/`test`/`typecheck`, so the constant cannot lag the
markdown.

## Functions (low-level)

### `ON_BEFORE_MERGEABLE_PROMPT_TEMPLATE` (exported constant)

A straight alias of the generated `ON_BEFORE_MERGEABLE_PROMPT`, existing so the JSDoc explaining
the flattening has a home and so the test file imports a name from this module rather than from
the generated one. Inert. Verdict: correct.

### `OnBeforeMergeableContext` (exported interface)

`session_name: string` (required) and `presets?: Record<string, { filePath: string }>`. The
optionality of `presets` is what makes the module usable from a test or a caller that has no
project on disk. Note the type is a wide `Record`, so a caller passing a *partial* map (e.g. only
`{ maintainability }`) type-checks and then fails at render with
`TemplateFragmentError: ... failed to evaluate: Cannot read properties of undefined`. That is a
loud failure with the offending fragment in the message, not a silent bad prompt, and no caller in
the repo passes `presets` at all. Reliance noted, not a defect.

### `renderOnBeforeMergeablePrompt(tf)`

In: the context. Out: the rendered prompt. Body: `renderTemplate(TEMPLATE, { tf: { ...tf, presets:
tf.presets ?? presetContext() } })`.

Edge cases:

- `presets: undefined` -> defaulted. `presets: {}` -> passed through (`??` only replaces
  null/undefined), then the maintainability fragment throws a `TemplateFragmentError`. Loud, and
  arguably right: an explicitly empty map is a caller error.
- `session_name: ''` renders as an empty string rather than throwing (`''` is not `undefined`),
  producing `changes introduced by ""`. Reachable only from a caller that has a session name field
  set to empty; the SPEC's requirement is specifically about a *missing* name, and the CLI checks
  first, so this is a soft spot rather than a bug.
- `session_name` containing a `"` or a newline is inserted verbatim into a quoted entry. The value
  comes from the agent's own `setSessionName()`, so it is not adversarial, but a name with a quote
  would produce a malformed queue entry. Not reachable via any validated path in this repo
  (session names are slugs); noted, not reported.
- Determinism: no clock, no randomness, no fs read - the same input always yields the same output.
- The context object is rebuilt per call, so no shared mutable state between renders.

Verdict: correct.
