What the tests cover:

- **Where the file lives** - `$XDG_CONFIG_HOME` wins over `$HOME`; an empty `$XDG_CONFIG_HOME` counts as unset and the file is the dotfile under `$HOME`.
- **A project's id** - the same path always gives the same id; different paths give different ids even when their folder names match; the id is URL-safe for a folder name with spaces, punctuation or accented letters.
- **Listing projects** - a missing file lists nothing; so does an empty, non-JSON, non-object or number-only file; malformed records are dropped and well-formed ones kept; duplicates by normalized path are dropped with the first one winning; a file whose top level is a bare list of projects, a shape the product no longer writes, reads as an empty registry.
- **Registering a project** - a record is appended and the file written as JSON that parses back, with the parent directory created; registering the same path again, with a trailing slash or a `..` segment, returns the existing record and keeps its original registration time; the stored path is absolute; the existing preferences survive the registration.
- **Validating preferences** - unknown keys and wrongly typed values are dropped; every on/off preference survives a save and a read; a known location round-trips and an unknown one is dropped; only the current key spellings are read, a renamed key being ignored beside the key that replaced it; the routine opt-out list is trimmed, deduplicated, purged of junk entries and cleared when empty; the spend offset round-trips, is clamped to the slider's reach both ways, and is dropped when not a finite number; the routine card's project is trimmed and dropped when blank or not text; the concurrency setting round-trips, has no upper bound, is floored at one, rounded to a whole number and dropped when not a finite number; the Discord, activity, "needs you" and transparent toggles round-trip; the model is trimmed, dropped when blank and dropped when it is the word "Default" in any casing; a known driver is kept and an unknown one dropped; the editor is trimmed and dropped when blank; a known theme is kept and an unknown one dropped; custom presets are trimmed, and entries with a blank label, a blank prompt, a duplicate id, a missing id or the wrong shape are dropped; when no custom preset survives the key is left out.
- **Patching preferences** - a patch merges only the keys it names over the stored block; a blank string or an empty list in a patch clears that key; the merged result is validated, so junk in a patch drops the key rather than landing; the store handed to the dashboard exposes the patch.
- **Reading preferences** - a missing file, or a file with no preferences block, reads as no preferences.
- **Saving preferences** - the validated block is persisted and the project list preserved.
- **The preferences store** - reads and writes go through the same file; the listener is told the keys the caller wrote, not the merged result, for a save and a patch alike; a listener that throws does not fail the write.
- **Atomic writes** - the live file is never written in place, only replaced by renaming a temporary file over it, and no temporary file is left beside it; a write that dies part way leaves the previous file intact and readable.
- **Serialized mutations** - two concurrent registrations both survive; a concurrent registration and preference save do not drop each other; a failed mutation does not block the next one.
- **The daemon token** - it is base64url text of at least 43 characters, stored at the top level and not among the preferences, and a second request returns the same token; reading returns nothing until one is generated; a token that is a number, empty, `null` or an object in a hand-edited file reads as none; the token survives registering a project, saving and patching preferences; two concurrent first requests settle on one token.
- **Credentials** - a saved webhook round-trips at the top level, not among the preferences; a patch leaves a credential it does not mention alone; `null` clears a credential, and clearing the last one removes the block; a hand-edited block is sanitized, unknown keys and non-text values dropped and the value trimmed; saving a credential keeps the projects and the preferences; the file is written owner-only with the permission set before the rename, so the real path was never readable by others; a filesystem without permission bits still gets the write; the token stays put when a credential is saved beside it.
