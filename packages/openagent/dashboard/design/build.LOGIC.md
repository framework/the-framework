Generates the design gallery: `pnpm design:build` renders every card of the registry (`previews.tsx`) to one self-contained static HTML page under `design/out/`, each page showing the card's component twice, in a "Light" pane and a "Dark" pane, styled by the very stylesheet the dashboard ships. The output is generated whole on every build and never edited by hand: `design/out/` is emptied first and kept out of version control, and a separate upload step publishes it to the gallery's host.

## Business logic — TL;DR

- **The shipped stylesheet, inlined** - the cards' CSS is compiled through a CSS-only build (`vite.config.css.ts`) from a gallery entry (`gallery.css`) that imports the dashboard's own stylesheet unchanged and only adds the components and the registry to what is scanned for classes; the compiled CSS is inlined into every page, so a card is styled exactly as the app is, and a build that yields no CSS fails with "gallery CSS build produced nothing" rather than writing unstyled cards.
- **One static page per card** - each card's content is rendered to static markup with no script, so a hover or open state is a separately rendered instance rather than something to click; the page carries the card's name and subtitle, the "Light" and "Dark" panes, and, for a replica, the flag "Replica: portalled at runtime, markup hand-copied from source". A marker comment at the top of each page names the card's group, for the upload step to file it under.
- **The gallery's own chrome stays apart** - the page's own framing (heading, panes, flag) uses a class namespace of its own, so it can never be mistaken for the dashboard's styling and never leaks into a card.
- **Generated, never edited** - `design/out/` is emptied before each build and the CSS build's scratch directory is removed after it; both are ignored by git, so the registry and the shipped components are the only source of truth. The build ends by logging how many cards were written and how much CSS was inlined.
