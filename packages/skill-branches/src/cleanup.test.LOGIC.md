What the tests cover, `branches cleanup` through the command line, against a real repository with a real remote and a person's own lines in the exclude file:

- **What goes and what stays** - with one checkout whose work is committed, one with an uncommitted edit that the agent named (so a branch link sits beside it), and another tool's checkout (`.branches/agent-data`): the first is removed and named `.branches/agent-<id>`; the second is kept with `<branch> has uncommitted work; the checkout was kept`, its edit untouched and its branch link still pointing at it, the link not named; the other tool's is kept with `not made by branches`, its file untouched; the branch holding the committed work stays at the same commit; the four rules (`/.branches`, `/node_modules/.bin/branches`, `/.claude/skills/branches`, `/.agents/skills/branches`) are all still in the exclude file; the remote's branches, the person's branch and the working tree are as they were; exit 0. Once the edit is committed and the other tool's checkout is gone, the clean-up removes the last checkout and then `.branches`, keeps nothing, leaves the exclude file with the person's own lines only, leaves both agents' branches where they were, leaves no checkout registered with git, and still changes nothing on the remote or the person's branch; a further clean-up removes nothing and keeps nothing.
- **A project the tool never worked in** - the clean-up answers `{"ok":true,"removed":[],"kept":[]}` and the exclude file, the remote, the person's branch and the working tree are exactly as they were.
- **The rules are the repository's** - in a project the tool never worked in, the four rules written by hand stay and the answer is empty; with a second checkout of the same repository that has an agent's checkout of its own, holding an uncommitted edit, the clean-up removes this project's checkout and `.branches`, leaves all four rules, and the other checkout's status stays clean while its agent's checkout shows only the agent's own edit.
