The `orchestration` skill [1]: a main agent [2] saves a plan of tasks, starts subagents [3] on them once the person approved it, lists them, reads their results, stops them, and lands their work on its own branch, from the shell with the `orchestration` command (`plan`, `start`, `list`, `read`, `stop`, `land`). Which coding agent and model a subagent runs on is the person's to say, not the agent's: the agent says whether each task is simple or hard, and the person's subagent settings [4] on this machine name the coding agent and model for each level and how many of one main agent's subagents run at once; the command keeps them (`settings`), and writes the dashboard's hook line that saves them (`init`). A subagent is a run of the runner's (`agent-runner`) started for the main agent: its own process, its own checkout, a branch started from the main agent's, and a run record like any other run's, so the dashboard shows it like any other agent. The command never waits: the runner tells the main agent when a subagent ends, as its next prompt. `SKILL.md` is what the agent reads; `package.json`, the `tsconfig*.json` files and the ignored build output (`dist/`, `dist-test/`) carry no business logic. The package depends on `agent-runner` (a run's first record, the spawn of its process, the readiness check, the tool's mark on a record, the live card and diary, the coding agents it can start, the writer of a dashboard's hooks file), on `agent-driver` (the wording of the prompt that carries the person's answer), on `skill-logs` (the run records), on `skill-branches` (the project, a run's checkout and its branch) and on `agent-data` (the data branch's write cycle, and hiding a directory from git); nothing depends on it, the runner least of all: the runner names no skill.

## Context

**User story**: the user asks one agent for a piece of work with parts that can be worked alone. The agent writes a plan of small tasks, saves it with `npx orchestration plan <file>`, shows it and asks the user to approve it; no subagent starts before the user's Approve. The agent then starts a subagent per task with `npx orchestration start --level <simple|hard> "<task>"`, each on the coding agent and model the user picked for that level in the dashboard's Settings → Subagents, no more at once than the user allows there, and ends its turn. Each subagent works alone, commits to its own branch, publishes nothing (no push, no pull request) and asks nobody. Each time one ends, the main agent is continued with which one ended, how, where its work is and its last words; it lands the work with `npx orchestration land <id>`, which merges the subagent's branch into its own and deletes that branch, keeping the subagent's last commit under a ref of its own on this machine and on the subagent's record, so the dashboard still shows what that one subagent changed, and goes on. Nothing of this reaches origin. When every task is landed it says so and ends its reply, publishing nothing itself: its branch becomes one pull request for the whole plan when the user publishes it, or asks the agent to. The user passes nothing along.

**Business logic story**: the runner can start a run for another run and tell that run when it ends (`agent-runner`'s `run --parent`, `run --base` and `parent.ts`). This package is what an agent uses to do so: it fills in the parent and the base from the calling run, adds to every task the lines saying the reader is a subagent, and reads the runs back by their parent.

**Problem**: a start spends money, so an agent that skipped asking would spend it unseen; a subagent's branch left behind after its work was merged is a second branch holding work that is now the main agent's, one for every task, and a merge and a delete left to the agent's memory are forgotten; a subagent or a main agent that published by itself would put work on origin the person never asked to publish; a main agent that waited for its subagents would hold a turn open for as long as they work; one that started them by the runner's own command line would have to name its own run and branch, could not tell its subagents from other runs, and could not stop one; a main agent that picked each subagent's model would spend the person's money on its own guess.

## Glossary

[1] skill: a capability an agent is taught, as a package with the instructions the agent reads (its `SKILL.md`) and a command on the agent's PATH.
[2] main agent: the run whose agent calls the command: the run named by `AGENT_ID` in the caller's environment, which the runner sets for every agent it starts.
[3] subagent: a run started for a main agent [2]: a run of its own, in its own checkout, on its own branch started from the main agent's, with the main agent as its parent on its record.
[4] subagent settings: the person's choice, on one machine, of the coding agent and model a task the main agent [2] calls simple runs on, the same for a task it calls hard, and how many of one main agent's subagents [3] run at once; one file, `.orchestration/settings.json` at the project's root, hidden from git.

## Business logic — TL;DR

- **What the agent is told** (`SKILL.md`) - what a subagent [3] is, the six command lines, to save a plan, with how hard each task is, and ask the person before any subagent, to commit before starting, to write a task that stands alone and say its level, to end its reply when the person's limit of subagents at once is reached and after starting, what the message a subagent's end sends is and to land the work then, and, once every task is landed, to say so and publish nothing itself: its branch becomes one pull request when the person publishes it, or asks the agent to.
- **The executable** (`bin/`) - the `orchestration` command, handing the shell to the command's rules.
- **The command and the subagents** (`src/`) - the command lines and their JSON answers; the plan saved beside the main agent's run record and approved by the person's answer to the question that names it; no subagent started before that; a subagent's branch landed on the main agent's and deleted, its last commit kept under `refs/landed/<its id>` on this machine and named on its record, origin never touched; a subagent started as a run with the caller as parent, from the caller's branch, told it is a subagent, on the coding agent and model the subagent settings [4] name for the level the caller gave, else the caller's own; no more of the caller's subagents running at once than the settings allow, 4 when unset; the subagent settings saved and read back, and the dashboard's `subagents` hook line written; no subagent of a subagent; the caller's subagents listed and read by the parent on their records; one stopped by a signal to its process.
