The instructions an agent reads before splitting its task across subagents [2]: what a subagent is, how to reach the `orchestration` command, its six command lines, the plan and the person's approval that come before any subagent, what to do before and after starting one, what the message it gets when one ends is, how to land the work, and what to do when every task is landed: say so and publish nothing itself. Tracked in a project where the coding agent's harness looks for skills, it is what turns the command into a skill [3]. Its description tells the agent to use it to split its task across other agents: plan it, get the person's yes, start the agents, and land their work on its branch.

## Context

**User story**: an agent whose task has parts that can be worked alone writes a plan, shows it to the person and asks them to approve it; once they did, it starts a subagent per task and ends its reply; each time one ends it is continued with a message saying which, how, and what it answered, lands the work on its own branch, and goes on; when every task is landed it says so and ends its reply, and its branch becomes one pull request when the person publishes it, or asks the agent to.

**Business logic story**: everything the skill says the command does is enforced by `src/cli.ts` and `src/subagents.ts`; the message a main agent [1] gets when a subagent ends is written and delivered by the runner (`agent-runner`'s `parent.ts`), which the skill does not name.

**Problem**: the command refuses to start a subagent without a level, and while as many run as the person allows, so an agent not told to say each task's level, and to wait for one to end, is refused; it refuses to start a subagent before the person approved the plan, and only the answer to one exact question counts, so an agent not told how to ask is refused without end; an agent that opened a pull request while tasks were still out would publish half the plan, and one that opened it by itself once they are all landed would publish what the person only approved as a plan: approving a plan is a yes to starting subagents, not to publishing; an agent that was never told what that message is takes it for a person's message about a run it did not start; an agent that waits for its subagents inside its turn spends the turn on nothing, since the message only reaches it once its turn ends.

## Glossary

[1] main agent: the agent reading the skill: the run whose agent calls the command.
[2] subagent: another coding agent the main agent starts on one part of its task: a run of its own, in its own checkout, on its own branch started from the main agent's.
[3] skill: a capability an agent is taught, as a package with the instructions the agent reads (its `SKILL.md`) and a command on the agent's PATH.

## Business logic — TL;DR

- **How to reach it** - run as `npx orchestration` from the repository's dependency `@gemstack/skill-orchestration`, installing with the lockfile's package manager when `node_modules` is missing.
- **The commands** - `start --level <simple|hard> "<task>"` answers the subagent's id at once, without waiting; `list` is the agent's subagents, newest first, as one JSON array; `read <id>` is one subagent's `status` and, once it ended, its `branch` and `result`, its last reply; `stop <id>` stops one that is running; `plan <file>` saves the file as the agent's plan and answers the `question` to ask the person; `land <id>` merges an ended subagent's branch into the agent's and then deletes that branch; a refusal exits 1 with a line on stderr saying why, and the skill explains no refusal beyond that: each line says what to do.
- **The plan first** - before any subagent the agent writes its plan to a markdown file outside its checkout, one heading per task with whether it is simple or hard, what to change, how to check it and which tasks must land before it, and saves it with `plan <file>`; it shows the plan in its reply and asks the person with an `await-choices` block as the very last thing in the reply: the title is the `question` the command answered, copied exactly, the options are `Approve` and `Change the plan`, `Approve` recommended; it ends its reply there; `start` is refused until the person chose Approve for the plan as it is saved; after any other answer the agent asks the person what to change, unless they said, and after any change to the plan it saves and asks again.
- **Before starting** - commit first: the subagent's branch starts from the agent's last commit; the task is one quoted argument, written for a reader who knows nothing of the conversation: what to change, where, how to check it; how hard it is is said with `--level`, as the plan says, since the person's settings pick the model for each level, and the agent never names a model; a task that needs another task's work starts once that one is landed; while as many of the agent's subagents run as the person allows, `start` is refused with `limit`, and the agent ends its reply and starts that task when it is told one ended.
- **After starting** - the agent ends its reply and does not wait, sleep or poll `list`; each time a subagent ends it gets a message from the program that ran it, not from the person, beginning `The run <id>, started for this run, ended <status>`, the status `done`, `failed`, `stopped` or `waiting`, the last meaning it stopped on a question nobody can answer, to be treated as failed; the message gives the subagent's last reply and, when one is left, the branch its work is on; it then lands the work with `land <id>`, starts another subagent, or ends its reply again while others run; what a refused `land` needs (its own changes committed, a conflict merged by hand) is said by the refusal's line, not by the skill.
- **When every task is landed** - the agent says so and ends its reply, publishing nothing itself; its branch becomes one pull request when the person publishes it, or asks the agent to: then, and only once every task is landed, the agent publishes it the way the project publishes work, with the tasks listed in the pull request's body.
