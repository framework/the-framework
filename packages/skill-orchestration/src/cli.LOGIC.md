The `orchestration` command: the command lines a main agent [1] runs to save and show its plan, start a subagent [2], list its subagents, read one's result, stop one and land one's work, that the package's Settings section in the dashboard runs to read and save the person's subagent settings [3], and that a dashboard runs to remove what the package left in a project. Each call is short and answers one JSON document on stdout, a line for a person on stderr when there is something to say, and an exit code that says how it went: 0 for a result, 1 for a refusal or a failure, 2 for a command line that could not be read. The same contract as the other skills' commands and the runner's.

## Context

**User story**: an agent splitting its task runs `orchestration plan <file>` to save its plan, and, once the person approved it, `orchestration start --level <simple|hard> "<task>"` for each part, and ends its turn; when it is told one ended it runs `orchestration land <id>` to take the work, `orchestration read <id>` or `list` to look again, and `orchestration stop <id>` for one it no longer needs. The user opens the dashboard's Settings → Subagents, which runs `orchestration settings` to show what is saved; a pick there runs `orchestration settings <json>` in every project that has the package.

**Business logic story**: what each command does, and every refusal about runs, is `subagents.ts`'s; this file is the command line and the contract around it. Every command acts on the project the working directory belongs to, found by the `branches` package even from inside a checkout under `.branches/`.

## Glossary

[1] main agent: the run whose agent calls the command: the run named by `AGENT_ID` in the caller's environment, which the runner sets for every agent it starts.
[2] subagent: a run started for a main agent: a run of its own, in its own checkout, on its own branch started from the main agent's, with the main agent as its parent on its record.
[3] subagent settings: the person's choice, on one machine, of the coding agent and model a task the main agent [1] calls simple runs on, the same for a task it calls hard, and how many of one main agent's subagents [2] run at once; one file, `.orchestration/settings.json` at the project's root, hidden from git (`settings.ts`).

## Business logic — TL;DR

- **The contract** - one JSON document on stdout per command that ran; a refusal exits 1 with `{"ok":false,"reason":…}` and one line on stderr; a failure exits 1 with `{"ok":false,"reason":"failed","detail":…}` and the detail on stderr; no command, an unknown one, an unknown flag or a wrong number of arguments exits 2 with the usage on stderr and nothing on stdout.
- **The project** - found from the working directory, from inside a checkout too; outside a git repository every command refuses `not-a-repo`, `not inside a git repository`.
- **`plan <file>`** - the file, read relative to the working directory, saved as the caller's plan and answered `{"ok":true,"question":…}`; a file that cannot be read is refused `no-file`, one that is empty or white space only `empty`, each with the `file`.
- **`plan`** - no argument; `{"ok":true,"plan":…,"question":…,"approved":…}`.
- **`start --level <simple|hard> <task>`** - exactly one argument; a task of white space only, a level that is neither word, or a `--model` or `--driver` flag, is a usage error; no `--level` at all is refused `no-level`, the line saying to give `--level simple or hard` since the person's settings pick the model for it; otherwise the subagent is started and answered `{"ok":true,"id":…,"level":…,"driver":…,"base":…}`, with `model` when the subagent runs on a named one and `uncommitted: true` when the caller's checkout holds uncommitted changes, which also puts `your checkout has uncommitted changes: the subagent does not have them` on stderr.
- **`settings [<json>]`** - at most one argument; without one, the subagent settings [3] as saved, `{"ok":true,…}` with `simple`, `hard` and `atOnce` each only when set; with one, the argument is the whole settings as one JSON object, `{"simple": {"driver", "model"}, "hard": {…}, "atOnce": <n>}`, each part optional and `null` meaning unset, saved over what was saved, so a part left out is unset again, the file replaced whole rather than written into (`settings.ts`), and answered as saved; an argument that is not JSON, or JSON that is not settings (`settings.ts`), is a usage error with the reason, and nothing is saved. It needs no calling run: the dashboard runs it.
- **`list`** - no argument; the caller's subagents as one JSON array, newest first, empty when it has none.
- **`read <id>`** - exactly one argument; the subagent's card with `ok: true`, and `result` once it has one.
- **`land <id>`** - exactly one argument; `{"ok":true,"id":…,"branch":…,"merged":…}`.
- **`cleanup`** - no argument, and no calling run needed; the settings file, then `.orchestration/` once it is empty, then the rule hiding it from git once no checkout of the repository has one, removed, and answered `{"ok":true,"removed":[…],"kept":[{"path":…,"reason":…}]}` (`cleanup.ts`).
- **The usage text** - the ten command lines (`plan` and `settings` each with and without an argument), that `start` runs on the coding agent and model the person set for the level and is refused until the person approved the saved plan and while as many of the caller's subagents run as the person allows, and that a refusal or a failure exits 1 with `reason` in the JSON and why on stderr, a usage error 2.
- **`stop <id>`** - exactly one argument; `{"ok":true,"id":…}` once the signal is sent.
- **What the command runs with** - this machine's name, the clock, the probe of a live pid, SIGTERM as the stop, and the runner's readiness check, its writing and taking back of a run's first record, and its detached spawn of a run's process, and the git that hides the settings' directory; a caller (the tests) may replace each.
