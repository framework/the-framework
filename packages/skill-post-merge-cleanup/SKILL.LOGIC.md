The `post-merge-cleanup` command skill: a skill file the coding agent's harness expands from `/post-merge-cleanup`, the prompt of the agent that writes what merged work decided and taught into the project's knowledge files, in a pull request a person reviews. Given an agent run's id instead, it does the same for that run's pull request before it merges, adding its changes to that same pull request. Marked so that only a person or a runner invokes it; the agent never chooses it by itself.

## Context

**User story**: a person types `/post-merge-cleanup` and, after it, the numbers of the merged pull requests to write up; or a project's schedule fires it with nothing after it, for every pull request merged since its last run that ended done. The agent writes what the merged work decided and taught into the knowledge files, `knowledge-base/DECISIONS.md`, `FACTS.md` and `INSIGHTS.md`, and opens a pull request with them; a person reviews it and merges it. Or the user ticks "Post-merge cleanup" in the dashboard's launcher: once the agent they started ends with a pull request, a second agent is started on its branch with `/post-merge-cleanup <the first run's id>`; it pushes its knowledge-file changes onto the same branch so they join that pull request, marks the body `Post-merge cleanup done.`, and the pull request merges once it is done.

**Business logic story**: the skill names no skill and no command, and assumes no capability. The agent composes the capability skills tracked in the project on its own; what this file carries is the rules of the job, which an agent nobody answers cannot infer from the skills alone.

## Business logic — TL;DR

- **Nobody answers** - the agent never asks and decides by itself.
- **The work** - what follows the slash command: one or more pull request numbers, or the id of an agent run (below), or nothing. When nothing follows it: every pull request merged since the start of the last run of this same command that had nothing after it and ended done, as the project's record of agent runs shows; every pull request merged in the last 24 hours when there is no such run.
- **Skipped pull requests** - one whose body has the line `Post-merge cleanup done.`: this skill's own pull requests end with it, and a pull request written up before it merged (below) got it then.
- **Pull requests unreadable** - it shows an error to the user saying why and stops; none left, it says so and stops.
- **Knowledge files** - from each pull request's changes and discussion: `knowledge-base/DECISIONS.md` (decisions taken and why), `knowledge-base/FACTS.md` (non-obvious facts), `knowledge-base/INSIGHTS.md` (insights), each created when missing; only what a future agent would need and cannot get from the code, and nothing already there.
- **Publishing** - nothing worth writing: nothing published. Otherwise the change committed, the branch pushed and its pull request opened, its body naming the pull requests it covers and ending with the line `Post-merge cleanup done.`; the merge is left to a person.
- **Last message** - each pull request covered and what was written.
- **Given an agent run's id** - the agent is on that run's branch and the run's pull request waits to merge until it is done. It reads the run in the project's record of agent runs (what it was asked, what its agent said) and that pull request's changes and discussion: the pull request is the work. A run it cannot read is an error shown to the user, and it stops. Nothing worth writing, nothing committed; otherwise the change is committed on the branch it is on and pushed, joining that pull request, no other pull request is opened and no merge armed, since the pull request is merged for it once it is done. Either way the line `Post-merge cleanup done.` is then added at the end of the pull request's body, the rest kept as it is. Its last message says what it wrote.
