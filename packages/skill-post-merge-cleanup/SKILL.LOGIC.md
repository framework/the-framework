The `post-merge-cleanup` command skill: a skill file the coding agent's harness expands from `/post-merge-cleanup`, the prompt of the agent that writes what merged work decided and taught into the project's knowledge files, published as far as whoever started the agent said. Given an agent run's id instead, it does the same for that run's pull request before it merges, adding its changes to that same pull request. Marked so that only a person or a runner invokes it; the agent never chooses it by itself.

## Context

**User story**: a person types `/post-merge-cleanup` and, after it, the numbers of the merged pull requests to write up; or the scheduler fires it with nothing after it, as the `schedule` key in the skill's front matter says, for every pull request merged since its last such run that ended done. The agent writes what the merged work decided and taught into the knowledge files, `knowledge-base/DECISIONS.md`, `FACTS.md` and `INSIGHTS.md`, and publishes them as far as whoever started it said: a run started at the publish level `pr` gets a pull request with them, which a person reviews and merges; with nothing said, they stay committed on the agent's branch. A scheduled run on a machine where nobody picked a publish level is started at the level `commit`: the files are committed on the agent's branch and nothing is pushed. Or the user ticks "Post-merge cleanup" in the dashboard's launcher: once the agent they started ends with a pull request, a second agent is started on its branch with `/post-merge-cleanup <the first run's id>`; it pushes its knowledge-file changes onto the same branch so they join that pull request, marks the body `Post-merge cleanup done.`, and the pull request merges once it is done.

**Business logic story**: the skill's body, the prompt the agent reads, names no skill and no command, and assumes no capability. The check of the `schedule` key in its front matter does name commands (`gh`, `npx logs`): the scheduler, `agent-scheduler`, runs that check, and the agent is not given it as an instruction. The agent composes the capability skills tracked in the project on its own; what this file carries is the rules of the job, which an agent nobody answers cannot infer from the skills alone. The skill names no publish level: how far the work is published is said by whoever started the agent (the launcher's publish menu, or the publish level a person picked on their machine for the scheduled command; the runner tells the agent the level in one sentence after its prompt), and the skill says to follow it.

## Business logic — TL;DR

- **The `schedule` key** - the front matter's `schedule` key, which the scheduler reads, makes the skill one scheduled command, `post-merge-cleanup`, run with nothing after it: at most every hour (`every: 1h`) unless a person set their own pace for it on their machine, and only while its check finds a pull request to write up. The check, a shell line the scheduler runs at the project's root, prints the work of a run with nothing after it, as **The work** below says it: the pull requests merged since the start of the last such run that ended done, or in the last 24 hours when there is none, less those whose body has the line `Post-merge cleanup done.`; the command is due while that list is not empty. Its `waits-for` line, the plain words a person is shown for the check, reads "when a pull request merged since the last clean-up has no clean-up yet". It gives no `agents`, so one run at a time across every machine. The `schedule` key says nothing about whether a command runs on a machine or how far its runs publish: each person sets those for their own machine, where they may also set their own pace for the command in place of the skill's, and a scheduled command starts switched off.
- **Nobody answers** - the agent never asks and decides by itself.
- **The work** - what follows the slash command: one or more pull request numbers, or the id of an agent run (below), or nothing. When nothing follows it: every pull request merged since the start of the last run of this same command that had nothing after it and ended done, as the project's record of agent runs shows, or in the last 24 hours when there is no such run; less every pull request whose body has the line `Post-merge cleanup done.` (this skill's own pull requests end with it, and a pull request written up before it merged, below, got it then).
- **Pull requests unreadable** - it shows an error to the user saying why and stops; no work, it says so and stops.
- **Knowledge files** - from each pull request's changes and discussion: `knowledge-base/DECISIONS.md` (decisions taken and why), `knowledge-base/FACTS.md` (non-obvious facts), `knowledge-base/INSIGHTS.md` (insights), each created when missing; only what a future agent would need and cannot get from the code, and nothing already there.
- **Publishing** - nothing worth writing: nothing published. Otherwise the change is committed, then published as far as whoever started the agent said, and nothing is published when they said nothing. A pull request's body names the pull requests it covers and ends with the line `Post-merge cleanup done.`.
- **Last message** - each pull request covered and what was written.
- **Given an agent run's id** - the agent is on that run's branch and the run's pull request waits to merge until it is done: that pull request is the work. It reads the run in the project's record of agent runs (what it was asked, what its agent said) and the pull request's changes and discussion. A run it cannot read is an error shown to the user, and it stops. No other pull request is opened and no merge armed, since the pull request is merged for it once it is done. Nothing worth writing, nothing committed; otherwise the change is committed on the branch it is on and pushed, joining that pull request. Either way the line `Post-merge cleanup done.` is then added at the end of the pull request's body, the rest kept as it is. Its last message says what it wrote.
