---
name: post-merge-cleanup
description: After work is merged, queue a maintainability refactor and a security audit of the changes that need one, and bring the project's knowledge files up to date in a pull request for a person to review.
disable-model-invocation: true
---

Clean up after merged work. Nobody will answer you: never ask, decide yourself. The work is what follows the command: one or more pull request numbers. When nothing follows it, it is every pull request merged since the start of the last run of this same command that ended done, as the project's record of agent runs shows; when the project keeps no such record, or the record holds no such run, it is every pull request merged in the last 24 hours. If the pull requests cannot be read, show an error to the user saying why and stop. Skip a pull request that is itself a maintainability refactor, a security audit, or only an update of the knowledge files below: cleaning up after it would start the same work again. Read each remaining pull request: its changes and its discussion. If its changes are not trivial and have refactor potential, put an entry on the agent queue asking to refactor the changes it introduced to make them as maintainable as possible, finding their maintainability red flags and fixing them. If its changes can potentially lead to security issues, put an entry on the agent queue asking for an exhaustive security audit of the changes it introduced, listing every aspect considered with a verdict, each security issue found fixed in its own commit. Each entry goes at a low priority, names the pull request by its number and its title, and says the whole job in words, since the agent that works it reads only the entry. Skip an entry whose work is already on the queue. A write to the queue that is rejected because someone else wrote first is tried once more, after reading again. If this project has no AI queue, show an error to the user saying the queue work was skipped, queue nothing, and do the rest. Then bring the project's knowledge files up to date from the changes and the discussions of those pull requests, creating a file that is missing: `knowledge-base/DECISIONS.md`, the decisions taken and why; `knowledge-base/FACTS.md`, the non-obvious facts relevant to the project; `knowledge-base/INSIGHTS.md`, the insights relevant to the project. Only write what a future agent would need and cannot get from the code itself, and nothing the files already say. Commit the change on your branch. Then publish it: push your branch and open its pull request, its body naming the pull requests it covers, and leave the merge to a person. If nothing is worth writing into the knowledge files, publish nothing. Your last message lists each pull request covered and what you queued for it. If no pull request was merged, say so and stop.
