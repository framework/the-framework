The `tickets` skill's widget [1] for the dashboard: one page, Tickets, mounted at `/tickets`, showing the tickets of every project that has this package — the whole backlog filtered, sorted and grouped, one ticket's own page, and a ticket's plan — and one card on the Overview, Hot tickets, the tickets agents hold and the ones flagged high priority; every read and change through the same `tickets` command an agent [2] runs, and everything else the pages need — a run started, a launcher opened, the project's runs, the actions other widgets offer on a link [3] — through the dashboard's host. The package exports the widget as `./dashboard` (`dist/dashboard/dashboard.js` and its stylesheet), which is how the dashboard finds it; the dashboard itself never names this package.

## Context

**User story**: the user clicks Tickets in the dashboard's sidebar and sees every project's backlog; narrows it, sorts it, ticks a few rows and hands them to the queue; opens a ticket, reads it whole, lifts a dead agent's claim; opens its plan and resumes the agent that wrote it; starts an agent on a ticket from its row; on the Overview, sees which tickets agents hold and which are flagged high priority. A project that does not depend on this package shows no tickets here, and a dashboard with no project depending on it shows no Tickets row and no Hot tickets card at all.

**Business logic story**: the pages read with `tickets list --local`, `tickets show <file> --local` and `tickets meta --local`, run by the dashboard in each project (this machine's copy of the branch, no fetch, so polling is cheap), and write with `tickets release <file> --force`, run as an act so the dashboard reads the change back at once. What the pages compose with other skills goes through the host and names none of them: a claim's holder is matched against the project's runs by id, a plan's author is the run whose ask named the plan, a start hands a prompt to the dashboard, which starts the run with the user's picks and lands on it, and a ticket is handed as a link to whatever actions the installed widgets offer. The rules are in `../src/widget.ts`, tested there; the pages bind them to React and to the host.

## Glossary

[1] widget: a browser module one of a project's packages brings to the dashboard, named by the package's `exports["./dashboard"]`; it adds pages and Overview cards to the dashboard and reads and changes its data through its own package's command.
[2] agent: the unit of work: one task worked by a coding agent in its own checkout, on its own branch, started through the project's start hook and shown in the dashboard from the files its tool keeps. The dashboard also calls one "a run".
[3] link: the name of some work and where it points, as a dashboard page shows it: a text, an optional target (a path inside the project's repository) and an optional priority from 0 to 10; the dashboard puts beside it whatever verbs the installed widgets offer on links ("Add to queue" when the project has the queue package).

## Business logic — TL;DR

- **The widget's definition** (`index.tsx`) - one page at `/tickets`, labelled Tickets with a ticket icon, one Overview card, Hot tickets, at order 20 (after the queue package's card), and the stylesheet beside the module; no actions on links of its own.
- **The page, routed on its address** (`TicketsWidgetPage.tsx`) - nothing after `/tickets` is the list, a project and a ticket's filename its page, `plan` after those its plan, anything else "No such ticket page." with the way back.
- **The list** (`TicketsPage.tsx`, `TicketFilterBar.tsx`, `lib/ticket-filter.ts`, `lib/ticket-priority.ts`) - every project's tickets from `tickets list --local`, their claims' holders matched to the project's runs, filtered, sorted and grouped by a view the address carries, with the shown or selected tickets handed as links to other widgets' actions, and rows that open a ticket, its plan or the run holding it, and start an agent on it.
- **One project's rows** (`TicketsPanel.tsx`, `UpdateTicketsButton.tsx`) - each ticket as a one-liner with its start and plan columns, the last-import stamp from `tickets meta --local`, and "Update tickets" starting the project's `/update-tickets` command.
- **One ticket** (`TicketDetailPage.tsx`, `TicketPageShell.tsx`) - the whole ticket from `tickets show <file> --local`, the ticket as a link for other widgets' actions, and "Release lock" running `tickets release <file> --force`.
- **Its plan** (`TicketPlanPage.tsx`) - the plan from the same `show`, with the way back to the run whose ask named it.
- **The Hot tickets card** (`HotTicketsCard.tsx`) - across every project, the claimed tickets with their holders and the unclaimed ones at priority 7 or up, from `tickets list --local` and the project's runs every 30 seconds; a row opens the ticket, a claim opens its run, and other widgets' actions on the ticket as a link sit beside each row.
- **What the pages show as tickets** (`lib/types.ts`) - the command's rows, with the run behind a claim when the lock names one of the project's runs.
- **The pages under test** (`test-host.tsx`) - a fake host whose commands answer from a table and whose every service is a spy, so the pages are tested without a dashboard.
- **Built to share, not to bundle** (`vite.config.ts`, `vitest.config.ts`, `vitest.setup.ts`, `dashboard.css`, `tsconfig.json`) - the module leaves React and `framework/widget` as bare imports the dashboard supplies, and its stylesheet holds only its own utilities, coloured by the dashboard's theme file; these files carry no business logic beyond that.
