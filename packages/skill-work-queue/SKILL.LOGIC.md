The `work-queue` command skill: the prompt of the agent a runner starts on the queued work, as a skill file the coding agent's harness expands from `/work-queue`. Marked so that only a person or a runner invokes it; the agent never chooses it by itself.

## Context

**User story**: a runner, the scheduler or a person, starts an agent with `/work-queue`. The agent reads the skills in its checkout, takes the first queued task, claims its ticket, works it in its own branch, commits, publishes the work as far as whoever started it said (a run started at the publish level `merge`, picked in the launcher or, for a scheduled run, picked for the command on that machine, gets a pull request that names the ticket, set to merge on its own once its checks pass), marks the queue entry done, writes the pull request on the ticket, releases its claim, and stops; the ticket closes when the pull request merges. An agent that finds nothing queued says so and stops.

**Business logic story**: the skill's body, the prompt the agent reads, names no skill and no command, and assumes no capability. The check of the `schedule` key in its front matter does name commands (`npx queue`, `npx tickets`): the scheduler, `agent-scheduler`, runs that check, and the agent is not given it as an instruction. The agent composes the capability skills in its checkout on its own (tickets, queue, branches, the git host's); what this file carries is the rules of the job, which an unattended agent cannot infer from the skills alone. The skill names no publish level: how far the work is published is said by whoever started the agent (the launcher's publish menu, or the publish level a person picked on their machine for the scheduled command; the runner tells the agent the level in one sentence after its prompt), and the skill says to follow it. Where the job is broken without a capability, the skill says so in capability words and stops.

## Business logic — TL;DR

- **The `schedule` key** - the front matter's `schedule` key, which the scheduler reads, makes the skill one scheduled command, `work-queue`, with no interval. Its check, a shell line the scheduler runs at the project's root, prints the queue's open entries less each one that names a ticket someone has claimed; the command is due while that list is not empty. Its `waits-for` line, the plain words a person is shown for the check, reads "when the queue holds a task nobody has claimed". It gives no `agents`, so one run at a time across every machine. The `schedule` key says nothing about whether a command runs on a machine or how far its runs publish: each person sets those for their own machine, where they may also set their own pace for the command in place of the skill's, and a scheduled command starts switched off.
- **Nobody answers** - the agent never asks and decides by itself.
- **One task, the first** - it takes the first open entry of the queue and no other; an entry `Create tickets/<name>.plan.md`, the one a plan is queued as, names the ticket `tickets/<name>.md`. When the entry names a ticket it claims the ticket first; when someone else holds the claim it leaves that entry and takes the next one, and when every entry is claimed it says so and stops. An entry whose ticket no longer exists is marked done and the agent stops.
- **A ticket not to work** - a ticket that is waiting or in review, as the ticketing system says, gets nothing done on it, not even a plan: its queue entry is marked done, the claim released, and the agent stops. A ticket found to have nothing to do until something outside the work happens gets what it waits on as its `Waiting:` line above the title, its entry marked done and the claim released; a waiting ticket is never closed here.
- **Commit, publish** - it commits on its own branch; once the work is committed it publishes it as far as whoever started it said, and publishes nothing when they said nothing. When the push or the pull request fails, the entry stays queued, the claim is released, and the run ends saying what failed.
- **The ticket goes into review, not closed** - the skill leaves this to the ticketing system's own rule for queued work, which the agent follows: the pull request's body names the ticket it closes (`Closes tickets/<file>`) and its issue (`Closes #<number>`), the queue entry is marked done, the pull request written on the ticket as its `PR:` line and the claim released; the ticket closes when the pull request merges, never here.
- **A task without a pull request** - it ends when what it writes is saved where it belongs, and its queue entry is marked done. A plan is written as the ticket's plan, not on the agent's branch; the claim is released and the ticket stays open. A task whose whole work is changing other tickets finishes its own ticket, and the agent closes it, so it is not queued again.
- **An entry that is no ticket** - the skill says nothing of its own: the claim, the `Closes` lines and the `PR:` line are each for an entry's ticket, so an entry that names none is worked as its text says, with none of them.
- **Nothing queued** - the skill's body says nothing of its own: the check of its `schedule` key lets the scheduler start a run only while the queue holds an entry that names no claimed ticket, and an agent started by hand on an empty queue says so without being told.
- **A missing capability** - with no AI queue, or a task that needs a ticketing system or a way to open a pull request the project lacks, it ends with an error saying so and stops; the note is in capability words and names no skill.
