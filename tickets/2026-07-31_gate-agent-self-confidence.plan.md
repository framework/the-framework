# [Plan] New gate: let agent gauge uncertainty

Concrete plan for confidence-conditional gating: the agent self-rates its finished work in a new signal block, and the framework branches on the value at the unattended points of no return — the session's own auto-merge and CI watch's merge-on-green — withholding the merge (draft PR + reported reason) when confidence is low; the interactive "ask the user" half is staged as v2.

## TLDR

The ticket's gate differs from the existing #326 gate family in one structural way: ambiguity/scope/alternatives are *blocking asks before or during* work, while this one fires *after* work — including on sessions with nobody attached (backlog drain, CI-fix agents), where a blocking ask auto-resolves to the recommended option and therefore cannot be the mechanism. So the recommended shape is a **signal, not an await gate**: a `confidence` block in the #551 signal protocol, emitted in the same turn as `ready-for-merge`, parsed in `turn-gate.ts` like its siblings, recorded on the journal and agent meta, and consulted where merges are decided:

1. **Session auto-merge** — `maybeAutoHandoff` (`cli.ts:987`): low confidence becomes a new `MergeWithheldReason` (`'low-confidence'`, `events.ts:103-107`), so push and PR still go ahead and the PR opens as a **draft** with the reason reported — the settled withheld-not-skipped doctrine (#1363/#1390). A false alarm costs a human glance (the Merge button, #1391), never lost work.
2. **CI watch** — the OP's own example (CI red → fix → confident? merge : ask): the fix prompt (`ciFixPrompt`, `ci-watch.ts:69`) gains the same instruction, the fix session's meta carries its confidence, and the sweep's merge-on-green half declines to land a PR whose latest fix attempt reported low confidence — it surfaces it for a human instead.

Precedents already in the codebase: plan files self-rate `Uncertainty: 0-10` and the value steers whether human intervention is needed (ticketing format); the #326 variability rubric has the agent score its own problems 0-10; the suggest-tickets preset expresses confidence as default-checked options. This ticket is the runtime twin of the plan-file `Uncertainty` value.

Relation to #1591 (AC-enforcement merge gate, planned in `2026-08-18_ac-enforcement-merge-gate.plan.md`): complementary, not competing. Self-assessment is **free** (no extra driver turn) but self-serving — it catches "I'm not sure this is right". The external gate agent costs a turn and catches "the agent is sure but wrong". If both land, the free check runs first and both report through the same withheld-merge surface.

## Problems

1. **How confidence crosses from agent to framework — uncertainty 5.** A blocking gate doesn't work unattended (headless gates fall back to the recommended pick, `await-gate.ts`), and "just don't call setReadyForMerge()" conflates *unfinished* with *finished-but-unsure* — the withheld reason would lie (`'not-ready-for-merge'`), and it would also skip the on-before-mergeable knowledge folding. Several real transports exist (new signal block / body on `ready-for-merge` / prompt-only).
2. **Scale and threshold — uncertainty 5.** Self-scores are notoriously overconfident and miscalibrated; a bare "rate your confidence 0-10" produces mostly 8s and 9s. What rubric, what polarity (confidence vs uncertainty), what cutoff, and who sets it.
3. **Which paths branch — uncertainty 4.** Session auto-merge only, or also CI watch's merge-on-green (the OP's literal scenario), or also an interactive ask when a human is attached.
4. **Absent signal: fail-open or fail-closed — uncertainty 4.** A driver that ignores the new instruction emits no block. Treating absence as low confidence blocks every merge until every driver reliably complies; treating it as fine means the brake only exists when the agent remembers to install it.
5. **Interplay with #1591 — uncertainty 3.** Both withhold merges at the same seam; ordering and shared reporting need one sentence of design, not machinery.

## Solutions

1. **Transport — recommended: a new `confidence` signal block** in `prompts/protocols/signal.md` (#551 convention), emitted in the same turn as `ready-for-merge`. Body: first line the score, below it one required line naming *what could be wrong* (the accountability line — a number without a stated doubt is a vibe). Parsed by a `parseConfidence()` in `turn-gate.ts` (last block wins, like its siblings — the system prompt already says to re-run the gates "anytime you make new changes", so a later re-gauge supersedes), emitted as an event by `createTurnSignalEmitter` (`turn-gate.ts:363`), recorded by the cli journal exactly like `ready-for-merge` (`cli.ts:601`).
   - *Alternative (a): body on the `ready-for-merge` block.* Tempting (confidence only matters once work is declared done) but couples two signals: `ready-for-merge` is pinned body-less by its SPEC, re-emission without the body would silently drop the score, and `open-pr` re-emission shows the value of independent blocks.
   - *Alternative (b): prompt-only — low confidence means raise an `await-choices` ("Merge / Hold for review") instead of new machinery.* Rejected as the mechanism: on unattended sessions the gate auto-answers with the recommended pick, so the framework state (armed + authorized merge) never actually changes; the branch would exist only when a human is watching, which is precisely when it's least needed. Survives as the v2 interactive layer (Solution/Problem 3).
   - *Alternative (c): no signal — an unsure agent withholds `setReadyForMerge()`.* Already possible today, and wrong: see Problem 1.
2. **Scale — recommended: 0-10 with a behavioral rubric, uncertainty polarity, fixed threshold.** Match the ticket title ("gauge uncertainty") and the plan-file precedent (`Uncertainty: 0-10`, 0 = clearly no human intervention needed): the block reports *uncertainty*, and the framework branches on `uncertainty > threshold`. Rubric phrased behaviorally, not introspectively — "0: you verified the change end-to-end (tests/build run, behavior seen) and a competent reviewer would have nothing to demand changed; 10: you could not verify it and a reviewer may well reject it" — verification questions calibrate far better than "how confident are you". Threshold: one named constant (merge proceeds at uncertainty ≤ 2), no preference knob in v1 — the zero-users rule says don't add the knob until someone asks; the constant's SPEC records it as the tunable.
   - *Alternative: binary `confident`/`unsure`.* Simpler and harder to game with an 8-out-of-10 hedge, but loses the dashboard signal and breaks with both numeric precedents; the threshold turns the scalar into the same binary at the seam anyway, so the scalar costs nothing extra.
3. **Scope — recommended v1: both unattended merge points; interactive ask deferred to v2.**
   - *Session auto-merge*: in `maybeAutoHandoff`, extend the `withheldMerge()` deps (`dashboard/agent-handoff.ts:610`) with the journal's latest uncertainty; a value above threshold maps to the new reason `'low-confidence'`, flips `armed.merge` off, PR opens as draft with the agent's own stated doubt threaded into the PR description (best-effort, like the rest of the handoff cosmetics).
   - *CI watch*: `ciFixPrompt` gains the gauge instruction (the fix agent is an ordinary session, so the signal machinery is already there); the sweep's merge half — which already discovers fix attempts by scanning agent metas for the `[ci-fix]` marker (`ci-watch.ts:45`) — declines to merge a green PR whose newest fix attempt reported uncertainty above threshold, logs why (once, per the ci-watch logging doctrine), and leaves it for a human; best-effort PR comment carrying the agent's stated doubt so the reviewer sees it on GitHub. This is exactly the OP's "CI red → agent fixes → confident? auto-merge : ask for review".
   - *v2, interactive*: when a session is live-chatted, low confidence additionally raises an `await-choices` — "Merge anyway / Hold for my review (stop)" with **Hold** as `recommended`, which per the existing gate doctrine is also the safe unattended fallback. v1 already gives the human the same power (withheld reason on the dashboard + the Merge button #1391), so the ask is convenience, not capability — fine to stage.
4. **Absent signal — recommended: fail-open in v1, said out loud.** The signal is an *additional* brake on top of the existing authorization (`ready-for-merge` + no open session TODOs); absence means the merge proceeds exactly as today, with a log line noting no confidence was reported. Fail-closed would make auto-merge unusable the day a driver gets flaky about emitting blocks, and unlike #1591's gate (where an inconclusive verdict means the check *ran and failed to answer*), absence here means the check never ran. Revisit toward fail-closed once emission proves reliable — the flip is one line in the `withheldMerge` mapping.
5. **Interplay with #1591 — recommended: free check first.** If both land: consult the journal's uncertainty before spending the gate agent's driver turn — an agent that already flagged itself needs no external audit to withhold. Shared surface, no shared machinery: both are just values of `MergeWithheldReason`.

## Considerations

- **Self-assessment is a complement, not a safety boundary**: an overconfident agent sails through. That's the ticket's own framing (middle ground between full autonomy and always-ask), and why #1591's external audit remains worth building separately.
- **Where the prompt instruction lives**: the block definition in `prompts/protocols/signal.md` (+ SPEC), the gauge instruction + rubric in `system_prompt.md`'s "After applying changes" section (`prompts/system_prompt.md:56-60`, + SPEC) — right where `setReadyForMerge()` is already decided — and the same instruction appended to `ciFixPrompt`. Prompts are compiled by `scripts/gen-prompts.mjs` into `prompts.generated.ts`. Per the repo rule, read sdd.md before touching any SPEC.md.
- **Parsing is forgiving, effect is strict**: `parseConfidence` accepts `N` or `N/10` on the first line; a malformed score is treated as absent (fail-open per Solution 4), never a crash. Pure function, own tests, like `parseErrors`/`parseReadyForMerge`.
- **Events and meta**: new `{ kind: 'confidence'; score: number; note: string }` event in `events.ts`; `AgentProgress` (`agent-view.ts:15`) and the persisted agent meta gain the latest value — the meta is what CI watch reads, and what lets the dashboard show it. Extend `MergeWithheldReason` with `'low-confidence'`; the existing withheld-merge surface (`FEATURES-SPEC.md:119`) renders the new reason with the agent's stated doubt — no new dashboard component needed in v1.
- **What the score covers is pinned in the prompt**: "the change is correct, complete, and safe to land unreviewed" — not "I followed the instructions". Without this pin agents rate task compliance, which is always high.
- **CI-watch bounds unchanged**: the two-fix-attempts cap and the one-week watch window stay; a low-confidence decline is a terminal surface-for-human, not a third retry path.
- **`ready-for-merge` without `confidence` in the same turn but present in an earlier one**: journal keeps the latest value across turns (an agent may gauge, then fix one more nit, then declare ready) — the value is stale-tolerant by design since the prompt requires re-gauging after new changes.
- **No new preference knob, no per-model calibration, no telemetry in v1** — zero-users rule. If scores prove uniformly inflated, tighten the rubric (a prompt change) before adding machinery.
- **Naming**: block tag `confidence` (matches the ticket slug and reads naturally as a signal name) even though the scale is uncertainty-polarity; the block's own first-line format makes the polarity unambiguous (`uncertainty: N`). Alternatively tag it `self-check`. Cosmetic — decide at implementation.
- **Tests**: parser (`turn-gate.test.ts`); `withheldMerge` mapping incl. absent-signal fail-open (`agent-handoff` tests); cli wiring with the fake driver; ci-watch sweep declining a low-confidence green PR (`ci-watch.test.ts`); prompt-render pins for the rubric text.
- **SPEC discipline** (per sdd.md): `signal.SPEC.md`, `system_prompt.SPEC.md`, `turn-gate.SPEC.md`, `events` docs, `agent-handoff` doc block, `ci-watch.SPEC.md`; `FEATURES-SPEC.md` gains a line under the auto-merge cluster (~:116-122), e.g. "The agent gauges its own uncertainty at ready-for-merge; high uncertainty withholds an unattended merge (draft PR / held CI-watch PR, reason + the agent's stated doubt reported)".

## Implementation

1. **Signal protocol**: define the `confidence` block in `prompts/protocols/signal.md` (+ SPEC): first line `uncertainty: N` (0-10), below it one line naming the doubt; emit alongside `ready-for-merge`, re-emit after further changes. Regenerate `prompts.generated.ts`.
2. **System prompt**: extend "After applying changes" (`prompts/system_prompt.md`) with the gauge + behavioral rubric (+ SPEC updates; read sdd.md first).
3. **Parser**: `parseConfidence(text)` in `turn-gate.ts` (+ SPEC + tests); wire into `createTurnSignalEmitter`.
4. **Events**: `{ kind: 'confidence' }` event; `MergeWithheldReason` + `'low-confidence'`; `AgentProgress`/meta carry the latest value.
5. **Session merge**: cli journal records it (`cli.ts:601` sibling); `maybeAutoHandoff` threads it into `withheldMerge()` (extended deps + threshold constant, `agent-handoff.ts:610`); low → reason `'low-confidence'`, draft PR, doubt line in the PR body.
6. **CI watch**: gauge instruction in `ciFixPrompt`; merge half reads the newest fix attempt's meta and declines above-threshold PRs with a logged reason + best-effort PR comment (+ tests).
7. **Docs**: SPEC updates + the `FEATURES-SPEC.md` feature line.
8. **v2 (separate PR, after v1 proves out)**: interactive `await-choices` on low confidence for live sessions ("Merge anyway / Hold for my review", Hold recommended); threshold preference and fail-closed absence if emission proves reliable; #1591 ordering when that gate lands.
