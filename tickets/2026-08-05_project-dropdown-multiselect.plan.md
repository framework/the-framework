# [Plan] Project dropdown

Concrete plan to replace the sidebar's Project collapsible with a top-of-sidebar multi-select filter dropdown scoping every dashboard surface — with the two calls that need a human (where the filter state lives; what happens to the tickets page's own project facet) laid out as decisions.

## TLDR

Today, project scoping *is* navigation: selecting a project routes to `/{projectId}` ("The URL is the selection", `dashboard/App.SPEC.md:11`), and the sidebar's `ProjectsNav` collapsible (`dashboard/components/AgentHistory.tsx:353-435`) is a nav list, not a filter. The code explicitly anticipates this ticket: `AgentHistory.tsx:211-213` and `:350-352` say "the filter-vs-navigate call is still open".

The change flips project scoping from *navigate* to *filter*:

- New `ProjectFilter` component at the very top of the sidebar, directly under `BrandLink` (`AgentHistory.tsx:191-193`), visually separated from the nav buttons below; `ProjectsNav` is deleted.
- Selection filters every cross-project surface **client-side, with zero server change**: all cross-project reads (`onDashboard`, `onQueue`, `onAllTickets`, `onRecentAgents`, `onHotTickets`, `onOpenQuestions`, `onInterventions`, `onActivity` — `src/dashboard-rpc/reads.ts:219-271`) take no arguments and return rows already tagged `projectId`; the tickets page proves the pattern (`lib/ticket-filter.ts:193`).
- Recommended: filter state as a daemon preference (`autoPmProject` precedent, `src/registry.ts:140-149`), empty = All; dropdown built on `Popover` + `Checkbox` rows (the `CheckFacet` precedent, `dashboard/components/TicketFilterBar.tsx:172-189`) — **not** `DropdownMenuCheckboxItem`, because checkbox-click and row-click must do different things.
- `/{projectId}` routes survive as *navigation* (project home / agent view); the dropdown only filters, never navigates.

The ticket is labeled `only-if-quick-win`; the full scope is not one (Effort 4). A genuine quick-win slice exists (see Considerations) but leaves the state-home decision half-made.

## Problems

1. **Where the filter state lives — uncertainty 6.** Two doctrines collide. (a) "The URL is the selection" (`App.SPEC.md:11`; doctrine block `App.tsx:46-59`) and the tickets view mirrors its whole filter — projects included — to the URL for shareability (`FEATURES-SPEC.md:98`, codec `lib/ticket-filter.ts:386,412`). (b) Sticky cross-page UI state lives in daemon preferences, explicitly "no more localStorage" (`lib/preferences.ts:8-9`), with `autoPmProject` as the exact precedent of a remembered project id (`src/registry.ts:140-149`). A global filter riding the URL means every `formatRoute`/`go` call (`lib/route.ts:75-88`, helpers `App.tsx:190-246`) must carry a query param through every navigation; a preference means the filter isn't shareable/bookmarkable.
2. **Fate of the tickets page's own project facet — uncertainty 5.** `TicketsPage` already has a project multi-select facet with counts and URL codec (`TicketFilterBar.tsx:327-339`, `lib/ticket-filter.ts:193,386,412`). Keeping both means two project filters compose (confusing); removing the facet is a **feature removal**, gated on human approval (`FEATURES-SPEC.md:6`, facet listed at `:96`, URL mirroring at `:98`).
3. **What navigation remains, and what the sidebar recents show — uncertainty 4.** `/{projectId}` (project home/launcher) and `/{projectId}/{agentId}` must stay reachable. Sidebar recents are currently navigation-scoped — the project's own agents via `useAgents(projectId)` when inside a project, pooled `onRecentAgents()` at root (`AgentHistory.tsx:146,157-172`) — which contradicts "recent sessions filter to the selection".
4. **Visual treatment of the trigger/top section — uncertainty 5.** The ticket says it is "open for brainstorming"; low-stakes but genuinely open.

## Solutions

1. **State home — recommended: daemon preference** `projectFilter?: string[]` in `Preferences` (`src/registry.ts:51-168`), absent/empty = All, written via `patchPreferences` patch-only writes (`lib/preferences.ts:229`). Sticky across pages, reloads and tabs (preferences refresh on focus, `lib/preferences.ts:150-161`); matches how a *global* scope should feel — you set it once, everything follows. Alternatives: (a) global URL query `?projects=a,b` appended by `formatRoute`/parsed by `parseRoute` — honors the URL doctrine and is shareable, at the cost of threading it through every navigation call and growing every URL; defensible if shareable dashboards matter. (b) Quick-win shortcut: React state in the shell only — cheapest, lost on reload, trivially upgradable to either of the above later.
2. **Tickets facet — recommended: remove it**; the global dropdown becomes the single project scope (zero users + "prefer clean code" per `AGENTS.md`; two stacked project filters is exactly the confusion the ticket wants to end). Delete the facet (`TicketFilterBar.tsx:327-339`), the predicate (`lib/ticket-filter.ts:193`), and the `?project` codec (`:386,412`); `FEATURES-SPEC.md:96` loses "project" from the facet list — **requires explicit human approval before implementation**. Alternative: keep the facet, computing its options/counts within the global scope (facet narrows further); pick this if tickets-view URLs must keep carrying project scope. Rejected: facet as a mirror of the global filter — two controls, one state.
3. **Navigation — recommended: the dropdown only filters.** Checkbox toggles membership; row-click selects only that project (both per ticket) — neither navigates. Project home stays reachable through `NewButton`'s picker (`AgentHistory.tsx:441-517`) and agent rows as today; a URL pasted to `/{proj}/{agent}` always renders regardless of filter (the filter scopes lists, never blocks pages). Sidebar recents become *always* pooled-and-filtered `onRecentAgents()` — one code path, matching the ticket — dropping the `useAgents(projectId)` sidebar variant (`lib/use-agents.ts:8-20` stays for whatever else needs it). Alternative: intersect the filter with the currently-navigated project when inside one — rejected as surprising (sidebar contents would change by page).
4. **Visual treatment — proposal** (brainstorm welcome): a full-width bordered trigger directly under the wordmark showing "All projects" / the single name / "N projects", a chevron, and a red dot when any project has errors (keeps `FEATURES-SPEC.md:91` true at a glance); a `SidebarSeparator` below it so it reads as the scope for everything underneath, nav buttons (`New`, `Overview`, `Tickets`) visually regrouped after the separator. Popover contents: an "All" row on top, then projects with selected-on-top ordering, each row = checkbox + name + activated/error dot with tooltip (port from `AgentHistory.tsx:398-417`, reuse `projectErrorTitle`), and an "Add project" row at the bottom opening the existing `AddProjectPanel` (`AgentHistory.tsx:432`).

## Considerations

- **Empty selection means All** — the tickets-facet precedent (`lib/ticket-filter.ts:193`: empty list = no constraint). Unchecking the last selected project returns to All; there is never a "nothing shown" state. The All row's checkbox reads checked exactly when the explicit selection is empty; checking a project while on All starts the explicit selection at {that project}.
- **Click semantics** (per ticket): checkbox click toggles and keeps the popover open — the codebase already encodes this intent (`ui/dropdown-menu.tsx:69`, `closeOnClick = false`: "Keep the menu open when toggling"); row-click outside the checkbox = "only this project" and closes. This two-target row is why `Popover` + custom rows (modeled on `OptionRow`, `TicketFilterBar.tsx:49-69`) beats `DropdownMenuCheckboxItem`, where the whole row is the checkbox.
- **Selected-on-top must not re-sort live** — compute the ordering when the popover opens, not on every toggle, or rows jump under the cursor mid-interaction.
- **Tooltips** (per ticket): trigger — "Filters everything: overview, tickets, recent sessions"; All row — "Show every project"; row body — "Show only <name>"; checkbox — "Include/exclude <name>"; dots keep their activated/error tooltips. Use `ui/tooltip.tsx` (portaled, delay 0); tests must use `test-utils.ts` `hoverTooltip` (`:10-23`).
- **What filters vs what doesn't**: data views filter — Overview cards (agents working now, AI queue, hot tickets, open questions, human queue), tickets, sidebar recents, activity, and the `interventionCount` badge on the Overview button (`AgentHistory.tsx:207`) so numbers match pages. Configuration surfaces don't — `NewButton`'s picker (you can start an agent anywhere), `RoutineWork`'s project select (`RoutineWork.tsx:238`, it's a setting), Settings. `TicketsPage` reads `onQueue()` directly (`TicketsPage.tsx:116`) — filter there too, not just in the shell.
- **Filtering lives in the shell** (`App.tsx`, where the cross-project polls already live, `:97-146`) so components stay dumb and every consumer gets scoped data uniformly.
- **Stale ids**: a preference may hold ids of removed projects — ignore ids not in `onProjects()` when filtering and drop them on the next write; no migration/cleanup code beyond that (zero-migration doctrine, `MEMORY.md`).
- **SPEC discipline** (per sdd.md): new `ProjectFilter.SPEC.md` + `ProjectFilter.test.SPEC.md`; update `AgentHistory.SPEC.md`, `App.SPEC.md` (the "URL is the selection" doctrine must be rewritten to "the URL is the *navigation*; the project scope is a filter"), `dashboard/SPEC.md:5` route/selection note, and `FEATURES-SPEC.md` (sidebar bullet `:90`, facet line `:96` if removed) — the FEATURES-SPEC.md delta is the approval artifact (`FEATURES-SPEC.md:6`).
- **Mobile/keyboard/theming**: sidebar is a fixed always-visible column (`collapsible="none"`, `AgentHistory.tsx:185` short-circuiting `ui/sidebar.tsx:143-153`), so no drawer work; Base UI Popover brings focus handling; reuse `--sidebar-*` tokens for the trigger like existing rows.
- **Quick-win slice**, if the label is to be honored strictly (Effort ~2): shell-state filter (Solutions 1b), filter Overview + recents + tickets universe, keep the tickets facet untouched, skip the preference and FEATURES-SPEC facet removal. Ships the visible UX; defers both human decisions. The full plan then becomes a follow-up.
- **Design gallery**: optionally register the new component in `dashboard/design/previews.tsx` (`PREVIEWS`, `:317-405`); neither the sidebar nor `ProjectsNav` has a preview today, so this is nice-to-have.

## Implementation

Order: decisions first — steps 1 and 4 encode Problems 1 and 2 and need the human call before code lands.

1. **State**: add `projectFilter?: string[]` to `Preferences` (`src/registry.ts`), read via `usePreferences()`, write via `updatePreferences({ projectFilter })`. (If the URL alternative is chosen instead: extend `Route`/`parseRoute`/`formatRoute` in `lib/route.ts` with a `projects` query and thread it through the `go` helpers in `App.tsx:190-246`.)
2. **Component**: `dashboard/components/ProjectFilter.tsx` (+ SPEC, test, test SPEC) — `Popover` trigger + rows modeled on `CheckFacet`/`OptionRow`/`FacetTrigger` (`TicketFilterBar.tsx:49-81,172-189`) with `ui/checkbox` and `ui/tooltip`; All row; selected-first ordering computed on open; activated/error dots ported from `ProjectsNav`; Add-project row wiring the existing `AddProjectPanel` + `onProjectAdded` refresh (`App.tsx:399-402`); trigger label + error dot.
3. **Sidebar rewiring** (`AgentHistory.tsx`): render `ProjectFilter` under `BrandLink` followed by `SidebarSeparator`; delete `ProjectsNav` (`:353-435`), its render site (`:214-219`), and the two anticipatory comments (`:211-213`, `:350-352`); recents switch to always-pooled `onRecentAgents()` (drop the sidebar's `useAgents(projectId)` branch, `App.tsx:78`, `AgentHistory.tsx:146`).
4. **Filtering**: in `App.tsx`, derive the active id set (empty ⇒ all) and filter the rows of `onDashboard`/`onQueue`/`onHotTickets`/`onOpenQuestions`/`onInterventions`/`onActivity`/`onRecentAgents` before passing down; scope `interventionCount`; in `TicketsPage.tsx`, scope `onAllTickets`/`onQueue` reads and remove the project facet + codec + predicate (pending the Problem-2 decision; else scope facet counts within the filter).
5. **Specs & features**: rewrite the `App.tsx:46-59` doctrine block and `App.SPEC.md`; update `AgentHistory.SPEC.md`, `dashboard/SPEC.md`, `FEATURES-SPEC.md` (needs the human sign-off).
6. **Tests**: `ProjectFilter.test.tsx` under `SidebarProvider` per `AgentHistory.test.tsx` conventions (`:1-39`) — checkbox toggle vs row-click vs All, selected-first computed on open, tooltips via `hoverTooltip`, add-project row; shell-level test that queue/recents/badge scope together; adjust `TicketsPage`/`TicketFilterBar` tests. `pnpm test` + `pnpm typecheck`.
