# [Plan] AC enforcement: a merge gate checking the diff against AGENTS.md and the ticket's acceptance criteria

Concrete plan for both layers — AGENTS.md into every run's context (cheap pointer), and a gate agent at the auto-merge decision that re-reads the rules against the actual diff and withholds the merge on violations — with the verdict-transport and fail-open/fail-closed calls laid out as decisions.

## TLDR

The two layers the ticket names map onto existing seams, cheapest first:

1. **Rules into context** — the #326 system prompt's `Context:` bullets (`CONTEXT_DOCS`, `packages/framework/src/system-prompt.ts:116-139`) carry `GOAL.md`, knowledge docs, tickets, the queue — but not `AGENTS.md`. One added `ContextDoc` bullet fixes the TF-driven half. Both current CLI drivers already get the rules natively (Claude Code auto-loads `CLAUDE.md` → `@AGENTS.md` per #1590; Codex reads `AGENTS.md` by its own convention), so this layer is a pointer for driver-independence, not the enforcement.
2. **Enforce at the gate** — the ticket points at `on-before-mergeable` (`cli.ts:961-982`), but the better hook is one step later: inside `maybeAutoHandoff` (`cli.ts:987`), where the merge-authorization gate already exists (`withheldMerge`, `dashboard/agent-handoff.ts:610-614`) and where `commitPendingWork` (`cli.ts:1005`) has already run, so the diff the gate reads is the diff that would land. A violation becomes a third `MergeWithheldReason` (`events.ts:103-107`): the push and PR still go ahead, the PR just opens as a **draft** with the violations reported — exactly the settled withheld-not-skipped doctrine (#1363/#1390), so a false positive costs a human review, never lost work.

v1 is one stock prompt ("list every AGENTS.md rule this diff violates; an empty list is required to proceed"). Per-ticket ACs and the SPEC.md human-ack rule are staged as follow-ups.

## Problems

1. **How the gate's verdict travels back — uncertainty 6.** The existing on-before-mergeable step spawns a full framework child (`spawnPromptAgent`, `cli.ts:1385`) whose only result is a clean-exit boolean — fine for "queue some TODO entries", useless for a check that must answer pass/fail-with-details. Something structured has to cross the process boundary (or the boundary has to go).
2. **What arms the gate — uncertainty 5.** `onBeforeMergeable` is an opt-in flag (`SESSION_DEFAULTS`, `cli.ts:296`). Is the gate another flag, a rider on that flag, or implied by auto-merge being armed?
3. **Fail-open vs fail-closed — uncertainty 5.** The on-before-mergeable step is deliberately best-effort ("a failure is logged, never thrown", `cli.ts:1417`). A *gate* that fails open is decoration; a gate that fails closed on a flaky driver blocks merges for reasons unrelated to the diff.
4. **What a violation does — uncertainty 4.** Withhold only, or feed the violations back to the agent for a repair round first?
5. **Layer 1 mechanics — uncertainty 4.** Pointer bullet vs inlining AGENTS.md's content into the system block vs relying on driver-native memory loading.
6. **Where ticket ACs live (phase 2) — uncertainty 3.** Neither the ticketing format nor the plan format has a machine-findable AC section today.

## Solutions

1. **Verdict transport — recommended: run the gate in-process, not as a child.** `cli.ts` already imports `runAgent` (`cli.ts:24`); a `kind: 'prompt'`, `vanilla` in-process run returns the agent's final text directly, which the gate parses for a pinned machine-checkable tail (last non-empty line `VERDICT: pass` or `VERDICT: violations`, violations as the bullets above it). The spawn indirection exists for stdio/archive concerns that don't apply to a short read-only check, and in-process is the only option that needs no new IPC. Alternatives: (a) keep `spawnPromptAgent` and have the child write a report file the parent reads — works, but invents a file protocol for one consumer; (b) a new emit-protocol signal — heaviest, touches the turn-gate signal machinery for no added value.
2. **Arming — recommended: no new flag; the gate runs iff the merge is armed** (`armed.merge`, `cli.ts:1017`). The gate guards the unattended point of no return; when auto-merge is off a human reviews the PR anyway, and gating a draft PR spends a driver turn to tell a human what they're about to read themselves. This also decouples it from `onBeforeMergeable` (a *quality-queueing* preference, off by default — tying the safety gate to it would leave the common auto-merge path ungated). Alternatives: (a) its own `--merge-gate` flag, default on when merge is armed — adds a knob the zero-users rule says to skip until someone asks; (b) always-on at ready-for-merge, annotating draft PRs too — nice, but double cost for little marginal safety; natural later extension.
3. **Fail-closed, with the reason said out loud — recommended.** An unparseable verdict or a failed gate run withholds the merge with its own reason (`gate-inconclusive`), distinct from `gate-violations`. Rationale: withheld ≠ lost (draft PR + reported reason, `FEATURES-SPEC.md:119`), so the cost of failing closed is a human glance, while a fail-open gate silently reverts to today's behavior exactly when it malfunctions. The `fake` driver and stopped runs skip the gate like every sibling step (`cli.ts:993-994` precedent) — a skip, not an inconclusive.
4. **Violation handling — recommended: v1 withholds and reports only.** The violation list rides the withheld-merge event and the PR body, so the human (or a follow-up agent) sees exactly which rule tripped. A repair round — one extra turn to the *same* driver session ("fix or justify each violation"), then one re-check — is the natural v2; bounded to one iteration to avoid a self-argument loop. Rejected for v1: silently queueing a TODO entry (violations are precisely what must not land first and get fixed later).
5. **Layer 1 — recommended: a `ContextDoc` pointer bullet** (`{ path: 'AGENTS.md', comment: 'project rules — every change must comply' }` in `CONTEXT_DOCS`). No `node:fs` in `system-prompt.ts` is a hard rule (`system-prompt.ts:5-8`, the dashboard renders the prompt in the browser), so inlining content means threading it through `system-prompt-file.ts` like `SYSTEM.md` — and for the Claude Code driver it would *duplicate* what `CLAUDE.md → @AGENTS.md` (#1590) already injects. The pointer is duplication-free, driver-independent, and layer 2 is the actual enforcement. Alternative: inline the content via the `user`/SYSTEM.md channel for drivers with no native memory loading — revisit if a driver without one ever ships.
6. **Ticket ACs (phase 2) — recommended: an optional `## Acceptance criteria` section in the plan format** (`prompts/ticketing_format.md`), which the gate includes verbatim when the session has a ticket (`opts.ticket`): read the ticket + its `.plan.md` off the data branch via the existing `readDataFile` (precedent: the `fixes` lookup, `cli.ts:1036-1039`). Ship phase 2 only after v1 proves out.

## Considerations

- **Placement inside `maybeAutoHandoff`, after `commitPendingWork` (`cli.ts:1005`) and after the cheap `withheldMerge` checks (`cli.ts:1017-1023`)** — the existing reasons (`not-ready-for-merge`, `session-todo-open`) are free to compute; the gate costs a driver turn, so it runs last and only when the merge would otherwise proceed. It also runs after `maybeFireOnBeforeMergeable` (`cli.ts:434-438` ordering), so whatever that step committed is inside the gated diff.
- **What the gate agent reads**: the prompt instructs it to read `AGENTS.md` itself and run `git diff <base>...HEAD` in the workspace (base = the repo's default branch) — no template plumbing of file contents, robust to large diffs, and the re-read-fresh-at-the-gate property the ticket wants is literal. Skip the gate when the diff is empty (the `no-commits` handoff skip already exists as precedent, `events.ts:73`).
- **Recursion guard**: the gate run must carry no `onBeforeMergeable` and no handoff arming — same rule as `promptAgentSpec` (`cli.ts:1357-1360`); in-process `runAgent` with `kind: 'prompt'`, `vanilla: true`, `todoLoop: false` gets this for free.
- **Verdict format is pinned by test**, like the on-before-mergeable template's flattening rule: the prompt's last instruction demands the exact `VERDICT:` tail; the parser treats anything else as inconclusive (fail-closed per Solution 3). Parsing is a pure function with its own test.
- **Events**: extend `MergeWithheldReason` with `gate-violations` and `gate-inconclusive`, and add a gate outcome event (`{ kind: 'merge-gate'; outcome: 'pass' } | { outcome: 'violations'; violations: string[] } | { outcome: 'inconclusive'; error: string }`) — dashboard-started runs have no stdout anyone reads (`stdio: 'ignore'`, the #835 rule), so an outcome that is not an event is an outcome nobody learns. The dashboard's withheld-merge surface (`FEATURES-SPEC.md:119`) then shows the violation list.
- **PR body**: append the violations to the draft PR's description so the reviewer sees them on GitHub without opening the dashboard — best-effort, like the rest of the handoff cosmetics.
- **Cost**: one extra driver turn per armed-merge session, only on the success path. The gate uses the session's configured driver/model; no separate model knob (zero-users rule).
- **Prompt lives in `prompts/merge_gate_prompt.md` + SPEC** per the #551 convention, compiled by `scripts/gen-prompts.mjs` into `prompts.generated.ts`; rendered by a new `src/merge-gate-prompt.ts` mirroring `on-before-mergeable-prompt.ts` (template + tiny context + render fn).
- **False positives**: AGENTS.md rules are terse and judgment-laden ("prefer clean code"); the gate agent will sometimes over-flag. Withheld→draft makes that a bounded annoyance. If it proves noisy, the prompt can be tightened to "violations you can point at concrete diff hunks for" — a prompt change, not a design change.
- **What the gate is not**: it never *approves* — a pass only leaves the existing authorization intact (`withheldMerge` unchanged semantics); a human's Merge action still bypasses everything (#1391).
- **SPEC discipline** (per sdd.md): new `merge-gate-prompt.SPEC.md` (+ test SPEC), updates to `cli.SPEC.md`, `events` docs, `dashboard/agent-handoff.ts` doc block, `prompts/SPEC.md`; `FEATURES-SPEC.md` gains a feature line under the auto-merge cluster (`:116-122`), e.g. "Merge gate: the diff is checked against `AGENTS.md` before an unattended merge; violations withhold the merge (draft PR + reported reasons)".
- **SPEC.md human-ack rule** (the ticket's "Related"): out of scope here — it is a different gate condition (a `*.SPEC.md` path filter on the diff, no agent needed) and deserves its own ticket once this lands.

## Implementation

1. **Layer 1**: add the `AGENTS.md` bullet to `CONTEXT_DOCS` (`system-prompt.ts:116-139`); pin with the existing system-prompt tests.
2. **Prompt**: `prompts/merge_gate_prompt.md` + `merge_gate_prompt.SPEC.md` — read `AGENTS.md`, diff against `${{ tf.base_branch }}`, list violations, end with the pinned `VERDICT:` tail; `src/merge-gate-prompt.ts` (+ SPEC + test) renders it.
3. **Gate runner**: `src/merge-gate.ts` — `runMergeGate(cwd, driver, ...)`: in-process `runAgent` (`kind: 'prompt'`, `vanilla`, no todo loop), plus the pure `parseGateVerdict(text)` → `pass | { violations } | inconclusive`.
4. **Wiring** (`cli.ts`, inside `maybeAutoHandoff`): when `armed.merge && !mergeGate` after the existing checks, run the gate; map `violations`/`inconclusive` to the new `MergeWithheldReason` values, flip `armed.merge` off, emit the `merge-gate` event; thread the violation list into the PR description.
5. **Events & dashboard**: extend `events.ts` unions; surface the reason + violations wherever withheld merges already render.
6. **Tests**: verdict parser; `withheldMerge`/reason mapping; cli wiring with the fake driver (gate skipped) and an injected gate runner (violations → draft, pass → merge proceeds); prompt render.
7. **Docs**: SPEC updates + the `FEATURES-SPEC.md` line (step list above).
8. **Phase 2 (separate PR, after v1 proves out)**: `## Acceptance criteria` in the ticketing format + gate inclusion of ticket/plan ACs via `readDataFile`; optionally the one-round repair loop (Solution 4).
