# [Plan] Orchestration: a main agent runs subagents

What is left of the ticket after its steps 1 to 3 landed (#1903, #1904, #1905, #1906): the dashboard tree, the stop that reaches subagents, the settings, subagent questions, and check and retry, as five pull requests with the choices each one takes.

## Where it stands

- **Done.** `agent-runner run --parent --base`, the line a child's end sends its parent (`agent-runner/src/parent.ts`), and `packages/skill-orchestration`: `plan`, `start`, `list`, `read`, `stop`, `land`, with the plan saved beside the run record and `start` refused until the person's Approve.
- **Both open questions of the ticket are answered.** The names are a recorded pick (`skill-orchestration/DECISIONS.md`: "The words are main agent and subagent"), and the runner's `DECISIONS.md` now says a run is started by "the scheduler's call, a person's, or another run's agent's".
- **Left.** Steps 4 to 7, and two of the ticket's "choices made while planning" that no step built: stopping the main agent stops its subagents, and the main agent's top bar shows the cost of the whole plan.

## Problems

1. **The parent does not reach the dashboard as a field.** The runner's mark (`caller.runner.parent`) arrives on `AgentMeta` only by accident: `fromRunCard` (`framework/src/store/run-record.ts`) spreads every key under `caller`, so an undeclared `runner` object is there at runtime. The Framework never depends on the runner, so it cannot read the mark by its type.
2. **A subagent's end looks like the person spoke.** The line the runner sends the parent becomes an ordinary `start` diary line; the chat shows it with the "you" badge. The inbox line and the `start` line carry no sender.
3. **A stop reaches one process.** The dashboard's Stop signals one pid; child runs are spawned detached, in their own process groups. Worse, a child that ends after its parent was stopped resumes the parent (`tellParent` resumes any ended parent): stopping a main agent with three subagents would wake it three times.
4. **Where the orchestration settings live.** The dashboard's preferences are in `~/.the-framework.json`, which neither the runner nor a skill reads. The `orchestration` command needs the three models and the limit at `start`, also for a main agent the scheduler started.
5. **What "their default model" is** when nothing is set. The runner knows no default model; the dashboard's preference reaches a run only as `--model` on its start.
6. **Where a subagent's level is kept.** A retry goes "one level up" and happens once, so the level and "this is a retry" must be on record. The run card's `caller` is rebuilt by the runner at every write and keeps only the runner's own keys.
7. **A waiting subagent pings the person.** The runner runs the person's `ended:` line for every run that ends waiting, and the dashboard lists every waiting run under open questions. With step 6 the main agent answers first; the person would be told about a question that is not theirs yet.
8. **The checker's shape.** `--then` needs a pull request and its follow-up has no parent; subagents open no pull request. And a verdict that is only prose is one the main agent can skip, as an unapproved plan was before `start` refused.
9. **A failed subagent's branch.** `land` deletes a branch only after merging it. A task retried from scratch leaves the first attempt's branch here and on origin.

## Solutions

1. **`parent` beside the mark, in the shape the dashboard reads.** The runner already writes `host`, `pid`, `kind` and `workspace` at the top of `caller` for the dashboard; it writes `parent` there too (marker card and live card, kept on a resume). `AgentMeta` declares `parent?: string`. Alternative, not picked: `parent` as a field of `RunCard` in `skill-logs`; cleaner to read, but it moves a runner concept into the record's own shape and changes `runnerMark` and every reader of it. Shortcut, not picked: the dashboard reading `runner.parent` off the untyped spread.
2. **A sender on the message.** `InboxLine` (`agent-driver/core/src/inbox.ts`) and the `start` event and diary line gain an optional `from`: the id of the run that sent it. `tellParent` sets it; `run --resume` takes `--from <id>` for the resumed path. The chat draws a `start` with `from` as a subagent's row, not as "you". `planApproved` (`skill-orchestration/src/plan.ts`) skips a `start` that has `from`, which closes the quoting hole for good. Shortcut, not picked: the dashboard matching the words "The run … started for this run": the runner's wording becomes a contract nobody sees.
3. **The run stops its own children, and a stopped parent is not woken.** In the runner, a run stopped by a signal sends SIGTERM to every run on this machine whose live card names it as parent and whose pid is alive (the live cards under `.branches/*/.the-framework/`). `tellParent` does not resume a parent whose record says `stopped`: the person stopped it, and a message they send later continues it as today. Both are the runner's rules about `parent`, no skill named. Alternative, not picked: the dashboard's `sendStop` signalling the children; a stop from a shell or from `orchestration stop` on the main agent would miss them.
4. **The skill's own file, written through its own command.** `<project>/.orchestration/settings.json`, per machine, hidden from git by a `.gitignore` of `*` inside it (as the run's live directory is). `npx orchestration settings` prints `{ simple, hard, checker, limit }`; `npx orchestration settings <key> <value>` sets one, an empty value clears it. A model value is `<driver>` or `<driver>:<model>`. The package declares `"framework": { "orchestration": "orchestration" }` in its `package.json`, as `skill-logs` declares `runs`; the dashboard's Settings reads and writes through that command and shows the section only in a project that has it. Alternatives, not picked: three more keys in `~/.the-framework.json` passed to the run as environment (a scheduled main agent gets none, and a hook line has to carry them); the skill reading the dashboard's file (the skill would read a file of The Framework's shape).
5. **Nothing set means the main agent's own.** A level with no setting runs on the main agent's coding agent and the model its record names (the full id the coding agent announced). A main agent started from the dashboard carries the person's default model, so all three are "their default model" until changed, with no file read. The limit defaults to 4.
6. **One file of the skill's beside the plan.** `<main id>.subagents.json` on the data branch, beside `<main id>.plan.md` and deleted with the run like it: per subagent id, its `level`, and `retryOf` when it is a retry. A checker needs no entry: its record's `base` is the branch of the subagent it checks. Alternative, not picked: the level on the run card's `caller`, which needs the runner to carry keys it does not know through every rewrite.
7. **A run with a parent runs no `ended:` line and is no open question.** Its parent is told instead. The subagent's own page still shows the question and takes an answer; the dashboard's open questions, interventions and notifications skip a run that has a parent. When the main agent passes the question on, it asks it as its own, and that one is listed.
8. **The checker is a subagent started from the checked branch, and `land` reads its verdict.** `orchestration check <id>` starts a run with the caller as parent and `--base` the subagent's branch, on the checker setting's model, with fixed lines after the task: check it the way the task says, change nothing, and end the reply with one line `Verdict: pass`, `Verdict: changes needed` or `Verdict: fail`, the reasons above it. It commits nothing, so its branch goes with its checkout. `read <checker id>` answers `verdict`; a last reply without the line has none. `land <id>` is refused (`not-checked`, `not-passed`) until the newest checker of that branch ended with `pass`. No runner change. Alternative, not picked: a checkout attached to the subagent's own branch as `--then` does it, which needs a new runner flag and lets a checker commit onto the work.
9. **`orchestration discard <id>`.** Deletes an ended subagent's checkout and branch, here and on origin, without merging, and takes the branch off its record: the second half of `land`, shared with it.

## Considerations

- `start` takes `--level <simple|hard>`, required, and loses `--model` and `--driver`: the ticket says the agent never picks a model. This replaces the recorded bullet "unless the main agent's own task names another" (`skill-orchestration/DECISIONS.md`), so it is a person's pick, listed below.
- The limit counts the caller's children that are `running`, checkers included; a waiting one does not count. `start` and `check` over the limit are refused (`limit`, with the number), and the line says to start it when one ends.
- A hard task has no level above it: its retry runs on hard again. A retry is refused for a subagent that is itself a retry (`retried`): the main agent stops that task and tells the person, and goes on with the tasks that do not need it.
- `changes needed` continues the same subagent with the checker's reasons (`tell`, below), then a new check. One round: a second verdict that is not `pass` is treated as `fail`.
- `orchestration tell <id> "<text>"` continues an ended subagent with a message, through the runner's detached resume, refused while it runs. It serves an answer to a waiting subagent (sent as `--answer`, so the subagent gets the continuation wording) and a checker's change request (sent as text). One command, not two.
- The subagent's fixed lines change in step 6: "Nobody will answer a question: decide yourself" becomes "ask only what you cannot decide; the agent that started you answers". `taskOf` strips whichever lines the record ends with.
- The sidebar: a subagent whose parent is not in the list (deleted, or past the Overview's 30) is a row of its own. `buildRecentAgents` caps top-level runs, and children come with their parent, so four subagents do not push four runs off the Overview.
- A folded parent says how many subagents it has and how many still run. It unfolds on its own while one is selected.
- The row title of a subagent is its prompt's start, so the fixed lines after the task show only when the row is expanded. Left as is.
- Cost: `AgentDetails` sums the run's own `usage` events; the plan's cost adds each child's card `cost` from the list the page already polls. A Codex run reports no price: the strip says "plus N subagents with no price reported" and does not show a total that looks complete.
- The Logs page reads cards without `caller`: no tree there. Not planned.
- A subagent on another machine is not stopped by the cascade: only this machine's pids are signalled, as `orchestration stop` already refuses.
- A stopped child still tells a working parent. Only a parent that is itself `stopped` is left alone, so the cascade's own children's ends go nowhere.
- Every changed source has a `LOGIC.md` beside it, and `.agents/skills/orchestration/SKILL.md` is a tracked copy of the package's `SKILL.md`: read the `logic-driven-development` skill first and update both with the code.
- Cheap models (the ticket's DeepSeek note) need a third coding agent or an endpoint setting. Not planned: a model value names a coding agent the runner already has.

## Implementation

One pull request each, in this order. After the third the ticket's goal 1 to 4 and 8 hold; the last two add goals 5 to 7.

1. **Dashboard: the tree, the live lines, the plan's cost** (ticket step 4).
   - `agent-runner`: `parent` at the top of `caller` in `markerCard` (`records.ts`) and the live card (`run.ts`), kept by `lasting`. `--from <id>` on `run --resume` (`cli.ts`, `runner.ts`); `tellParent` sets `from` on the inbox line and the resume.
   - `agent-driver/core`: `from?` on `InboxLine`, on the `start` event (`cli-session.ts`) and its diary line (`session-log.ts`).
   - `framework/src`: `AgentMeta.parent` (`store/agent-store.ts`); `eventOf` carries `from` on a `driver`/`start` (`store/run-record.ts`); `buildRecentAgents` caps top-level runs (`dashboard/overview.ts`).
   - `framework/dashboard`: `AgentHistory.tsx` groups rows by `parent` into a foldable parent row with its children indented under it. `EventList.tsx`: a `start` with `from` is a "subagent" row linking to that run. `AgentView.tsx`: a strip above the composer, one line per child that is running or waiting (status pill, task, since when, click to open), from the `onAgents` poll. `AgentDetails.tsx`: "Spent" adds the children's cost.
   - `skill-orchestration/src/plan.ts`: `planApproved` skips a `start` with `from`.
   - Tests: `records.test.ts`, `parent.test.ts` (the `from`), `run-record.test.ts`, `overview.test.ts`, component tests for the grouped sidebar and the subagent row, one e2e story with a fake parent and child record.
2. **Runner: a stop reaches the children** (the ticket's "stopping the main agent stops its subagents"). `run.ts`: on a signal, after the agent's process tree is ended, SIGTERM to each live child on this host. `parent.ts`: no resume of a parent recorded `stopped`. Tests in `run.test.ts` and `parent.test.ts`. Two bullets for the runner's `DECISIONS.md`, proposed below.
3. **Settings and levels** (ticket step 5). `skill-orchestration/src/settings.ts` (the file, its read, its set, the model value's parse) and `ledger.ts` (`<main id>.subagents.json`, written through `withFileBranch` like the plan); `cli.ts`: `settings`, and `start --level`; `subagents.ts`: the level's model and coding agent, the limit, the ledger entry. `package.json`: the `framework` key. `framework`: a read and a write through the declared command (as `store/runs.ts` runs `logs`), and an "Orchestration" section in `SettingsPage.tsx`: Simple, Hard and Checker, each the launcher's `DriverModelMenu` with "the main agent's own" as the empty choice, and "Subagents at once". `SKILL.md`: each task of the plan says simple or hard; `--level` on `start`.
4. **Subagent questions** (ticket step 6). `cli.ts`/`subagents.ts`: `tell <id> <text>`, through `resumeDetached`. `SUBAGENT_LINES` reworded. `SKILL.md`: on `ended waiting`, answer with `tell` when the plan or the code decides it, else ask the person the same question with the question block and pass their answer on with `tell`. `agent-runner/src/run.ts`: no `ended:` line for a run with a parent. `framework/src/dashboard/open-questions.ts`, `interventions.ts` and the notification read skip a run with a parent.
5. **Check and retry** (ticket step 7). `cli.ts`/`subagents.ts`: `check <id>`, `retry <id>` (a new subagent on the same task with the checker's reasons, one level up, `retryOf` in the ledger, the first attempt discarded), `discard <id>`; `verdict` on `read`; `land` refused without a `pass`. `SKILL.md`: check every ended task, land on pass, `tell` on changes needed, `retry` on fail, and on a second fail tell the person and go on with what does not depend on it. Tests in `cli.test.ts` with the injected `spawn`, as today.
